# A release is what the tag pipeline publishes

A channel of Repon's is whatever its tag pipeline publishes, and nothing is published by hand. A channel commits to publishing every time rather than once, and the only mechanism that keeps such a commitment is the pipeline itself. The evidence is a comparable project whose crates.io leg sat outside its pipeline: it went stale at the first release nobody remembered to publish, and stayed stale for the next twelve while every channel inside the pipeline advanced.

So a channel outside the pipeline is not a channel. crates.io publishes from a workflow the tag triggers, beside the jobs that build the binaries and push the tap formula, never from a command someone remembers to run. A version label on the pull request decides the bump, and merging that pull request cuts the tag. `just ci` is the single definition of CI, so a check added locally reaches the pipeline in the same commit. The library publishes in lockstep with the binary and its surface is permanent once it is on the index, which is why the pre-publish gate is a gate and not a wish.

**Enforcement:** `just workflows` (`justfile`, its own job in `.github/workflows/ci.yml`) parses every workflow and fails if a local `uses:` names a file that is not there, so the tag-triggered chain cannot silently break. `just publish-check` rehearses `cargo publish --workspace --dry-run` and fails if the rehearsal verified a stale extraction. `modules_the_release_gate_names_are_private_at_the_crate_root` in `crates/repon-core/src/lib.rs` reads the gate's own list out of [releasing.md](../spec/releasing.md) and fails if a module it names is public. Nothing prevents a person running `cargo publish` by hand; the rule against it is unenforced.
