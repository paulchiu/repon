# A release is what the tag pipeline publishes

A channel of Repon's is whatever its tag pipeline publishes, and nothing is published by hand. Until beta there is no tag pipeline, so there is exactly one channel: `cargo install --git https://github.com/paulchiu/repon --locked repon`, which works today in 44.9 seconds, measured 2026-08-30 on macOS with rustc 1.95.0, like every figure in this document. At beta, crates.io becomes a channel, and its publish is a job in the same pipeline that cuts the tag, never a command someone remembers to run. The repository is 15 commits old with no tags, so the rule costs nothing to adopt now and everything to retrofit later. The one live channel has one recorded sharp edge: on a machine whose git config rewrites GitHub HTTPS to SSH (`url.ssh://git@github.com/.insteadOf https://github.com/`, present on the owner's own machine) the command fails with "no authentication methods succeeded", and succeeds with the rewrite still in place once `CARGO_NET_GIT_FETCH_WITH_CLI=true` is set. The channel's cost is also measured: a cold release build with an empty CARGO_HOME is 50.2 seconds wall, 124.8 seconds CPU, 333 packages, 175 MB of registry plus 350 MB of target, which is what every `cargo install --git` user pays and what a binary channel would remove; that trade is refused below.

The rule is about the pipeline rather than about which channels to pick, and the evidence is the owner's own comparable project. blubat is a two-crate Rust workspace of the same shape as Repon (`blubat-core` plus `blubat`, resolver 3, edition 2024, MIT), serving here the role the owner's tuicr config serves in [0014](0014-config-is-read-only-and-a-set-bounds-the-work.md) and mrx serves in [0003](0003-clean-room-from-mrx.md): the nearest shipping comparable, mined for evidence rather than copied. It published `blubat 0.4.0` and `blubat-core 0.4.0` to crates.io on 2026-08-02 and has published nothing since, while its repository has shipped through v0.17.2 on 2026-08-21, thirteen releases later, through GitHub Releases and a personal Homebrew tap. `cargo install blubat` today installs 0.4.0. The cause is structural, not an oversight: blubat's release pipeline is generated by cargo-dist 0.32.0, whose jobs are plan, build-local-artifacts, build-global-artifacts, host and publish-homebrew-formula, and dist states its own scope boundary as not handling "publishing to crates.io". Every channel inside the pipeline advanced thirteen times; the one channel outside it went stale at the first release nobody remembered to publish and stayed stale for the next twelve. A channel is not a decision to publish once, it is a standing promise to publish every time, and the only mechanism that keeps the promise is the pipeline itself. That is why the decision is a rule about where publishing lives rather than a list of channels to open.

Publishing `repon-core` is forced, not chosen. `cargo publish -p repon` fails today with "all dependencies must have a version requirement specified when publishing. dependency `repon-core` does not specify a version". Adding the version is one line, and the binary still cannot reach the registry unless the library is there first, so the beta publish is two crates or none, in lockstep, which [0015](0015-the-core-owns-the-table.md) already decided ("no separate versioning") and this ADR inherits rather than decides. What that makes the first publish is a permanent commitment to `repon-core`'s public surface. Cargo's own words: "a publish is generally permanent. The version can never be overwritten, and the code cannot be deleted." And the surface being committed is one 0015 has already scheduled for demolition: it says "`fanout` and `git` become private modules" and that the `Box<dyn std::error::Error + Send + Sync>` placeholder "is not `Clone` and cannot survive", while `crates/repon-core/src/lib.rs` says in its own doc comment "What this crate exposes is not settled." Publishing an unsettled surface to an index that never forgets is the first of two blockers on the first publish: 0015's demolition lands before the first tag, or the crates that go up at 0.1.0 carry modules already condemned.

One claim made while deciding this, not in the survey behind it, was wrong and is corrected here rather than quietly: that the binary's publish cannot be rehearsed until the library is permanently on the index. That is true of `cargo publish -p repon`, which fails as above, and false of `cargo publish --workspace --dry-run`, which packages and verifies both crates and exits 0 because it resolves the sibling from the workspace. The release is one command and it is fully rehearsable, which is what lets `just publish-check` run on every change rather than being a ritual performed once, blind, at beta. The rehearsal already earned its keep by catching a packaging defect: six of six of Repon's direct dependencies (ratatui, gix, clap, serde, rayon, crossterm) ship licence text inside their `.crate`, and neither Repon crate did, because `README.md` and `LICENSE` sit at the workspace root and cargo only includes files inside the package directory. Packaged, `repon-core` is 8 files, 48.3 KiB, 14.9 KiB compressed, and `repon` is 15 files, 108.8 KiB, 31.2 KiB compressed.

The second blocker is [0014](0014-config-is-read-only-and-a-set-bounds-the-work.md)'s unfinished move. 0014 settled config at `~/.config/repon/config.toml` and recorded at its own line 17 that the move to `etcetera` "is recorded, not done: the map's destination is decisions, not features". `crates/repon/Cargo.toml` still carries `directories = "6.0.0"` and no `etcetera`, so a published 0.1.0 would read config from `~/Library/Application Support/repon/` on macOS, the location 0014 argues at length is wrong, and moving it after a release breaks a user-visible path with no migration story. A decision that was safely not done while the only installers were people reading the repository becomes a shipped defect the moment an index hands the binary to someone who has read nothing. The two blockers together are the pre-publish gate, and [releasing.md](../spec/releasing.md) carries the gate in full.

The crates say Unix-only, and the restriction lands on the library. The workspace compiles clean for `x86_64-pc-windows-msvc` today, a 27.2 second `cargo check` with no errors, so the window is open right now and [0018](0018-an-action-is-a-fanout-of-pty-backed-steps.md) closes it: [actions.md](../spec/actions.md) puts `setsid(2)` in `pre_exec`, `openpty(3)` through libc and `/dev/null` on stdin, and [0015](0015-the-core-owns-the-table.md) assigns Action fan-out and the child-process environment contract to the core, so the crate that cannot be ported is `repon-core` rather than the terminal crate. A `compile_error!` guarded by `cfg(not(unix))` now sits in `crates/repon-core/src/lib.rs`, turning compiles-today-breaks-at-0018 into a stated refusal. docs.rs builds five default targets and two of them are Windows (`x86_64-pc-windows-msvc` and `i686-pc-windows-msvc`), so both crates carry `[package.metadata.docs.rs] targets` restricted to a Linux and a Darwin triple; without that, two of the five documentation builds fail on the guard by design. The distribution survey's recommended five-target list included `x86_64-pc-windows-msvc` and is dead on arrival.

`rust-version` was declared nowhere, and the survey's reason for declaring it was too weak. The effective floor is 1.88.0, set by twelve lockfile packages (ratatui 0.30.2 with its five sibling crates, darling 0.24.1 with two, time 0.3.55 with one, and instability 0.3.13), not by ratatui alone as the survey said. 1.88.0 builds and tests the workspace clean, measured, so the declaration is a promise true on the day it is made rather than the untested claim the survey named as the biggest regret risk. The stronger reason is resolution, not documentation. The workspace already sets `resolver = "3"`, and cargo's own message shows what the declaration changes: `cargo update --dry-run` with nothing declared reads "Locking 1 package to latest Rust 1.95.0 compatible version", using whatever toolchain happens to be installed, against "Locking 1 package to latest Rust 1.88.0 compatible version" once 1.88 is declared. The resolved lockfile is identical today either way, `generic-array` held at 0.14.7 in both, so the effect is latent rather than current; what it buys now is that `cargo update` stops depending on whose machine runs it.

The pipeline needs something to gate on, and the repository had no `.github` directory at all. The gates start green: `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` (3 tests) and `cargo doc` under `RUSTDOCFLAGS=-D warnings` all pass on the untouched tree, so adoption costs nothing and every future red is a new defect rather than inherited noise. A `justfile` owns what CI means and the workflow runs `just ci`, the arrangement copied from blubat, so a green local run is a green pipeline and the two cannot drift; there is no second list of checks living in YAML to fall behind the first. The justfile is also where [0015](0015-the-core-owns-the-table.md)'s enforcement finally lands, strengthened. 0015 asked for "one CI line asserting repon-core's dependency tree contains no ratatui and no crossterm"; `check-core-isolation` is an allowlist instead, asserting the core's direct dependencies are exactly `crossbeam-channel gix rayon`, because a denylist stops the two crates somebody thought to ban and an allowlist stops the rendering crate nobody did. Standard GitHub runners are free on public repositories, macOS included, so the test job is a matrix over `ubuntu-latest` and `macos-latest`, with no Windows leg for the reason the `compile_error!` already states.

What was refused, each with its reason. Reserving the crate names with a placeholder publish: RFC 3463 permits reserving "only to a certain degree and if you have a good reason for it", and the answer to what release one is for is shipping rather than reserving; the risk that leaves open is real and named below. Prebuilt binaries before beta: the release binary is 1,599,200 bytes and 774,513 gzipped, so the asset is cheap, but there is nobody to hand it to. Homebrew before beta: the repository is two days old with 0 stars, 0 forks and 0 watchers, and homebrew-core's own rule that "a code repository less than 30 days old is normally not eligible" rules it out before the notability bar of 90 forks, 90 watchers or 225 stars for a self-submission is even reached. release-plz: its value is coordinating a release-PR review cycle that does not exist with one maintainer. A support-window MSRV promise: the floor is a measured fact that moves with the lockfile, not a policy to defend. A Windows CI leg: it would test a platform the library refuses at compile time.

The namespace risk is stated plainly rather than buried. `repon`, `repon-core`, `repo-n` and `repo_n` are all unclaimed today, and not publishing leaves them that way for as long as beta takes. The neighbourhood is not empty: `reponest` 0.1.0-alpha, published 2025-12-14, describes itself as "A TUI/CLI tool for managing multiple git repositories written in Rust", and `gitpane` describes itself as "Multi-repo Git workspace dashboard TUI" with 1,638 downloads and a release dated 2026-08-29, yesterday. The names sit in an active corner of the index, and deciding to ship rather than reserve accepts that risk with open eyes.

## Consequences

- The pre-publish gate has two members and [releasing.md](../spec/releasing.md) carries it in full: [0015](0015-the-core-owns-the-table.md)'s surface demolition (`fanout` and `git` private, the `Box<dyn Error>` placeholder replaced) and [0014](0014-config-is-read-only-and-a-set-bounds-the-work.md)'s move to `etcetera`. No tag pipeline is built until both close.
- `repon-core` becomes a public crate whose API 0015 will break. 0015's rejection of `#[non_exhaustive]` was reasoned against an in-repo consumer and now gets a wider audience it was not argued for; it stands, but unre-argued, and a real external consumer is the evidence that would reopen it.
- The gutter of channels is now empty by choice, and the README says so: no crates.io, no Homebrew, no binaries until beta, one install command, and the `CARGO_NET_GIT_FETCH_WITH_CLI=true` caveat for machines that rewrite GitHub HTTPS to SSH.
- `just ci` is the definition of CI in both places: the workflow runs it and nothing else, so a check added locally reaches the pipeline in the same commit and a green local run is a green pipeline.
- The Unix guard means the workspace no longer builds for Windows, deliberately. The clean 27.2 second `cargo check` for `x86_64-pc-windows-msvc` was the last one, and both crates' docs.rs target lists exclude the two Windows triples the guard would fail.
- `rust-version = "1.88"` is a declared fact, not a support promise. Its resolution effect is latent today (identical lockfile with or without it), and when a dependency raises the floor the declaration moves rather than being defended.
- The missing version requirement on the `repon-core` dependency and the missing licence text in both packaged crates are fixed here, and both were found by rehearsing rather than by reading. `just publish-check` runs that rehearsal on every change, since `cargo publish --workspace --dry-run` verifies both crates without touching the index, so the next defect of that shape is found the same way.
- The unclaimed names stay unclaimed, and `gitpane`'s 2026-08-29 release shows the neighbourhood is moving. That is the accepted cost of refusing a placeholder publish.
- The tag pipeline itself is not designed here and is the next ticket: whether it is dist (whose scope boundary excludes crates.io, so a publish job is added beside it) or hand-rolled, and whether crates.io trusted publishing can be configured for a crate that does not exist yet, which is unverified.

## Amended by #416

The pipeline this ADR left as "the next ticket" is now built, and it is dist rather than hand-rolled. The rule is unchanged: every channel is fed by the tag, and nothing is published by hand. What changed is the reading of dist's scope boundary. dist does not publish to registries, which is the fact this ADR rests its blubat evidence on, but it does accept a custom publish job, so crates.io runs inside the pipeline as `.github/workflows/publish-crates.yml` rather than beside it. That is the first of the two options this ADR's own last consequence named, taken for the reason it named: dist already builds the binaries and pushes the Homebrew formula, and reimplementing those to keep a hand-rolled crates.io job would trade the whole of dist for one job dist has a seam for.

blubat's thirteen-release staleness therefore stands as evidence for the rule and is no longer evidence against dist. It went stale because its crates.io leg sat outside its pipeline entirely, not because dist forbade one.

Two deferrals also expire. Prebuilt binaries and Homebrew were each refused for want of anyone to hand them to, and Homebrew additionally against homebrew-core's age and notability bars. A personal tap has neither bar, this ADR itself named a tap as the path, and `paulchiu/homebrew-tap` already exists, so the refusal now rests on the audience argument alone, which the maintainer has answered: the app is good enough to publish.

The version bump moves too. It was a hand-run `cargo set-version` on `main` after each merge, which moved the number on every change while a tag was cut only when someone remembered, the same gap between a channel and a standing promise this ADR is about. A version label on the pull request now decides the bump, and merging a labelled pull request cuts the tag.
