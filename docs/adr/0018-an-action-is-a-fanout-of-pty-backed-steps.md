# An Action is a fan-out of PTY-backed steps, and its result is a receipt rather than a reading

> Superseded in part by [0020](0020-the-ascii-glyph-set-is-vetted-over-the-row-interior.md), whose glyph table gives `capture elision` a mark in each set, and by the change that drew the mark from there: the elision line the capture bullet below records is no longer written into the captured bytes. `bound_head_and_tail` writes nothing between the kept head and the kept tail, the core reports the drop beside the bytes as two counts, how many lines went and how many kept lines precede the gap, and the detail pane inserts the row from the live glyph set at render time. Everything else in that bullet stands: head 200 plus tail 200, cut on a char boundary, and the ONLCR and bare-`\r` rules.

An Action's result is a receipt of something Repon did, not a reading of the world, and that one distinction decides most of what follows. Every reading in Repon lives in a `Cell`: it carries the Generation that produced it and a staleness flag, the poll marks it Stale, a newer Generation supersedes it, and `Presence::Vanished` turns every cell Stale at once. All four are machinery for keeping a claim about a moving world honest, and a receipt makes no claim about the world: it records that a command ran, where, and how it exited, facts no later look at the filesystem can contradict. So the result is not a `Cell<T>`, never goes Stale on a poll, is not superseded by a Generation, and does not persist. What the world looks like after the run is the next Generation's question, asked through the same path as every other reading.

The result lives in a new field on `EntityState`, Diagnostics-shaped (per-entity, not a cell) but fold-eligible. Plain `Diagnostics` cannot hold it, because [the core API spec](../spec/core-api.md) says such facts "reach the detail pane and never the list" and excludes them from the row-summary fold, and the partial-failure requirement needs the list. So an Action failure marks the row `!`, entering the gutter through the derivation route [0017](0017-discovery-stops-at-the-repo-boundary.md) already opened when it let an unparseable `.gitmodules` make a row Failed with no blank cell. The cost is stated plainly: `!` now means both "Repon could not read this repo" and "your command exited nonzero", so a perfectly readable Repo can carry a provenance mark. The alternative is a new column out of a 90-column budget, and [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md)'s own prototype already rejected a glyph in every cell for noise; the detail pane is what distinguishes the two, the same trade 0017 accepted when a Submodule row and a Worktree row came to look alike.

A step's child goes into a new session with `setsid(2)` in `pre_exec`, and setsid stands alone because it cannot be combined with the obvious safe API: Rust's `CommandExt::process_group(0)` is `setpgid(0,0)`, which makes the child a process-group leader, and setsid then fails with EPERM. Measured directly: setpgid-then-setsid fails, setsid alone returns 0, setpgid alone returns 0, so the contract is setsid through `pre_exec` (unsafe) or the command-group crate, never `process_group`. setsid earns its unsafe block by doing three jobs at once. It makes `killpg` reach grandchildren: `Child::kill` was measured leaving a backgrounded grandchild alive and reparented to launchd, where under setsid the pgid equals the pid, the group held the shell plus two sleeps, one killpg took all three with wait status -9, and the group was empty afterwards. It detaches the controlling terminal, so a step cannot write over Repon's alternate screen: under a real controlling terminal a plain child's `echo X > /dev/tty` reaches the screen while a setsid child gets "/dev/tty: Device not configured", and `Stdio::null()` on all three descriptors does not prevent it. And a killpg against Repon's own process group would kill Repon too, so the new session is mandatory rather than an optimisation. stdin is `/dev/null`: a child that inherits stdin and reads it was measured hanging forever while holding a concurrency slot, where with `/dev/null` it gets EOF and exits with its own code, which is the warning BSD xargs(1) carries verbatim ("Undefined behavior may occur if utility reads from the standard input"), and [refresh.md](../spec/refresh.md) already states the governing rule for the periodic fetch: "a prompt behind the alternate screen is a hang with no visible cause". `GIT_TERMINAL_PROMPT=0` is set for every step, and the fifteen git local environment variables [config.md](../spec/config.md) lists stay unset.

stdout and stderr both point at one PTY slave rather than a pair of pipes, because the owner's requirement is that colours survive capture: the pane is a mini shell showing the run, not only a report of it. Pipes cannot deliver that. Neither `CLICOLOR_FORCE=1` nor `FORCE_COLOR=1` recovers colour from git or cargo through a pipe; only two things work, the command asking itself (`--color=always`, `-c color.ui=always`) or a PTY, under which every case tested emits colour, so colour through pipes would be a near no-op. The PTY is built on `openpty(3)` through libc, already in Repon's dependency tree via backtrace/color-eyre and cpufeatures/sha1, not portable-pty, which pulls anyhow, downcast-rs, filedescriptor, log, a second nix version, serial2 and shell-words; openpty plus setsid plus a null stdin was verified capturing git's real colour, `## \x1b[32mmain\x1b[m...\x1b[31morigin/main\x1b[m\r\n`, green branch and red remote. Merging the two streams into one costs nothing the design promised, since [layout-and-provenance.md](../spec/layout-and-provenance.md) promises output "per step, labelled, separately readable", per step and not per stream, and a merged stream preserves the true write order a shell shows. The PTY is a fixed 120 columns and not a config key: tools wrap to the width they are given, so output is wrapped once at capture and read later at whatever width the pane happens to be, 120 is wide enough that cargo and git format normally, and a constant width means the same output never re-wraps differently between two readings. The honest cost, stated rather than hidden: a PTY widens the class of programs that hang. Under pipes `less` exits cleanly with code 0 while `vim` and `top` hang anyway; under a PTY `less` hangs too. The PTY widens that class rather than creating it, and a repainting program is not a memory problem, since `top` on a PTY emits only 9 KiB per second.

Captured colours are rendered rather than stripped, the owner's explicit override of the recommendation to strip them, and rendering them takes a parser, because ratatui-core 0.1.2 silently drops every control character: src/text/span.rs:314 and buffer.rs's `set_stringn` both filter on `!symbol.contains(char::is_control)`, so raw bytes fed straight in render `\x1b[1;31merror\x1b[0m[E0308]` as the literal `[1;31merror[0m[E0308]`, and an 11-frame CR progress bar collapses to one 286-character line of concatenated frames. ansi-to-tui 8.0.1 works against ratatui 0.30.2, verified by compiling it: it parses that string into ("error", Red) and ("[E0308]: mismatched types", Reset), and its dependencies are nom, ratatui-core, simdutf8, smallvec and thiserror. The parse happens in the consumer, never in repon-core, because ansi-to-tui produces ratatui types and the core has a CI line asserting its tree contains no ratatui; the core stores raw bytes and the consumer parses SGR into spans at render time, which reinforces [0015](0015-the-core-owns-the-table.md)'s seam rather than bending it. The detail pane wraps rather than truncates, because there is no horizontal scroll key in the `detail` context and adding one would spend a binding to reach content vertical scroll already reaches; the longest real line measured, 1,653 characters from `cargo build -v`, is 16 wrapped rows at the pane's 104-column interior. Under `NO_COLOR` the captured SGR is stripped too, because that variable is a statement about the whole screen, not about Repon's share of it. The honest cost: [0011](0011-themes-correct-the-terminal-palette.md) makes a theme a correction layer over the terminal's own palette, [theming.md](../spec/theming.md) states that no meaning is carried by colour alone, and captured output is the first surface in Repon that neither rule reaches, a child's red sitting beside `danger` red on the same screen. The reconciliation: captured output is a quotation of another program's screen rather than one of Repon's own surfaces, so the theme deliberately does not reach inside the quoted region, while Repon's own step labels keep their roles and sit outside it.

The fan-out runs on its own thread pool, sized by `concurrency`, never on rayon's global pool, which replaces the shape the code already has: crates/repon-core/src/fanout.rs uses the global pool and [the core API spec](../spec/core-api.md) puts probes there too. A step blocked in `wait()` removes a worker from that pool and rayon does not grow to compensate. Measured on 18 rayon threads, a 403-entity probe fan-out dispatched 300ms into an Action whose tasks block for 5 seconds: concurrency 4 gives 174ms, 9 gives 287ms, 17 gives 2,486ms, 18 gives 4,836ms and 26 gives 5,025ms. At concurrency 18 the refresh makes no progress at all, and refresh.md's 30 second generation deadline then turns every outstanding cell to Unknown(TimedOut) for reasons that have nothing to do with git, which is exactly the lie [0001](0001-per-cell-provenance.md) exists to prevent. A `concurrency` of 16 or 32 for network-bound steps is a reasonable thing for a user to write and the schema has no maximum, so the separate pool needs no config key, following [0013](0013-no-filesystem-watching-a-refresh-is-a-cancellable-generation.md)'s own reasoning about gix's per-repository thread limit being "a measured property of two libraries rather than a taste". The settled default of 4 is separately confirmed as the right number: the same git action over 403 entities took 17.63s at concurrency 1, 5.41s at 4, 5.60s at 8 and 5.17s at 16, so the plateau starts at 4.

Starting an Action cancels an in-flight Generation rather than sharing the machine with it. Measured: an Action over a 60-entity Selection takes 0.85s alone and 3.14s while a Generation runs, a 3.7x penalty, while the Generation itself barely moves, 7.06s to 6.82s. The background read crushes the thing the user asked for, which is the same trade [refresh.md](../spec/refresh.md) already made when it chose cancelling at 1.04x over draining at 1.79x. Completion starts one normal Generation, following the precedent refresh.md sets for a finished fetch: "A finished fetch starts a normal generation, so the new behind counts arrive through the same path as everything else." The ticket's own framing, each Repo re-probed first the way a Launcher return already does, does not survive measurement: `probe_now` is synchronous and single-entity, and forty of them is 0.44s at best and about 3.6s under the contention the fan-out itself creates, which is a frozen TUI. The stated cost: the first Repo to finish shows stale cells for the length of the run, which is precisely the compare-failures window.

A step's outcome is a closed set of four: Ok, Failed carrying the exit code, NotRun because an earlier step failed, and Cancelled. This fixes a defect already sitting across three specs. [config.md](../spec/config.md) says steps run in order and stop at the first failure with implicit gating, which admits exactly two outcomes; [layout-and-provenance.md](../spec/layout-and-provenance.md)'s detail-pane mock draws `step 1 ok` then `step 2 skipped no upstream configured`, a step that neither ran-and-succeeded nor was blocked by an earlier failure; and [theming.md](../spec/theming.md)'s role map gives `warn` to "a skipped Action step" while giving no role at all to a failed one, since `danger` is "Failed provenance, a Gone Worktree" only. Two specs describe an outcome the third forbids, and the one outcome the whole feature exists to surface is unthemed. `skipped` is deleted from theming.md, `danger` gains a failed Action step, and the mock is corrected. Cancelled is not a failure and does not colour as one, following [0013](0013-no-filesystem-watching-a-refresh-is-a-cancellable-generation.md)'s precedent that interrupted work becomes Unknown rather than Failed.

The compare-failures loop is the workflow the result exists to serve, and the owner's stated bar for it: it is fine for the row to carry only a status, as long as there is a way to see output detail for the erroring ones and it is legible. Three gaps stood between that bar and the settled design, all real: no binding jumped to a failure, `EntityState` carried no Action outcome so the Filter predicate could not express "failed", and no spec ever asserted that an open detail pane re-targets when the cursor moves. All three close here. `n` and `N` in the `list` context step to the next and previous failed row; they are free, because `n` is bound only in `confirm` and contexts do not overlap, the same split [keybindings.md](../spec/keybindings.md) already defends for Ctrl+U being half-page in three contexts and clear-line in the fourth, and better, that spec records that Repon has "no backward to search", which is exactly why the vim search pair was never claimed. The new `EntityState` field makes a `failed` Filter term expressible, and the spec now states plainly that while the detail pane is open beside the list, moving the cursor re-targets it.

The result's whole life is the session: it lives in memory and dies with the process, and nothing about it is written anywhere. That satisfies "keep until the next run" exactly, with no key, no clock and no expiry, and the "configurable expiry" half of the recorded requirement is dropped, said plainly here rather than left quietly unimplemented. The measurements sit on the other side of the ledger, taken with the pinned toml crate: an 8 KiB per-step bound across 403 entities is a 3.2 MiB state.toml costing 15 to 26ms to serialise, 64 KiB per step is 25 MiB and 80 to 165ms, and an unbounded 1 MiB policy is over 400 MB and more than a second, all paid at startup against refresh.md's 50ms first-frame budget. Four comparable tools (pueue, GNU parallel, ansible, turbo) independently split a small structured metadata record from the output text and never put both in one blob, so even a Repon that persisted would not persist this shape. config.md's "Where it lives" table has exactly one log, repon.log, whose documented purpose is warning detail behind `w`; captured output does not go there and no new path row is added.

Suspend and quit are a genuine conflict between three settled sentences, named as such rather than papered over. [core-api.md](../spec/core-api.md) assigns Action fan-out to the core because "No terminal is involved"; [refresh.md](../spec/refresh.md) says all background work stops while the TUI is suspended; and core-api.md says pause and resume exist because of that and "The core is not told why", listing the reason it was paused among the things the core does not know. For probes that ignorance is free, because cancellation costs 0.5 to 0.9ms and the work is idempotent and re-runnable. For a child process it is not: suspending means SIGSTOP then SIGCONT, quitting means SIGTERM then SIGKILL, and the core is contractually forbidden the information that tells them apart. The resolution: pause stays ignorant, and the fan-out gets its own hold and stop verbs, so nothing needs a reason and the sentence stands. Ctrl+Z stays ungated and SIGSTOPs the step groups, where `q` and Ctrl+C are gated behind a confirm, [keybindings.md](../spec/keybindings.md)'s "because quitting orphans the children"; the asymmetry is deliberate and recorded, since suspending is reversible where quitting is not. Teardown respects that SIGTERM is trappable, measured: `trap '' TERM; sleep 300` survives SIGTERM and dies on SIGKILL with status -9. So the stop verb is SIGTERM to the group, then SIGKILL after a grace, the shape of GNU parallel's default `--term-seq`, 350ms of TERM pulses before KILL.

One Action runs at a time, which replaces a state of affairs in which two at once was forbidden nowhere. [keybindings.md](../spec/keybindings.md) names six contexts and `running` is not among them, so as specified, `;` opens the Action palette again mid-run, `s` and `1` to `9` switch Set and re-run discovery, so in-flight step results arrive for EntityKeys no longer in the table with no Generation to arbitrate them, and Ctrl+R reloads config, which [config.md](../spec/config.md) says re-applies `[[action]]` immediately, possibly deleting the running one. All four are inert while a fan-out is in flight. `!` stays live, because handing one Repo to lazygit while another installs is a thing a person may legitimately want. The honest cost falls on [0016](0016-one-binding-table-feeds-every-surface.md): an inert key is a binding conditional on runtime state, and 0016's table is a pure function of context, one of six named panes, never of runtime state. The footer is derived and follows along fine, but the help overlay and the load-time collision check run over the static table, and 0016 spent a paragraph rejecting lazygit's GetDisabledReason mechanism as the thing that makes the escape hatch vanish where a user is most lost. The price is recorded here openly rather than discovered in review.

Run progress renders in the header, and the header gains the degradation rule it never had. Composed from what the specs already require, [0006](0006-no-git-state-cache-session-state-by-name.md)'s match count, config.md's `worktrees: 161 (preference off)` beside it and a restored Filter announcing its own count, the header is already 85 columns against an 88-column narrow screen and a 90-column list, and run progress makes it 107. The footer got four explicit rules, a measured drop table and a width-check-every-item mandate from [0016](0016-one-binding-table-feeds-every-surface.md); a grep for a header degradation rule across [layout-and-provenance.md](../spec/layout-and-provenance.md) and [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md) returns nothing. The rule, modelled on the footer's four, is a priority order while a run is in flight: the entity count, then run progress, then the Filter's match count, then the worktrees note, then timing. This closes a pre-existing gap rather than routing around it, and it is cheap because 0016 already worked the rules out.

The Action palette shows the Selection count, and [GLOSSARY.md](../../GLOSSARY.md) is corrected to stop promising a count the schema cannot compute. Its Action entry says the palette shows how many of the selected Repos "define it"; [theming.md](../spec/theming.md) says the border title carries the Selection count and reads `run on 12 repos`; and nothing in `[[action]]` lets a Repo define or not define an Action. Three artefacts, three claims, and [0015](0015-the-core-owns-the-table.md) makes the glossary contractually load-bearing on the core's public surface. Correcting the glossary drops a recorded requirement the source called "the single biggest usability gain over the CLI", and that is said plainly rather than absorbed; per-Repo Action applicability graduates to the map as fog rather than being smuggled back in as a palette annotation.

## Consequences

- theming.md's `warn` loses "a skipped Action step", `danger` gains "a failed Action step", and layout-and-provenance.md's `step 2 skipped no upstream configured` mock line is corrected, because skipped is not one of the four outcomes and the word the specs wanted for it belongs elsewhere.
- An excluded `[[repo]]` row ("Listed, never operated on") is still selectable with Space and swept in by `a`, so the confirm count subtracts it and `run "reinstall" on 12 repos?` counts the entities actually operated on; the same count sits in the Action palette's border title, so a wrong one would lie twice. After a run such a row shows NotApplicable, the one legitimate producer of a not-applicable Action outcome, and a count of zero does not run and says so rather than fanning out over nothing.
- An ad hoc command typed into the palette is argv, split with shell-words, and never implicitly `shell = true`: [0007](0007-launchers-are-argv-vectors.md)'s opt-in lives in config, and an ad hoc command has no config entry in which the risk could be made visible. `REPON_ACTION` stays unset, exactly as for a Launcher, and the pane labels the run by its command string, which makes the mock's `fetch --all` line correct as drawn.
- Captured output is raw bytes, bounded to head 200 lines plus tail 200 lines with an elision line naming the dropped count, truncated only at a char boundary; head plus tail rather than a tail-only ring, because the tail alone loses the invocation and keeps the noise. The bound is a defence against the pathological case, not a normal-path cost: `git status --short --branch` across all 403 entities produces 15,279 bytes in total, and the bound over a 10 MiB stream costs 0.4ms and keeps 16 KiB. Under ONLCR a `\r` before `\n` is a line ending whose CR is dropped, and a bare `\r` is a progress-frame separator of which only the last frame is kept.
- There is no per-step timeout, because a legitimate step can take minutes and refresh.md already rejected per-cell deadlines on the ground that a rayon task cannot be pre-empted. Esc cancels and the pane carries per-step elapsed time, and the residual risk is stated rather than engineered around: an Action left unattended with a step that waits forever holds its concurrency slot until someone comes back.
- A program that checks for a terminal now behaves like it found one: `less` exits cleanly under pipes and hangs under the PTY. That widened hang class is the price of colour, and Esc plus the elapsed column are the recourse.
- crates/repon/src/action.rs's `Action` enum, the ratatui template's message type threaded through more than twenty sites, is renamed to `Message`, because [GLOSSARY.md](../../GLOSSARY.md) makes Action a domain word. This is implementation the spec records rather than performs, and it is one commit now against a much worse one after the domain type lands beside it.
- Under `glyphs = "ascii"` an in-flight Action, and every refresh, has no progress mark at all, because theming.md claims "one switch, two vetted sets" while the ascii set is listed nowhere in docs/ and the spinner is braille. That is the [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md) disjointness class of defect sitting in the spec today; it is named here and graduates to the map as its own ticket, because enumerating a second vetted glyph set is theming's question.
- Repon produces no exit code reporting Action failure in v1, because nothing can ask for one: no headless run verb exists and `Core` has no Action-invoking method. core-api.md's rule stands, nonzero means the tool could not get an answer and never that the news is bad, and the narrower obligation [0005](0005-rendering-agnostic-core.md) imposes is met: the result type carries the per-entity exit code even though nothing in v1 prints it. ansible's overloaded codes, where HOST_UNREACHABLE and PARSER_ERROR are both 4, are the mistake that separation avoids.
- [0002](0002-repon-owns-the-outer-loop-only.md) limits Repon's mutating operations to the narrowest safe cases, and an Action runs arbitrary commands across N Repos. The reconciliation, previously unwritten: 0002 governs what Repon decides to do unbidden, never what the user asks for behind a confirm gate. Without this sentence a future reader would read 0002 and conclude the feature violates it.
- `lazygit` typed into the Action palette, which [0008](0008-two-palettes-not-one.md) already accepts with open eyes, exits immediately with code 1 under a null stdin plus setsid rather than hanging, which is one more argument for that descriptor policy.
- The executor stats the working directory itself before reporting a spawn failure, because `Command::current_dir` on a deleted directory and `Command::new` on a missing program both return kind NotFound with raw OS error 2, and telling a user their command is missing when their Repo is gone is not exotic: `confirm = true` puts a keystroke between the decision and the spawn, a Vanished row keeps its place and is selectable, and config.md's own example Action begins with `rm -rf node_modules`.
- NotApplicable unsets an environment variable exactly as Unknown does. A Submodule's `state` and `base` are NotApplicable and every measured Submodule is detached ([discovery.md](../spec/discovery.md)), so without this rule `${REPON_DEFAULT_BRANCH:-main}` in a `shell = true` step would quietly substitute `main` into a Submodule whose origin/HEAD says qmk-master, the known-wrong answer [0012](0012-the-default-branch-is-a-remote-tracking-ref.md) records with no local detector.
