# Repon writes the Repo entries it owns, and deletion is confirmed rather than undoable

Repon writes `config.toml` for one bounded set of entries, `[[repo]]`, and deletes a Repo's working tree on an explicit confirmed gesture over the Selection. This supersedes the opening sentence of [0014](0014-config-is-read-only-and-a-set-bounds-the-work.md), "Repon never writes `config.toml`", and redraws the scope ruling that put removal beyond this effort. The rest of 0014 stands: there is still no config watcher, still no first-run materialisation of a default file, and `repon config --example` still prints to stdout for the user to redirect.

The reason is the product's own definition. [0002](0002-repon-owns-the-outer-loop-only.md) says Repon owns acting on many Repos at once, and telling a tool which Repos to stop operating on is that kind of act: it is a fact about a set of entities, discovered while looking at the table, applied to several rows in one gesture. Sending the user to an editor to hand-write a `[[repo]]` block per row is the outer-loop cost the product exists to remove, and a management surface that only prints the commands for the user to run would be that same cost with an extra step. So management is a fan-out over the Selection, sharing the Action confirm gate's shape (a count, with ineligible entities subtracted and named) without its pty machinery, since nothing here runs a child process.

0014's objection was mechanical rather than stylistic, and it is answered by measurement rather than by argument. It said the pinned `toml` 1.1.4 cannot round-trip a hand-edited document without dropping every comment and that keeping them would need `toml_edit`, which is true and remains true. `toml_edit` 0.25.13 adds exactly one package to the lockfile, 17 lines, because it already shares `indexmap`, `serde_spanned`, `toml_datetime`, `toml_parser`, `toml_writer` and `winnow` with the `toml` this crate carries. Measured against a fixture in this repository's own house style, comments and all: appending a `[[repo]]` left every comment in place and landed the new table after the last existing `[[repo]]` and before the following `[[launcher]]`; removing a `[[repo]]` took that table's own leading comment with it, which is the right answer for a comment written about the entry being removed, and left every other comment untouched; and creating the array of tables from a file that had none, then removing the entry again, round-tripped byte for byte identical to the source, with an end-of-file comment staying at the end rather than being captured by the appended table. The cost 0014 refused to pay is one package, and the correctness it doubted is demonstrable.

What may be written is bounded to `[[repo]]`, and the bound is not arbitrary. A `[[repo]]` entry is keyed by a path, so it states a fact about one entity that Repon already knows exactly. Everything else in the file states a class: a `[[set]]`'s `exclude` is a glob, a `[[launcher]]` is a command, an `[[action]]` is a procedure, and inferring any of them from one row the cursor happens to be on is a guess. So ignoring a Repo is written as `[[repo]] exclude = true`, which [config.md](../spec/config.md) already defines as "listed, never operated on", and never as a Set `exclude` glob, which would change what exists for every Set sharing that root. An entity excluded this way is still a row and is still subtracted from the Action confirm gate's count, which is the behaviour wanted: an ignore list protects against acting on something, and hiding it from view is the Filter's job ([0022](0022-the-filter-language-is-total-and-three-valued.md)), which is transient by design.

Each write is a read, a modify and a write of the file on disk, with no lock and no watcher, so the last writer wins against a user editing the file at the same time. That is the same exposure a user already has between two editors and is not worth a lock file to close. Every entry Repon appends carries a comment saying so, because the file's whole value under 0014 is that its comments carry more information than its values, and an entry appearing with no explanation is exactly the loss that argument was protecting against. After a successful write, Repon runs the same path `Action::ReloadConfig` runs rather than mutating its in-memory document, so there is one way config reaches the running app and a write cannot produce a state the file alone would not reproduce.

Deletion removes a Repo's working tree, and its bound comes from what the operation actually breaks elsewhere. A Submodule is refused: its git common dir is `<parent>/.git/modules/<name>` rather than its own, so deleting the directory corrupts the parent, whose `.gitmodules` still names it. A linked Worktree is refused: removing one is `git worktree remove`'s job, it leaves administrative files in the Repo it was linked from, and worktree management stays out of scope. Repos only, which is the narrowest operation that satisfies the request rather than the narrowest operation available. The confirm gate reports rather than refuses: uncommitted changes, unpushed commits and the number of linked Worktrees pointing into each Repo are shown before the gesture is accepted, which is the standing "report ineligible cases rather than fix them" constraint applied inside the decision rather than against it.

There is no undo and no trash, accepted deliberately. A branch that exists on a remote, or a backup, is the user's own safety net, and it is a better one than anything Repon could offer: a trash directory would be a second store Repon then has to garbage-collect, size-bound and explain, and it would give a false assurance for the case that actually loses work, which is uncommitted changes in a Repo with no remote. That case is what the confirm gate names. Whether `d`'s dismissal of a Vanished row wants an undo (#171) is a different question about a different operation and is not settled here.

## Consequences

- 0014's first sentence no longer holds, and 0014 carries a note saying so. Its other refusals stand: no watcher, no first-run materialisation, no editing of anything the user hand-wrote.
- `toml_edit` joins `crates/repon`'s dependencies. It is not a core dependency and `check-core-isolation`'s allowlist is untouched.
- `[[repo]]` is the only table Repon writes. A future feature wanting to write a `[[set]]`, `[[launcher]]` or `[[action]]` reopens this ADR rather than extending the code, because the bound is the argument.
- Comment preservation is now a behaviour with a test rather than a property of not writing at all. A round-trip test over a commented fixture belongs in CI, and losing a comment is a failing build.
- Deletion is available on Repos and refused on Submodules and linked Worktrees, with the refusal reported and counted rather than silent.
- Work is lost permanently when the confirm gate is accepted. That is the recorded trade, not an oversight.
- The map's Out of scope entry ruling out removal is redrawn to worktree removal specifically, which remains out of scope.

## Amended by #260

The scope line above, "A linked Worktree is refused... worktree management stays out of scope", and the Consequences bullet repeating it, are overruled by hands-on use. A Worktree is a row Repon discovered, reports on and lets the user `ignore`; refusing to remove it was the one operation that stopped halfway, and "it leaves administrative files in the Repo it was linked from" was always an argument for calling `git worktree remove`, not for refusing outright.

`delete` is now eligible on a Worktree and removes it the way git does: its own administrative entry under the Repo it is linked from, then its own working directory, falling back to a bare directory removal, reported as that rather than a clean removal, when that Repo cannot be opened. Deleting a Repo now takes its linked Worktrees with it too, so the count this ADR's confirm gate names as "the number of linked Worktrees pointing into each Repo" becomes a count of what will be destroyed rather than a warning about what will be orphaned. A Worktree already in the same Selection as its parent Repo is removed once, by the Repo's own `delete`, and is not named or run a second time. A Submodule stays refused for the reason this ADR already gives, unchanged.
