# Discovery stops at the repo boundary, and Submodules are read rather than walked

Discovery walks each Set root and stops at the first repo boundary it meets: a directory containing a `.git` entry, whether that entry is a file or a directory. Submodules are then reached by reading `.gitmodules` in what the walk already found, never by walking deeper. The cost gap is the whole argument. Measured warm, in Rust, median of three, across `~/dev` and `~/dev-misc`: the boundary-stop walk takes 20.6ms, touches 14,386 entries and finds 403 entities. The deep walk that also finds Submodules takes 89,141ms and touches 6,424,758 entries. Two cheaper deep variants were measured and both lose: skipping `node_modules`, `target`, `vendor`, `Pods` and eight other directory names by name is 10,673ms and still 645,808 entries, and a walk that honours `.gitignore` (the `ignore` crate) is 20,850ms and 857,691 entries. [The refresh spec](../spec/refresh.md) had recorded the deep walk at 11.4 seconds; that figure is wrong by 8x and is corrected as part of this decision. Mechanics live in [the discovery spec](../spec/discovery.md).

There is no depth key and no deep mode. [config.md](../spec/config.md) deliberately left `max_depth` unwritten pending this ticket, and the answer is that it never gets written. A repository sitting inside another repository's working tree is reached by adding its parent directory as a Set `root`, a mechanism that already exists. A mode that costs 20 to 89 seconds cannot ride the refresh, and the refresh spec already states the rule: discovery rides on the refresh only while it costs less than the cheap phase.

The ticket's own premise was half wrong, and the inventory is the reason. The ticket described the 38 entities the boundary-stop walk misses as "18 submodules plus 20 vendored repos". Measured by name, they are: 16 registered Submodules at depth one (eight under `vial-qmk`, six under `qmk_firmware`, and `ghostty` in each of `nex` and `nex-fork`); one Submodule of a Submodule, `qmk_firmware/lib/chibios-contrib/ext/mcux-sdk`; one bare gitlink with no `.gitmodules` entry at all, `fitkit-pocs/poc4-sample-obs-plugin`, index entry mode 160000; 19 independent clones under `manage/.claude/worktrees/`, every one a `.git` directory rather than a linked Worktree, all created on the same day, all sitting on `main`, all clean, and all matched by the owner's own global gitignore rule for `.claude/`; and one transitive CocoaPods checkout, `crew-frontend/ios/Pods/libvmaf/vmaf`, whose `.git` is a file reading `gitdir: ../.git/modules/vmaf`, matched by that project's own `ios/.gitignore`. So the deep walk's entire yield beyond the Submodules is tooling debris that the owner's own ignore rules already disown. The half of the premise that held: all 163 linked Worktrees are found by boundary-stopping, because a Worktree sits beside its parent rather than inside it, and the boundary-stop walk finds exactly 163 `.git` files.

The Submodule pass is a read, not a walk. Statting `.gitmodules` in all 403 discovered entities costs 2.82ms, and parsing the four files that exist costs 1.10ms, so 3.92ms in total, against 20,850ms for the cheapest walk that finds the same things. The pass runs over every discovered entity rather than every Repo, because a linked Worktree has its own working tree and therefore its own `.gitmodules`, which can pin a different commit than its parent's. It does not recurse: one level from each discovered entity, which finds 16 of the 17 and leaves `mcux-sdk` invisible. Unbounded recursion is how a 3.92ms pass becomes a walk again.

`.gitmodules` is the sole authority on what counts as a Submodule. Reading index gitlinks instead was measured at 13,610ms across the population, and would find 17 gitlinks in 5 repos against 16 `.gitmodules` entries in 4. The one extra is `fitkit-pocs/poc4-sample-obs-plugin`, which is what `git add` on a directory that happened to be a repository leaves behind, and git itself does not call it a Submodule: `git submodule status` in that repo returns empty. If git will not call it a Submodule, Repon will not either. Cost and authority point the same way here, which is worth saying plainly.

Symlinks are followed, but only to a Repo. A symlink under a root is a statement of intent to make a Repo available. The mechanism that honours the intent without the blast radius: a directory symlink is followed only when its target is itself a Repo, and then only to record that Repo, never to walk through it. The measured population makes the case. The boundary-stop walk sees 69 directory symlinks; 66 sit below a repo boundary (`node_modules` shared between a Repo and its Worktrees) and are never reached either way. Three sit above any boundary. Two are Obsidian plugin links pointing at Repos already discovered under their real names, `obsidian-sample-plugin` and `obsidian-fitkit`. The third points at the user's home directory, from inside a mise state fixture; following it would walk `$HOME`, which config.md already records as the 100-second, 1.45-million-entry case. Under the rule as written, the home directory is not a Repo, so it is not followed. Because the walk never descends through a symlink, cycles are impossible rather than guarded against, a property worth having rather than a loop detector worth writing. The cost is stated honestly: a symlink pointing at a directory of Repos is not followed either, and that case is served by adding a root.

Identity is the canonical path. config.md records that across all 403 entities zero names collide, and the state file keys the Selection by name, so two paths to one Repo would break restore-by-name with two live instances. The canonical path is the entity; a symlink that resolves to an already-discovered Repo is silently dropped, and that is not a Vanished row and not a warning, because nothing is wrong.

Discovery is never held. Two measurements, not a principle. At 20.6ms there is nothing worth saving, and nothing cheap can validate a cache: a direct probe of APFS shows a directory's mtime does not propagate upward (creating `a/b/c/newrepo` bumps `a/b/c` and leaves `a` and `a/b` untouched), while an ordinary file write inside a working tree bumps its own directory constantly. Validating an mtime-keyed cache therefore means statting every directory, which is the walk. This puts discovery on the uncached side of [0006](0006-no-git-state-cache-session-state-by-name.md)'s line for a reason that has nothing to do with git state going stale.

`show_submodules` narrows the view rather than bounding the work. config.md draws that line hard: a Set bounds the work and an excluded entity is never discovered, where a Filter only narrows what is visible. Because the pass costs 3.92ms the flag does not need to gate it, so the pass always runs and Submodules are always known; the flag decides whether they are rows, whether they are probed, and whether the two-second metadata sweep touches them. That makes toggling instant, keeps the poll's cost proportional to the screen, lets `repon sets` report how many Submodules a Set covers while they are hidden, and means a fault found by the pass is reported whether or not Submodules are shown.

What a Submodule row actually holds is weak, and that is stated rather than buried. All 16 initialised Submodules in the measured population are at a detached HEAD; none has an attached branch. So `state` is Not applicable, because none of Merged, Gone, Local only or Active means anything without a branch. `base` is Not applicable too, and that one is the interesting call: [0012](0012-the-default-branch-is-a-remote-tracking-ref.md) already records this exact population as its ceiling, Submodules whose cached default is `master` where the truth is `qmk-master`, with no local detector, so a blank beats a confident wrong number. `branch` carries the short object id. That leaves `name`, `branch`, `sync` and `dirty` carrying content, and 15 of the 16 are firmware vendor pins nobody edits. Keeping them discoverable was still the call, because the cost is now 3.92ms and they are hidden by default.

An unparseable `.gitmodules` gives `RowSummary` its first input that is not a cell. The file is tracked, hand-edited and merge-conflict-prone. When it will not parse or will not read, the parent Repo's own cells are all fine, so nothing is blank, and yet something about that Repo could not be read. The gutter shows `!`, Failed rather than Unknown, because we asked and got something we could not use, which is a different fact from getting nothing back. This amends [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md): the fold is no longer over the cells alone but over the cells and the entity's own derivations, and the honest consequence is that a row can show `!` with no blank cell, so the detail pane is the only place that names which derivation failed. 0010 already accepted a version of this trade-off in writing for the four-cells-into-one case; this widens it by one.

Two things never become rows, both for free. A bare repository is never a row: it has no working tree, so five of the seven columns would be permanently Not applicable, and boundary-stopping cannot find one anyway, because there is no `.git` entry to stop at. Six exist under the roots, all fixture remotes in a test harness. And a vendored or embedded checkout is never a row, which needs no rule of its own because boundary-stopping already produces it.

One implementation constraint is worth recording. gix's `Repository::modules()` falls back from the worktree `.gitmodules` file to loading the whole index, and then to peeling HEAD to a tree. Calling `submodules()` on a Repo with no `.gitmodules` is therefore not cheap, and the 3.92ms figure holds only because Repon stats the file itself and calls gix for the four entities that have one. The population holds 14.6 MB of index files across 238 entities, so getting this backwards reintroduces the cost the design just avoided. gix 0.87.1 needs no new cargo feature for this: `Submodule` is gated on `attributes`, which Repon's already-enabled `status` feature turns on transitively through `blob-diff`, verified by building against the pinned version and feature list.

## Consequences

- The `∙` (U+2219) Submodule row marker in [layout-and-provenance.md](../spec/layout-and-provenance.md) is dropped, and a Submodule row carries `└`, the mark a Worktree row already has. U+2219 sits one codepoint from `·` (U+00B7), the clean value glyph, on the same row, which is structurally the defect [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md) exists to prevent. The cost is that a Submodule row and a Worktree row now look alike, and the name column, the two Not applicable cells and the detail pane are what distinguish them.
- config.md never gains `max_depth`, a directory denylist or a discovery budget key. Every deep variant measured lost, so there is nothing for a tunable to tune.
- A `[[repo]]` entry cannot exclude a parent and its Submodules together, because a Submodule's git common dir is `<parent>/.git/modules/<name>` rather than the parent's. A Set's `exclude` glob is the tool for a subtree.
- A Set's globs are tested against a Submodule's own absolute path, so a Submodule that arrived by the pass rather than the walk is still bounded by the Set.
- An uninitialised Submodule is a row with every cell blank and `?` in the gutter. The alternative makes rows appear on `git submodule update --init` with nothing having changed in what the Repo declares.
- A future reader will want the deep walk back as an opt-in. Point them at the inventory: its entire yield beyond the Submodules was debris the owner's own ignore rules disown, and the cheapest walk that finds it costs 20,850ms.
- refresh.md's 11.4 second figure for the deep walk is corrected to 89.1 seconds.
- The map's fog item about detached HEAD as a Worktree state becomes load-bearing rather than incidental, since every Submodule in the measured population is detached.
- Discovery is now two halves that return one entity list, so a Submodule that appears or disappears goes Vanished by exactly the rule a Repo does.
- A row can show `!` with no blank cell, and the detail pane is the only surface that names which derivation failed. This widens the fold [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md) accepted for four-cells-into-one by one more input.
- The Submodule pass stats `.gitmodules` itself and calls gix only where the file exists. Calling `submodules()` unconditionally reintroduces the index-loading cost the pass exists to avoid.

## Amended by 0019

The Submodule row keeps its answer and loses its reason. This ADR blanks `state` "because none of Merged, Gone, Local only or Active means anything without a branch", and that is wrong: Merged needs a commit and a default branch, not a branch name, and 55 of the 125 measured detached entities prove it. The reason `state` and `base` are Not applicable on a Submodule row is the one this ADR already gives for `base` alone, that [0012](0012-the-default-branch-is-a-remote-tracking-ref.md) records that population's default branch as known-wrong with no local detector, so a proof against it would be a confident lie. The rule is "no trustworthy default branch, so no proof", and detachment was a coincidence in that population rather than the cause. The `branch` cell's short object id is unchanged and now covers every detached row. See [0019](0019-a-detached-head-is-a-shape-of-head-not-a-worktree-state.md).

## Amended by #173

The reason 0019 supplied is right and the variant carrying it is wrong. "No trustworthy default branch, so no proof" is not a question that fails to apply; it is a question that applies and has no answer Repon can stand behind, which is Unknown with a reason rather than Not applicable. Not applicable is reserved for a question with no meaning on the row, the way Worktree state has none on a Repo row, and [0001](0001-per-cell-provenance.md) exists to stop those two collapsing. So `state` and `base` on a Submodule row are Unknown, carrying the default-branch reason, and they move together because 0019 already binds them under one rule.

Two things follow. Merged becomes computable, with no new machinery: [0012](0012-the-default-branch-is-a-remote-tracking-ref.md) records that since git 2.48 a plain fetch with default refspecs creates a missing `origin/HEAD` and `remote.origin.followRemoteHEAD=always` corrects a stale one, so the periodic fetch repairs the input and the proof then runs through the same path a detached Worktree already uses. Gone, Local only and Active stay Not applicable, each needing an upstream a detached HEAD structurally cannot have, which is 0019's split applied unchanged.

And with the fetch off, which is the default, Submodule rows carry `?` in the gutter where they now carry a space. That is 16 of 403 entities, hidden by default, and genuinely unknown rather than settled, so it passes the test 0019 applied when it refused to mark 125 detached rows `?` for a settled fact. What a Submodule row is worth overall is unchanged: weak, 15 of the 16 being firmware vendor pins nobody edits, kept because the pass costs 3.92ms. See [#173](https://github.com/paulchiu/repon/issues/173).
