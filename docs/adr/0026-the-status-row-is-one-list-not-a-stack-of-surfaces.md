# The status row is one list, not a stack of surfaces

> **Retired.** This record is kept for its history. Its product intent now lives in
> [product.md](../product.md) and its implementation detail in
> [layout-and-provenance.md](../spec/layout-and-provenance.md). Nothing below is maintained.

The status row holds one list of items, degraded by one drop table, rather than a stack of surfaces ranked against each other. A standing warning is an item in that list, not a rival to the header. Its **indicator**, a `!` and a count, is reserved out of the budget before anything is laid out and can never be dropped; its message text competes for what is left. `w` **acknowledges**: once the user has opened the expanded list, the row falls back to the indicator, and a newly-arrived warning expands it again. A Notice remains the one thing that takes the whole row, as [0023](0023-an-unbuilt-binding-is-not-advertised-and-an-unavailable-one-answers-on-press.md) already settled. This answers the question 0023 left open and ticketed.

The two obvious answers are both bad, and they are bad because the framing was wrong. Ranking a warning above the header hides the entity count for a whole session, since a config warning is continuously true and, as this decision found, nothing dismissed one. Ranking it below drops a warning silently at 88 columns, which is the quiet lie [theming.md](../spec/theming.md) invokes [0001](0001-per-cell-provenance.md) to forbid. Both follow from treating two claimants as whole surfaces that win or lose the row outright. Neither survives the row being one budget with items in it.

A standing warning is the same kind of thing as the items already in that list. `filter: 12 matches` and `worktrees: 161 (preference off)` are continuously-true facts about the session that the user reads to know what they are looking at, and a half-applied theme or an abandoned discovery is exactly that with a worse implication. [actions.md](../spec/actions.md) already built the mechanics for such a list: items separated by ` · `, the ASCII ` ...` ellipsis reserved inside the budget rather than appended after it, every item width-checked including the first, and the last surviving item dropping the ellipsis rather than itself. Two degradation rules for one row was the defect; the warning joins the one that exists.

The arithmetic is what forces a floor rather than a rank. `actions.md`'s ladder line for 88 columns measures exactly 88, so at the narrow prototype screen with a run in flight the header fills the row with nothing spare at all. The longest warning `Display` in the tree, `theme \`solarized-dark\` named in config.toml does not exist`, is 58 columns, and `slot_line` appends ` (+2 more, w to expand)` for another 23. At 81 against 88 no arrangement carries both as text. Whatever survives a narrow row has to be a mark, so the decision is which mark and what reserves it, not which sentence wins.

Reserving the indicator is the same move the row already makes twice. The ellipsis is reserved inside the budget for the identical reason, that a thing appended after a full budget is a thing that never appears; and `slot_line` already reduces every warning but the most severe to `(+2 more, w to expand)`, so compressing warnings to a count is established, and this compresses the last one. `!` is available on this row: [0020](0020-the-ascii-glyph-set-is-vetted-over-the-row-interior.md) scopes glyph disjointness to the row interior and stops at the frame and the footer, so `!` meaning Failed in the gutter cannot collide with `!` meaning warnings outstanding above the frame.

The Notice is not readmitted by any of this, and the difference is what a floor form can mean. 0023 refused the Notice as an item on this table's own arithmetic, and that refusal stands: a Notice is transient, user-caused, and has to be read at the instant it fires, so an indicator saying a reply happened is not a reply, and there is no `w` to recover it from because it is gone in seconds and never logged. A warning is standing, so a mark plus a recall gesture loses nothing but immediacy, and the condition is still there to be read when the user asks.

Acknowledgement is what makes the priority safe, and it closes a promise that had no mechanism. [theming.md](../spec/theming.md) said the slot was persistent "until dismissed" and that each condition "is dismissible", and nothing in the tree dismissed one: `d` dismisses a Vanished row and `w` expanded the list. The objection to a warning holding the row is entirely that there is no way out of the state, so the exit is the fix, and `w` is already the key the user presses to find out what is wrong. Per-warning dismissal was refused: a warning the user has waved away while it is still true is a quiet lie of its own, and acknowledgement records that the user looked rather than that the condition ended.

The rule moves documents, because the document that carried it disagreed with itself. [theming.md](../spec/theming.md) fixed the order in one sentence and disclaimed it four lines later, which is the failure [0024](0024-repon-releases-what-it-enables-and-holds-mouse-capture-off.md) diagnosed when a count kept in two places let two documents drift. The row's composition now lives in [layout-and-provenance.md](../spec/layout-and-provenance.md)'s frame, the document about where things are drawn, which already owned the frame and already redirected here. theming.md keeps what a warning is, the report-twice rule, the three sources, the severity ranking and the `warn` role, and actions.md keeps run progress as an item. Each document owns what it is named for. [#128](https://github.com/paulchiu/repon/issues/128) put the active Set on this same row through that one door ([0027](0027-the-active-set-names-the-status-row-and-the-picker-is-the-strip.md)), and [#261](https://github.com/paulchiu/repon/issues/261), which gives the current Refresh's own state an item on the row, took the same door rather than inventing a second one.

Two things follow for the implementation. `warnings::draw_slot` writes at `area.x` with no width check and owns the row outright, so it stops being a renderer and becomes one item source feeding the row's layout, beside the header's own. And acknowledgement is session state on the app rather than on a warning: the set of conditions the user has seen, cleared by a condition arriving that is not in it, and never persisted, since [0006](0006-no-git-state-cache-session-state-by-name.md) keeps computed state out of the state file and a warning is computed every run.

## Amended by #259

The indicator's glyph is `[N]`, not `!`. The reasoning above about *where* the indicator is reserved and *that* it can never be dropped stands; only the character was wrong.

[0020](0020-the-ascii-glyph-set-is-vetted-over-the-row-interior.md)'s scoping argument, that `!` meaning Failed in the gutter cannot collide with `!` meaning warnings outstanding above the frame because the two rows are in disjoint territory, is correct as far as it goes, but it only checks the gutter. It misses the other `!` already on this screen: `!` is the key that opens the Launcher palette, and the prefix of the Launcher palette's own query line (`"! filter launchers"`). That binding and that query line are not in the row interior 0020 scopes either, so the indicator sat outside 0020's fence twice over, not once, and the second collision is the one that reads badly in practice: a `!` above the frame looks like a Set badge or a launcher hint, not a warning count, because that is what `!` already means everywhere else on screen. Reported from manual use.

`[N]` is not used as a status glyph anywhere else on the row, which is the property `!` turned out not to have. Brackets cost one more column per digit (`[1]` is 3 columns against `!1`'s 2), which moves the reserved width, the shift `layout-and-provenance.md`'s acknowledged ladder applies to `actions.md`'s own published widths, and the floor at which nothing else survives, from 2 columns to 3; the layout rule that reserves and never drops the indicator is unchanged, only the arithmetic it produces. See [#259](https://github.com/paulchiu/repon/issues/259).
