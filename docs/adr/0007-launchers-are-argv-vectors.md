# Launchers are argv vectors, and context travels in the environment

A Launcher is stored as an argv vector, never a shell string, and Repo context (path, branch, name) reaches it through environment variables, never interpolated into a command. This deviates from the obvious template-string approach for a security reason: a branch name or path can contain shell metacharacters, and with argv plus environment it cannot break out of its word. A Launcher may opt into a real shell (pipes, `&&`, globs) via an explicit per-entry flag, making the risk visible in config rather than the default. Launchers suspend-and-exec in the same terminal, which must be left exactly as found after quit, panic or suspend.

## Amended by #351

"Shell behind an explicit flag" still governs a Launcher and a config `[[action]]` step: both keep `shell = false` as their default, and both have a config entry in which the opt-in is visible. It is narrowed rather than repealed for one third case that has no such entry: a command typed into the Action palette's ad hoc field, which now defaults to `shell = true` instead.

The reasoning above was never about shells being dangerous in the abstract; it was about a flag with nowhere to be seen, since a file that opts in silently is the actual hazard 0007 exists to close. That premise held for a typed command when this ADR was written, because [`StepResult::label`](https://github.com/paulchiu/repon/blob/main/docs/spec/actions.md) recorded only the string, never the mode it ran under, so an implicit shell there would have been invisible twice over: no config entry to read it in, and no receipt to see it on after the fact. It does not hold today. `StepResult` now carries `shell` itself, the detail pane renders it beside the label, and the ad hoc field's own chrome and the confirm gate both name the live mode before a keystroke commits it. The receipt is the audit trail a typed command lacked; once it exists, withholding the shell from the one field shaped like a prompt is not caution, it is a silent wrong answer, `echo $(pwd)` printing four literal characters back to a user who typed a command a real shell would have run correctly.

Narrowed, not repealed, because the property that earned Launchers and config steps their own default is a property they still have and the ad hoc field still lacks: a file that persists, gets re-read and gets re-run belongs behind an explicit, visible flag, since a mistake written there is a mistake that keeps firing. A string typed and fired once in the same gesture has no persistence to protect against; its own risk is per-run, and a per-run toggle (`Alt+S`) reset to the default every time the field opens is the matching per-run answer, not a config key. See [#351](https://github.com/paulchiu/repon/issues/351) and [actions.md](../spec/actions.md)'s "The Selection and the gate" for the full shape, including the regression surface this accepts (an unset variable in a step like `git reset --hard $BASE` now expands instead of erroring) and the mitigation (the toggle, plus the mode visible in three places rather than none).
