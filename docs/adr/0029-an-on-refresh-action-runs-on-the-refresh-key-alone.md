# An `on_refresh` Action runs on the Refresh key alone, with no gate and no queue

`on_refresh = "sync"` names one declared `[[action]]`, and Repon runs it after a Refresh the user asked for: `r` and `R`, and nothing else. This is a trigger for machinery that already exists, not a second way to run a command. The declared Action fans out one PTY-backed child per entity, in that entity's own working directory, with the environment contract, gated on exit code and bounded by `concurrency` ([0018](0018-an-action-is-a-fanout-of-pty-backed-steps.md), [actions.md](../spec/actions.md)); none of that is touched here. What was missing was any way for an Action to start without a keystroke aimed at it, which is what myrepos's `update = ~/bin/some-sync-script.sh` has and Repon did not.

The restriction to `r` and `R` is the decision, and it has two independent reasons, either of which would be enough on its own.

The first is [0002](0002-repon-owns-the-outer-loop-only.md). It limits Repon's mutating operations to the narrowest safe cases, and an Action runs arbitrary user commands across N Repos, which is the widest possible mutation. [actions.md](../spec/actions.md) already reconciled the two: "0002 governs what Repon decides to do unbidden; an Action is what the user asked for, behind the confirm gate." A script fired by `r` is on the asked-for side of that line, because a person pressed a key and the file they wrote says what that key now does. A script fired by a two second background tick is not: nobody was there, and Repon would be deciding to run it. The reconciliation survives the hook only because the trigger stays a keystroke. Widen it to the periodic fetch's own completion Generation and 0002 is simply violated, with `actions.md`'s sentence no longer covering the case.

The second is mechanical and admits no judgement at all. [actions.md](../spec/actions.md) fixes that an Action finishing starts one normal Generation, the same path a finished fetch takes. A hook triggered by a Generation would therefore trigger itself: Generation, hook, hook finishes, Generation, hook, for as long as the process lives, each cycle spawning one child per Repo. There is no debounce that makes that safe, because the loop is not a race but the plain composition of two settled rules. So the trigger cannot be "a Generation started"; it has to be "the user asked for one".

Focus gained and resume are refused for the first reason rather than the second. Neither loops, and both are a Generation that follows something a person did. But `refresh.md` makes focus gained best effort and terminal dependent, so whether the hook fires at all would depend on a `focus-events` option in tmux, and a script that runs when you switch windows is a script that runs when you alt-tab. Resume is the return from a Launcher, which is precisely the moment the user was doing the inner-loop work by hand; running a sync script over every Repo on the way back out of lazygit is not what "I am back" means. Both are Repon deciding, on a signal the user did not aim at anything.

The hook's scope is the scope of the Refresh that fired it: every known Entity for `r`, the Selection for `R`. This does not fold into "an Action acts on the Selection", and the difference is deliberate. `r` is the gesture that means "everything", and a hook that ran on the cursor row alone because nothing was checked would be a per-Repo command wearing a whole-population key. `R` already means "these rows", so its hook means the same thing, and the two keys keep the meanings they had.

The gate is not consulted, and this overrides `confirm`'s documented default rather than working around it. `confirm = true` exists so a destructive fan-out gets a keystroke between the decision and the spawn, and that keystroke is `r` here: the user wrote the key into a file, and a dialog on every refresh is not a safety feature but an unusable one. An entry with `confirm = true` chosen from the palette still asks, so nothing is weakened for the palette; what the file says is only that this one trigger is its own confirmation.

The Refresh the key started is still dispatched, and the hook fires after it rather than in place of it. Composed with two rules already in force, starting an Action cancels an in-flight Generation and finishing one starts a fresh Generation, that reads on screen as: refresh, script, refresh. The first Generation is largely cancelled and its cost is real but small, and paying it is what keeps [refresh.md](../spec/refresh.md)'s Triggers table true: `r` means "a new generation over everything" whether or not a config key is set, and the hook is a row added to that table rather than a condition rewriting an existing row. A hook that suppressed the Generation would make one key mean two different things depending on a value elsewhere in the file, which is worse than the milliseconds it saves.

The hook yields rather than queueing while another Action is in flight. [actions.md](../spec/actions.md) already fixes that one Action runs at a time, and `;`, `m`, `s`, `1` to `9` and `Ctrl+R` all go inert while a fan-out runs; `r` is not on that list and stays live, because refreshing during a run is legitimate. So the refresh happens and the hook does not, with nothing remembered: a queue needs an ordering and a cancellation story, and the thing being deferred is a script whose whole point is that it runs periodically. The next `r` runs it.

A nonzero step stands as a Warning, and that is a fifth standing condition rather than a reuse of an existing surface. Every other Action in Repon is watched: the user chose it from the palette moments ago, the run progress is in the status row, and the `!` gutter plus `n` and `N` are the compare-failures loop [0018](0018-an-action-is-a-fanout-of-pty-backed-steps.md) built. A hook fired by a refresh has none of that attention on it, so a failing step would be a `!` on a row nobody is looking at, which is the "unattended script whose failure nobody sees" the feature would then be. It qualifies as a Warning on [theming.md](../spec/theming.md)'s own terms: it is continuously true until a later run replaces those receipts, and it puts something already on screen in doubt, since the rows show a world the script was supposed to have changed. It is derived fresh from the live receipts every frame rather than latched, the shape the Vanished count already takes, so nothing has to be reset by hand and the condition clears itself.

`on_refresh` naming an Action nothing declares is a load warning on the existing path, not an exit and not silence. Every other value in the file is still usable, so refusing to start would be out of proportion; and a hook that quietly never fires is the exact defect [0023](0023-an-unbuilt-binding-is-not-advertised-and-an-unavailable-one-answers-on-press.md) rules out for a keybinding, a thing configured, accepted and inert with nothing said.

[0028](0028-repon-writes-the-repo-entries-it-owns.md)'s bound stands untouched. `[[repo]]` is still the only table Repon writes, and `on_refresh` is hand-written like everything else in the file.

## Consequences

- `on_refresh` is a top-level bare scalar, following [config.md](../spec/config.md)'s own nesting rule: it is about the whole program rather than one subsystem, and it names one thing rather than configuring one.
- [refresh.md](../spec/refresh.md)'s Triggers table gains a row, and the existing eight are unchanged. The two Refresh-key rows are the only ones the hook reads.
- [theming.md](../spec/theming.md)'s warning population goes from four standing conditions to five, and the new one ranks between a config key that fell back and an abandoned discovery: something the user asked Repon to run did not finish, which is worse than a silent fallback and better than a table that may be missing rows.
- `confirm`'s documented default is unchanged and its scope is narrowed in writing: it governs the palette, never this trigger.
- The hook has exactly two production call sites and a source scan holds them there, because the restriction is an absence claim and an absence claim nothing checks is a comment.
- An Action that is slow, or that prompts, is now reachable from a key pressed reflexively many times a session. That is the user's own declaration and Repon does not second-guess it, but the honest cost is stated: `r` was a free keystroke before and is not one after a hook is declared. Esc cancels the fan-out, exactly as for any other Action.
- No headless equivalent is added. `repon status` settles a document and prints it; it runs no Action, and [actions.md](../spec/actions.md)'s open question about a headless run verb is where that would be settled.

## Amended by #250

The first Consequences bullet's reasoning is wrong, though the decision it defends, that the top-level key stays a bare scalar, is right. That bullet reasons `on_refresh` is top-level *because* it is about the whole program, and the concrete case this feature exists to serve, five myrepos config files each with its own `update`, is the counter-example: the script belongs to the scope the Refresh bounds, and a Set is that scope. [config.md](../spec/config.md)'s own nesting rule already gives the honest reason instead: a table when a key is about one named thing, and a Set is one named thing, so `[[set]].on_refresh` is a field on it, following the same rule rather than an exception to it. The top-level key is not demoted by this; it stays what a Set declaring none falls through to, and the everything-everywhere case (no Sets declared, or every Set content with the same script) still writes one line.

Nothing else this ADR decided moves. The trigger is still the Refresh key alone, the hook still fans out over what its Refresh covers, still skips the confirm gate, still yields rather than queues, a nonzero step still stands as a Warning, and the hook still has exactly two production call sites. What changes is which `on_refresh` value those two call sites read: the active Set's own, then the top-level key, then no hook, resolved at the moment the hook fires rather than cached at load or at a Set switch. Caching either the name or the resolved Action would keep firing the Set the process launched with after the user pressed `s` or `1` to `9` to leave it, silently, which is the exact "configured, accepted and inert with nothing said" shape [0023](0023-an-unbuilt-binding-is-not-advertised-and-an-unavailable-one-answers-on-press.md) already rules out for a keybinding; a hook is not exempt from it for having a config key instead of a binding.

A name a Set's own `on_refresh` gives that no `[[action]]` declares is a load warning on the same path the top-level key's own bad name already takes, naming the Set: two Sets sharing one bad name must produce two distinguishable warnings, since a warning naming only the value could belong to either.

There remains no way for a Set to opt itself out of a top-level hook it does not want, the open question this issue recorded rather than solved. See [#250](https://github.com/paulchiu/repon/issues/250).

## Amended by #261

"The refresh key" is any chord dispatching `Action::RefreshAll` or `Action::RefreshSelection`, not the literal characters `r` and `R` this decision named. The restriction itself is unchanged: the two reasons above are about *a keystroke the user aimed*, never about which key it happened to be, so naming `r` and `R` was this decision describing its own compiled default rather than the property it actually relies on. `keys::dispatch` already resolved a chord to an `Action` before either call site here ever ran, so the hook was never wired to the two characters in the first place; the wording was narrower than the mechanism it described.

Two things follow now that the wording matches the mechanism. `F5` joins `r` as a second compiled chord for `Action::RefreshAll` ([keybindings.md](../spec/keybindings.md)), the refresh key other software trains a user to reach for, and it carries the hook the same way `r` always did, with no change to either call site. And a user's own `[keys]` rebind of `refresh_all` or `refresh_selection` to any chord keeps the hook: [config.md](../spec/config.md)'s example used to illustrate exactly this rebind onto `F5` and lose it to macOS Dictation, which is a keybinding availability problem the example now avoids by picking a chord that works, not a reason the hook itself would have stopped firing. It would not have: the hook fires on the `Action` the merged table dispatches, whatever chord config puts there.

Nothing else moves. The trigger is still a keystroke rather than a Generation, the hook still fans out over what its Refresh covers, still skips the confirm gate, still yields rather than queues, and the two production call sites are unchanged. [refresh.md](../spec/refresh.md)'s Triggers table is reworded to match.
