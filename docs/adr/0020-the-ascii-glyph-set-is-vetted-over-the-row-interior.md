# The ascii glyph set is vetted over the row interior

Repon has two glyph sets, `full` and `ascii`, chosen by one config key. Two, and only ever two: no `auto`, no third value, no runtime probe and no table of terminal names. Each further set is a further disjointness obligation, and an environment-derived set is an unbounded family of them, which would leave the vetting neither finite nor reviewable. The one environment signal read is `TERM=linux`, which makes `ascii` the default there, because the Linux console's kernel substitution table is fixed and knowable and rewrites two `full` gutter marks onto each other; an explicit key pins either set.

The rule the sets are vetted against is scoped to the row interior: the gutter marks, the value marks and the child-row marker. Inside that scope no gutter mark may equal a value mark, no two meanings may share a glyph, and a character present in both tables must carry the same meaning in each. Violating it puts a provenance mark that also reads as a real value on screen, the defect per-cell provenance exists to close, arriving through the glyph table rather than through the type. The frame and the footer sit outside the scope, so a frame may collapse four corner shapes onto one character: a border is read as a region, where a value is decoded character by character. Glyph sets are never user-supplied, so there is nothing at load to check and the check runs at compile time.

**Enforcement:** the `const fn disjoint` assertions in `crates/repon/src/glyphs.rs` fail the build with `error[E0080]` on an overlapping pair, once per table, reading the fields the one `glyph_set!` invocation generates rather than a list retyped beside them. In the same file, `assert_row_interior_is_injective` (reached by `the_full_table_never_lets_two_meanings_share_a_glyph` and its ascii twin), `a_character_present_in_both_tables_carries_the_same_meaning_in_each` and `both_tables_define_glyphs_for_the_same_set_of_meanings` are the rest. `glyphs_default_reads_exactly_one_term_value_and_no_other_variable` in `crates/repon/src/config/document.rs` fails on a second `TERM` read anywhere in the workspace or a second value the default treats as significant. The floor is mechanical: no assertion can see confusability, human review is recorded alongside it, never in place of it.
