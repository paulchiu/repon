# The ascii glyph set is vetted over the row interior

Repon has two glyph sets, `full` and `ascii`, selected by `glyphs` in `config.toml`, and [theming.md](../spec/theming.md) promises "one switch, two vetted sets" while enumerating only one of them. Writing the second set down forced three questions that were never settled: what the switch is for, how far [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md)'s disjointness rule reaches, and where the rule is enforced. The answers: the switch exists for font coverage rather than width, the rule is scoped to the row interior, meaning the gutter, the value cells and the child-row marker, with the panel frame and the footer outside it, and enforcement moves to compile time, which is earlier than the ticket asked for.

The switch is for font coverage, and both places the docs state its purpose already say draw, not measure. Measured, that is the right reason. A cmap parse over the five macOS system monospace faces (SF Mono, Menlo, Monaco, Andale Mono, Courier New) gives:

| glyph | faces carrying it |
| --- | --- |
| `·` `↑` `↓` `└` `─` `│` | 5 of 5, except as noted below |
| `≡` | 4 of 5, SF Mono lacks it |
| `●` | 4 of 5, Monaco lacks it |
| `╭╮╰╯` | 2 of 5, only Menlo and SF Mono |
| `∅` | 1 of 5, only Menlo |
| braille | 0 of 5 |

The braille spinner is in zero of the five faces. Across all 1,123 installed faces on the machine it sits in six: five Apple Braille tactile-display faces and Apple Symbols, which is proportional, so not one usable monospace face on the survey machine can draw the Loading mark. Two sharper results fell out of the same sweep. Monaco carries `↓` and `→` but not `↑`, so a Monaco user gets a correct behind count and a tofu box for ahead in the same nine-column `sync` cell. And Menlo Bold and Menlo Bold Italic lack the entire box-drawing set (`└ ─ │ ╭╮╰╯`) while Menlo Regular and Menlo Italic carry it, so a profile that bolds the focused pane can lose the frame on focus. Coverage is per-glyph and per-weight, which is why the set is vetted as a whole rather than probed piecemeal. The terminal matters as much as the font: kitty, Ghostty and WezTerm draw braille and box drawing themselves from internal sprites and never consult the font, while iTerm2, Terminal.app, Alacritty and the Linux console do not, so the same font gives a working screen in one emulator and tofu in the next.

Ambiguous width is real but secondary, and it supplies no reason at all to replace the two hardest glyphs. Measured with unicode-width 0.2.2: `width()` returns 1 for every glyph in the full set, while `width_cjk()` returns 2 for `≡ · ↑ ↓ ● └` and all six border characters, and 1 for `∅`, the braille frames, and every ASCII character. So `∅` and the braille spinner, the glyphs coverage kills hardest, measure one column under both functions, and a width-motivated switch would leave them alone. The failure mode when widths do disagree is quiet. ratatui computes width with `UnicodeWidthStr::width()` and never `width_cjk()` (`ratatui-core-0.1.2/src/buffer/cell_width.rs:42`), so it always budgets an ambiguous glyph at one column, and the crossterm backend emits `MoveTo(x, y)` only when a cell is not immediately right of the previous one (`ratatui-crossterm-0.1.2/src/lib.rs:242-247`), so a full repaint prints each row as one contiguous run. A glyph the terminal draws two columns wide shifts every remaining cell of that run one column right, and because the buffer believes it drew what it drew, the corrupted cells compare equal on the next diff and are never repainted. It also almost never fires: every emulator in the survey defaults East_Asian_Width=Ambiguous to one column, matching ratatui, the three that expose a switch ship it off, and the trigger is a user who has deliberately turned a CJK setting on. Width is a defect class the switch happens to also close, not the reason it exists.

The vetted set, in full:

| meaning | `full` | `ascii` |
| --- | --- | --- |
| Fresh (gutter) | space | space |
| Stale (gutter) | `~` | `~` |
| Unknown (gutter) | `?` | `?` |
| Failed (gutter) | `!` | `!` |
| Loading (gutter, and a cell) | `⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏` | `\` `|` `/` |
| in sync | `≡` | `=` |
| clean, a known zero | `·` | `.` |
| no upstream, or no branch at all | `-` | `-` |
| no remote at all | `∅` | `x` |
| ahead by n | `↑n` | `>n` |
| behind by n | `↓n` | `<n` |
| n changed files | `●n` | `*n` |
| child row | `└` | `` ` `` |
| panel border | `╭╮╰╯─│` | `+ + + + - |` |

The set costs no columns. A read-only sweep of 540 entities under two roots (358 Repos, 183 linked Worktrees, 246 detached) gives the live distribution: 197 rows would show `≡`, 252 would show `-`, 11 would show `∅`, 520 of 540 would show `·`, 20 rows carry a dirty count with a maximum of 2, two rows are ahead with a maximum of 21, and fifteen rows are behind with a maximum of 1449. The widest `sync` cell measured is five characters, `↓1449`, in a nine-column budget. Every full-set glyph is already one column to ratatui and every ascii counterpart is one column too, so the layout maths in [layout-and-provenance.md](../spec/layout-and-provenance.md) is untouched by the switch.

The spinner is the whole problem, and the classic answer is provably dead. [0013](0013-no-filesystem-watching-a-refresh-is-a-cancellable-generation.md) amended 0010 so the spinner moves into cells once a row holds some values, and that amendment closed with the words "the disjointness rule survives untouched, since a braille spinner is not mistakable for any real value". That sentence is only true because the spinner is braille. Take braille away and the spinner must be drawn from the same 95 printable ASCII characters the value set already occupies, in a cell. The canonical ASCII spinner is `|/-\`, whose `-` frame then lands in the `sync` cell where `-` already means no upstream configured: 0010's founding defect verbatim, one config key away. Of the 90 entries in the cli-spinners table that most ecosystems vendor, only five are single-column ASCII, and four die on the value set: `line` on `-`, `star2` on `x` and `*`, `toggle13` on all three of `=`, `*` and `-`, and `balloon` on `.` and `*`. What survives is `\` `|` `/`, the canonical four minus its fatal frame, which reads as a wobble rather than a rotation, the cost of keeping the rule.

The full set's spinner had never been written down either. Not one of the sixteen places `docs/` mentions the spinner gives a frame list, a frame count or a cadence, so [refresh.md](../spec/refresh.md)'s claim that a braille spinner is not mistakable for any value was asserted about an object nothing defines. Both frames the mockups draw, `⠋` U+280B and `⠹` U+2839, are members of the canonical ten-frame `dots` set, and `dots` contains no U+2800, the blank braille cell that would render as Fresh's space. So the `full` column of the Loading row records what was already drawn rather than deciding it anew.

A static Loading mark is not available. [refresh.md](../spec/refresh.md) records the predecessor's defect as a 4.02 second refresh sampled 55 times with not one spinner frame on any row, and an ascii set with no moving mark reproduces exactly that. It is worse than a regression: under `NO_COLOR` the screen loses the `accent` role too, so Loading and Fresh become a blank gutter over a blank cell, which is [theming.md](../spec/theming.md)'s "colour is never the only carrier" floor failing on the state it was written to protect. Movement is the ascii set's only remaining carrier for Loading, so the wobble is mandatory rather than decorative.

One rule in the vetting is new: no ascii glyph may take a meaning a full-set glyph of the same character already holds. The two sets are one config key apart, and a user flipping the key would see a character change meaning under them. This is what disqualifies git's own `+N`/`-N` ahead-and-behind vocabulary, since `-N` would make `-` mean behind in the very cell where `full` has it mean no upstream. `>n` and `<n` are not invented: git-prompt.sh uses `=` for in sync, `>` for ahead, `<` for behind and `<>` for diverged, and starship's plain-text preset overrides only ahead to `>`, behind to `<` and diverged to `<>`, so the ascii `sync` vocabulary, `=` included, is a citation of two shipping tools.

The child marker must be one character, and the measurement is name-column pressure rather than taste. A child name gets the name column's width less the six columns the indent, marker and gap spend: 28 minus 6 = 22 columns at the column's minimum, 21 behind a two-character marker, and 40 minus 6 = 34 once the column has grown to its cap. Across the 183 child rows, one character truncates 68 of 183 names (37.2%) and two characters truncates 103 of 183 (56.3%), because 35 names sit at exactly 22 characters. GNU tree's ASCII table is `` `-- `` for a last child and `|-- ` for a middle one, with one-character forms `` ` ``, `+` and `|`; `` ` `` is the last-child form as `└` is the last-child mark, so it is a citation rather than an invention. The cost is real and recorded: `` ` `` hangs at the top of the cell where `└` hangs at the bottom left, so the visual attachment to the parent row is weaker, and `` ` `` is a legal branch-name character, so a branch literally named `` `foo `` reads oddly in the name column. git 2.50.1's `check-ref-format` rejects exactly seven printable ASCII characters in a branch name, `* : ? [ \ ^ ~`, and the gutter already spends `~` and `?`, so a marker outside the legal-branch-character set was never on offer.

Scoping the rule to the row interior is not an exemption invented for ascii. 0010's contract is about a blank cell read against a value in a cell, and a border rule and a footer hint occupy neither, which is why [keybindings.md](../spec/keybindings.md)'s footer already prints `?` and `!`, two live gutter glyphs, under `full` today with nobody confused. So the frame is exempt, and the ascii border may be `+ - |` even though `-` is a value in the row interior. The frame is also allowed a liberty the value vocabulary is not: collapsing. All four corner shapes map to `+`, which is what every surveyed line-art renderer does; lipgloss maps nine junctions to `+`, and tig collapses twelve commit-graph shapes onto eight ascii strings. A vocabulary must stay injective; line art need not, because a border is read as a region rather than decoded character by character.

The switch is half a promise, and the spec now says so. [actions.md](../spec/actions.md) draws a captured pnpm failure inside the detail pane emitting its own `└─┬` and `✕`, and Repon cannot reach inside that. The principle already exists there for colour: captured output is a quotation of another program's screen rather than one of Repon's own surfaces, so the theme deliberately does not reach inside the quoted region. It now extends to glyphs, so `glyphs = "ascii"` governs every mark Repon draws and none a child emits. Forcing a locale on the child was considered and refused: [0018](0018-an-action-is-a-fanout-of-pty-backed-steps.md) derives the child environment from git facts only, and `LC_ALL=C` would change git's own output, a bigger lie than a tofu box.

Enforcement moves earlier than the ticket asked for. [keybindings.md](../spec/keybindings.md) records that a key collision differs from glyph disjointness because it "can be checked at load", and measured, that distinction is incomplete: keybindings are user-supplied and glyph sets are not, so there is nothing at load to check and the check can run at compile time instead. This is proven in a throwaway crate: a `const fn disjoint(a: &[char], b: &[char]) -> bool` written as two nested `while` loops, plus `const _: () = assert!(disjoint(SET.gutter, SET.value), "...")`, compiles on edition 2024 and fails the build on a deliberately overlapping set with `error[E0080]: evaluation panicked`. A `GlyphSet` struct with one field per meaning adds the second half: a new meaning fails to compile until both sets define it. The limit is stated with the mechanism: the property that founded the rule was never set intersection. [0017](0017-discovery-stops-at-the-repo-boundary.md) dropped the `∙` Submodule marker because U+2219 sits one codepoint from `·` on the same row, and those two never intersected. The mechanical check is a floor, and a recorded human confusability review is the rest, which matters more in ASCII than in Unicode because `.` and `,`, `-` and `_`, `|` and `!`, `o` and `0` are all one glance apart.

One limit the machine cannot reach at all. On the Linux console the kernel's own fallback table rewrites `⠹` to `?` and `⠀` to a space, which are the Unknown and Fresh gutter marks. Disjointness is therefore a property of the glyph set composed with the terminal's substitution table, and no assertion over two compiled-in constants can check that composition. This is recorded rather than solved: it makes the braille spinner in the `full` set the more serious defect, since a full-set user on that console sees Loading rendered as Unknown, and that belongs to its own ticket rather than to a sideways amendment here.

What was refused: `glyphs = "auto"`, any third value, `TERM` sniffing and a runtime probe. "One switch, two vetted sets" is the only reason the vetting obligation stays finite and reviewable. A third set is a third disjointness proof, and an environment-derived set is an unbounded family of them. tig gates its equivalent switch on the locale codeset and that is real precedent, but the empirical kill on probing is sharper: tmux answers a cursor-position report from its own pane grid, so vim's probe measures the multiplexer rather than the terminal, and the same probe clobbers two screen rows before the first frame. A wrong automatic answer is worse than a manual switch, because the user who flipped the switch knows they flipped it.

## Consequences

- The disjointness rule gains a stated scope it never had: the row interior, meaning the gutter, the value cells and the child-row marker. The panel frame and the footer are explicitly outside it, which retroactively legitimises the `?` and `!` the footer already prints under `full`.
- The ascii Loading mark is a three-frame wobble, not the rotation everyone recognises, and its `|` beat sits against a `|` border and momentarily reads `||`. The exposure is bounded: one beat in three, and only while a row holds no values at all, since [0013](0013-no-filesystem-watching-a-refresh-is-a-cancellable-generation.md) moves the spinner into cells the moment some settle.
- `` ` `` is a legal branch-name character and hangs at the top of the cell rather than the bottom left, so a child row is marked less clearly under `ascii` than under `full`. That is the price of the one-character budget the name-column measurement imposes.
- The switch does not reach captured child output. A user who set `ascii` because their terminal cannot draw the full set still sees whatever git, pnpm and cargo emit inside the quoted region of the detail pane.
- Enforcement is a compile-time floor and nothing more: the const assertion proves the sets disjoint but cannot see confusability, a worse gap in ASCII than in Unicode. The human review is recorded alongside the assertion, not replaced by it.
- Four sentences elsewhere in the docs were false and are corrected in this ticket: [theming.md](../spec/theming.md)'s assertion about what fonts carry the `full` set, [default-branch.md](../spec/default-branch.md)'s claim that `∅` is ambiguous-width (it measures one column under both functions), [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md)'s value-set enumeration, which lists six of seven and omits `∅`, and [0016](0016-one-binding-table-feeds-every-surface.md)'s universal that every value glyph measures two under `width_cjk`, false when written because `-` has been in the value set since 0010 and measures one.
- [0019](0019-a-detached-head-is-a-shape-of-head-not-a-worktree-state.md) corrected the "`-` means you could push and have not" gloss against [default-branch.md](../spec/default-branch.md), a file that never contained it. The gloss lives in [layout-and-provenance.md](../spec/layout-and-provenance.md) and is corrected there by this ticket. That is the same shape as the defect that produced this ticket: the record says the work is done and the work is not there.
- The braille spinner in the `full` set stands as the more serious open defect: it is unreadable on any terminal that neither carries braille nor synthesises it, and on the Linux console its frames land on two other gutter marks. It graduates to its own ticket rather than being patched sideways here.

## A ninth value meaning: Checked

The Selection's own marker joins the row interior's vocabulary as a ninth value meaning, `Checked`, drawn in a column of its own rather than inside any existing cell. The two characters proposed for it, `✓` (U+2713) for `full` and `+` (U+002B) for `ascii`, are run through the same vetting this ADR ran the rest of the set through: font coverage, confusability, and the rule that a character shared by both tables must carry the same meaning in each.

Font coverage, the same cmap parse over the five macOS system monospace faces this ADR's own table used: `✓` is carried by 2 of 5 (SF Mono, Menlo). That is not the pathological tier: it matches the panel border corners' own coverage (`╭╮╰╯`, 2 of 5, the same two faces) rather than the braille spinner's zero of five, the coverage that made Loading the standing open defect above. A `full`-set glyph at this tier already ships in the row interior's own gutter-adjacent frame; `Checked` sits at the same tier as a value glyph rather than a worse one, and `ascii` remains the complete fallback for a terminal that cannot draw it, the reason the switch exists at all. `+` is one of the 95 printable ASCII characters carried by all five faces, the same as every other `ascii` glyph; no separate coverage claim is needed for it.

Confusability. `✓` is not one glance from any other `full` row-interior glyph (`≡ · - ∅ ↑ ↓ ● └`, plus the four gutter marks and the ten spinner frames): nothing else in either set is check-mark-shaped. A solid bullet (`•` U+2022, 5 of 5 coverage) was considered and rejected on exactly this ground, since it sits one glance from `●` (U+25CF), the `full` table's own Changed count glyph, and a marker easily mistaken for a dirty-file count is worse than one with imperfect coverage; `✔` (U+2714) and `☑` (U+2611) were also considered and both measure only 1 of 5 (Menlo), the same tier as `∅`, and were set aside for `✓`'s better coverage rather than either being disqualified outright. `+` repeats a character `ascii` already uses, but only in the panel border's four corners, which "The rule, and how far it reaches" above exempts from the row interior's disjointness obligation on exactly the terms that already let the ascii border's horizontal rule repeat `-`, the no-upstream value: a border is read as a region around the whole panel, a marker as a column inside one row, at different positions on the same screen. This is recorded as a second instance of that accepted class, not a new kind of risk, and `crates/repon/src/glyphs.rs`'s own tests pin both the existing collision and this new one by name. `+` was chosen over the remaining ascii alternatives that do not already carry another meaning in the row interior (`#`, `@`) because `` `-- `` and `+-- ``, GNU tree's own ascii forms for a last and a middle child respectively, already cite `+` as a tree-structure mark, the nearest available precedent for a mark denoting "this one, distinctly" in a name-adjacent column; `X` (uppercase) was set aside as a homoglyph of the table's own lowercase `x` (no remote), the same class of risk `x` itself was flagged for at "no remote at all" above. Within its own table, `+` collides with no gutter mark, no other value glyph, no spinner frame and no child marker.

`✓` does not appear anywhere in `ascii`, and `+` does not appear anywhere in `full`'s row interior, so the cross-table rule (no ascii glyph may take a meaning a full-set glyph of the same character already holds) has nothing to check for this meaning; neither character crosses tables.

Both glyphs pass and are adopted as proposed. `docs/spec/theming.md`'s "The two sets" table and `crates/repon/src/glyphs.rs`'s `glyph_set!` invocation carry the decision; the compile-time disjointness assertions extend to `Checked` automatically, since it is declared through the same macro as the other eight value meanings rather than bolted on beside it.

## A tenth value meaning: Truncated

A name cut to fit its column joins the row interior's vocabulary as a tenth value meaning, `Truncated`, drawn as the column's own last character rather than in a column of its own the way `Checked` is: the name column has no width to spare for a second axis (the same reasoning "The child marker must be one character" above already applies to this column), so the mark has to come out of the budget it is warning about rather than sit beside it. One glyph is proposed for both tables rather than a `full`-only unicode mark with an `ascii` fallback, and it is run through the same three questions: font coverage, confusability, and the cross-table meaning rule.

The character proposed is `$` (U+0024). Font coverage needs no separate claim: it is one of the 95 printable ASCII characters carried by all five surveyed faces, the tier every other `ascii` glyph already occupies, and it is proposed for `full` too, so `full` inherits the same universal coverage rather than a fancier mark at a worse tier. Width: measured with unicode-width 0.2.2, `$` returns 1 under both `width()` and `width_cjk()`, the floor every glyph in both tables already clears, so no width risk rides in with it. This is also why a `full`-only ellipsis is refused a second time here: `…` (U+2026) was already disqualified above for scoring 2 under `width_cjk`, and the same reasoning that made width "a defect class the switch happens to also close, not the reason it exists" for the rest of the set applies with the same force to a tenth glyph. One plain ASCII mark, unchanged by which table is live, is simpler to recognise than a unicode mark for one table and a different ASCII one for the other, and the ticket that opened this question proposed exactly that shape (one glyph, both sets), only at the wrong character.

Confusability. `$` is not one glance from any glyph already in either table's row interior, gutter, spinner or child marker (`≡ · - ∅ ↑ ↓ ● └ ✓` / `= . - x > < * `` ` `` `+`, the four gutter marks, and both spinner sets). The ticket proposed `+`, reasoning that it "holds no meaning in either the gutter set or the value set" — true of the ADR's original nine, but the ninth value meaning above already spent `+` on `Checked`'s own `ascii` glyph, so by the time this meaning was vetted the claim no longer held: `+` would put two distinct value meanings, `Checked` and `Truncated`, on one `ascii` character, which is exactly what `assert_row_interior_is_injective` (`crates/repon/src/glyphs.rs`) exists to catch, and it does, on the second glyph added rather than the first. `#` and `@`, the two ascii alternatives the ninth section above considered and set aside only because `+` had the stronger citation, were reconsidered for this meaning and set aside again for the same reason `+` cannot be reused: neither carries a citation as strong as the one `$` has. That citation: `less(1)` and GNU `nano` both mark a line that continues past the visible width with a `$` at the boundary, "there is more here than what is shown", the nearest available precedent for this exact meaning, in the same spirit the ahead/behind vocabulary above cites git-prompt.sh and starship rather than inventing a symbol from nothing.

This meaning carries a cost the mechanical disjointness check cannot see, the same shape of cost `` ` `` carries as the child marker: `$` is not one of `check-ref-format`'s seven forbidden printable ASCII characters (`* : ? [ \ ^ ~`), so it is a legal git ref-name character, and a name that happens to end in a literal `$` immediately before the cut boundary reads exactly as a truncated one. This is not particular to `$`; it is the price of any single character embedded inside the value's own text rather than beside it in a column of its own, the way `Checked` avoids it. The alternative, a column of its own, was refused for the reason the ticket that opened this question refused it too: "Out of scope: giving the name column the filler's slack. That needs a spec amendment and is filed separately."

Because `$` is proposed as the same character in both tables, the cross-table rule (a character shared by both tables must carry the same meaning in each) is not vacuous here the way it was for `Checked`, whose two characters never crossed at all: it is exercised directly, and it holds, since `full.truncated` and `ascii.truncated` name the identical meaning.

The glyph passes and is adopted as proposed, in both tables. `docs/spec/theming.md`'s "The two sets" table and `crates/repon/src/glyphs.rs`'s `glyph_set!` invocation carry the decision as a tenth value field, `truncated`, declared through the same macro as the other nine value meanings; the compile-time and `#[test]` disjointness checks extend to it automatically rather than being bolted on beside it.

## Amended by #265

The name column is no longer 28 columns wide, and `Truncated` is no longer the name column's alone. The spec amendment this ADR filed separately ("Out of scope: giving the name column the filler's slack") has landed: [layout-and-provenance.md](../spec/layout-and-provenance.md)'s "Growing `name` and `branch`" gives `name` a 28-column minimum and a 40-column cap and `branch` a 24-column minimum and a 75-column cap, both growing into the slack the filler used to keep. So the child-name arithmetic above states both ends of the rule rather than the single figure it once did, and the 68-of-183 truncation count it measured is the floor, at the column's minimum, rather than the count on any frame with slack to share out.

Two figures in this ADR read differently now and neither is wrong. The one-character child marker still earns its place: the measured cost of a second character is one column off the child budget at every name-column width, so the argument is unchanged wherever the column sits between 28 and 40. And `$` reaches `branch` as well as `name`: the value it warns about is a user-supplied string long enough to overflow, `branch` is now the other column holding one, and the reason this ADR gave for marking `name` ("a silent cut looks like a whole value") is the same reason. `crates/repon/src/glyphs.rs` is untouched by that: both cells read the same `truncated` field, so the vetting above covers the second use without a second glyph.

What the earlier reasoning missed is that the name column's width was treated as a constant of the design when it was only a constant of the implementation. The measurement it rests on (name-column pressure) is real and still governs; the number 28 was the pressure at one frame width, and the ADR wrote it down as though it were the pressure at all of them.
