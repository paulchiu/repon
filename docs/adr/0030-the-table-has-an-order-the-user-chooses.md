# The table has an order the user chooses, it is modal, and it is session state

The table had exactly one order: grouped discovery order, a Repo followed by its own Worktrees and Submodules, fixed by [layout-and-provenance.md](../spec/layout-and-provenance.md#the-list). That order answers "what have I got" and nothing else. It cannot answer which Repo is dirtiest, which branch is furthest behind, or where the `gone` Worktrees are, which are the questions the outer loop is actually opened for ([0002](0002-repon-owns-the-outer-loop-only.md)). `o` now opens a sort menu, one column key puts the table in that column's order, and the same key again reverses it.

The interaction model is not invented here. It is the one the author already built and uses in blubat (`src/tui/{app,view,render,columns}.rs`), reproduced rather than improved on: a mode key opens a menu, the table holds still underneath it in whatever order it was already in, only the footer's advertised keys change, and a second keypress picks the column and closes the menu. The state is a `(column, direction)` pair. Choosing the active column reverses the direction; choosing any other column opens it at that column's own natural direction and never inherits the previous column's, which is blubat's `View::choose_sort` transcribed into `RowOrder::choose`. Copying a model the author has lived with for months is worth more than a locally better one they have not.

The natural directions are one rule, not six. `name` and `branch` open ascending, A to Z, because they are labels and a label's order is alphabetical. The other four, `sync`, `base`, `dirty` and `state`, all count trouble, and the reason to sort by a count of trouble is to bring the worst rows to the top, so they open descending. Every one of them is one keypress from its opposite, so none is a decision the user is stuck with.

Two of those four have no count to rank by directly, so their orders are written out rather than left to an enum's own declaration order. `state` is ranked worst first: **Gone**, whose upstream is deleted, so nothing on the remote remembers the branch; then **Merged**, landed and safe to sweep; then **Local only**, never pushed and so never safe to sweep ([0009](0009-worktree-state-model.md)); then **Active**, unlanded pushed work, the ordinary state with nothing to do about it. `WorktreeState`'s own variant order is a narrative order, not a ranking, and taking it would have been a ranking arrived at by accident. `sync` is ranked the same way: a rank, then the behind count, then the ahead count, so descending opens on the rows furthest behind their upstream and sinks the rows with nothing to compare against, `NoUpstream` and then `NoRemote`, to the bottom. `base` and `dirty` need none of this: each is already one number, commits behind the default branch and changed paths, and descending is that number descending.

**Grouping is not something a sort may undo.** A sort reorders the Repos among themselves and each Repo's own Worktrees and Submodules within that Repo. A child never leaves its parent and the groups never flatten, in every column and both directions. This is the invariant `visible_row_order` already held and that [#248](https://github.com/paulchiu/repon/issues/248) recorded the cost of losing. It is held here by construction rather than by a rule the comparator has to remember: the sort runs over the flat candidate list and `grouped_row_order` runs over the result, so the group walk takes the Repos in the sorted order and each Repo's own children in the sorted order. There is no arrangement of the comparator that can flatten a group, because the comparator never sees a group.

**A cell that has settled no value sorts last in both directions.** Unknown, Failed, Not applicable, and a cell nothing has probed yet all fall on the same side, and the direction reverses the value rather than the absence: the key is a `(has no value, value)` pair, and only the second half is reversed. This is [0001](0001-per-cell-provenance.md) reaching the order. An unknown dirty count is not a clean row, and reversing the direction must not make it the dirtiest row either; either reading is the absent count rendering as a number, which is the defect per-cell provenance exists to prevent. blubat does the same thing for an unread battery level, and for the same reason.

**The column keys are rows of their own context and of no other.** `n`, `b`, `s`, `a`, `d` and `t` are letters that already mean something outside the menu: `b` re-derives default branches, `s` opens the Set picker, `n` jumps to the next failed row, `d` dismisses a Vanished row, `a` selects every visible row. Binding a column to one of those globally would let a stray press reorder the table from underneath the list, which is exactly what blubat's own comment says it routes its column keys around the dispatcher to prevent. Repon already has contexts, so the way to say the same thing here is a seventh one: `sort` is its own context, `global` is suspended in it the way it is in `input`, `overlay` and `confirm`, and the menu swallows every key it does not bind. That keeps [0016](0016-one-binding-table-feeds-every-surface.md) intact, which routing around the table would not have: the menu's footer is derived from the same compiled rows as every other footer rather than written out as strings, and a `[keys.sort]` block rebinds a column the same way `[keys.list]` rebinds anything else.

**It is session state, not config.** The sort survives a Refresh, a Filter committed or cleared and a Set switch, and a restart opens on the natural grouped order. Nothing writes it to `state.toml`. This follows [0006](0006-no-git-state-cache-session-state-by-name.md)'s line on what session state is for, and it is a narrower claim than blubat makes: blubat's `[dashboard] sort` names the column its dashboard opens on, because a battery dashboard is opened to answer one question and the same one every time. Repon's table is opened to answer whichever question that morning has, so a configured default would be a guess with a keystroke's worth of value and a config key's worth of surface. `0` restores the natural order, which is the same escape a restart gives, without waiting for one.

Three costs are accepted rather than mitigated. The header's arrow is appended to the column's own text with no space, `dirty↓` rather than `dirty ↓`, because `base` and `dirty` are six columns wide and a space costs exactly those two columns their arrow; one spacing rule that fits every column beats a prettier one that silently fails on two of them. `o` is not in the list or detail footer, both of which are at their documented full widths with no room for a ninth hint; it is a `global` binding, so the help overlay's own `global` section already carries it, and the column keys are taught by the menu's own footer at the one moment they mean anything. And `state` has no value on a Repo row, which is a settled Not applicable rather than a gap ([0019](0019-a-detached-head-is-a-shape-of-head-not-a-worktree-state.md)), so sorting by `state` orders the Worktrees inside each Repo and leaves the Repos themselves in discovery order. That is the honest rendering of a column that means nothing for half the rows, and it is what grouping costs.

## Amended by #284

Manual use reversed two things this ADR chose deliberately. The interaction model it borrowed from blubat, `RowOrder::choose`, the natural-direction rule and everything about grouping, is unchanged; what was wrong is what a cold start defaults to and where the choice lives.

The natural order was never a neutral absence of a sort, and calling it one is the mistake underneath both reversals. `RowOrder::Natural` is grouped discovery order, and discovery orders nothing: the walk pushes each directory's own `fs::read_dir` entries onto a stack with no `.sort()` anywhere outside `#[cfg(test)]` (`discovery.rs`'s walk). So the order a fresh table opens on is whatever the filesystem happened to hand back, arbitrary, different machine to machine, and shifting as directories are created or removed. This ADR weighed a configured default against that order as though the order were free of a guess itself, and it is not; it is a guess made by the filesystem instead of the user, and a worse one, because it carries no reason a reader could name. Alphabetical is the order a list of names is expected to arrive in and it is stable, so `RowOrder::cold_start` (name ascending) is what a session with nothing stored now opens on, in place of `Natural`. `Natural` stays exactly what it was otherwise: reachable through `0`, and the one order no header carries an arrow for.

"It is session state, not config. Nothing writes it to `state.toml`" bundled two claims, and only the first holds up. Sort still has no place in `config.toml`, for the reason already given: the table is opened to answer whichever question that session has, so one configured column would be a guess with a keystroke's worth of value for every session it guessed wrong for. But "session state" is precisely what `state.toml` exists to persist ([0006](0006-no-git-state-cache-session-state-by-name.md)), and `filter` was already living proof: an empty string restoring as no committed Filter, next to the Selection, by name, across a restart. The second sentence never followed from the first, and sort now sits beside `filter` in `ScopeState` on the same terms, `RowOrder` (and `SortColumn`, `Direction`) round-tripping through `state.toml` per scope, including a `Natural` chosen with `0` and then kept through a quit. An older build's file, or a first run, carries no `sort` key at all, which restores as `RowOrder::cold_start` rather than failing or silently becoming `Natural`.

Both changes stay inside `crates/repon`. `RowOrder`, `SortColumn` and `Direction` are still defined in `sort.rs` and gain nothing but `Serialize`/`Deserialize`; `state.rs` reads them the same way it already reads `Filter`'s own string. `repon-core` gains no vocabulary for sort, and `repon status`, its one other consumer, still has no cursor and nothing to sort.

See [#284](https://github.com/paulchiu/repon/issues/284).
