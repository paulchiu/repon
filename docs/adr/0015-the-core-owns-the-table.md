# The core owns the table, and only the core supersedes

`repon-core` owns the assembled table of entities and their state, only `repon-core` applies supersession, and its public surface is a snapshot the consumer reads rather than a channel of cell updates. Whoever writes a cell must hold that cell's previous Generation, so whoever writes owns the state. A bare channel of cell updates as the public API leaves the state in the consumer, and every consumer then reimplements per-cell Generation bookkeeping: a second apply loop kept consistent by hand, which is the failure [0005](0005-rendering-agnostic-core.md) exists to prevent, arriving through the API rather than through a widget layer.

The split is fixed. The core owns discovery, the probe phases, the metadata poll, a Set as a bounding specification it is handed, the Generation counter and supersession, the fold of a row's cells into one summary, the environment contract for a child process expressed as data, and Action fan-out. The consumer owns the terminal, the Launcher end to end, config discovery and parsing, when a Filter is applied, the cursor, every glyph, the theme and the keybindings. The line is the terminal, not the process. What the crate root exposes is the vocabulary [GLOSSARY.md](../../GLOSSARY.md) already names, so reading the crate root and reading the glossary give the same answer.

**Enforcement:** `just check-core-isolation` holds the dependency boundary. `public_surface_matches_glossary` in `crates/repon-core/src/lib.rs` fails on a crate-root export the glossary does not name, and `modules_the_release_gate_names_are_private_at_the_crate_root` beside it reads the private-module list out of [releasing.md](../spec/releasing.md) and fails if one of them is public. `every_settled_known_destructure_names_every_field_it_does_not_use` in `crates/repon/src/test_support.rs` holds the cell contract the snapshot carries.
