# A management run moves off the calling thread and cancels between rows

`App::run_management`'s per-row work now runs on a background thread `y` over a built-in's confirm gate starts, rather than on the thread that draws frames and reads keys. This is the second half of #336, deliberately not attempted there: the first half made the run legible, painting a Notice naming each row and its position before that row's own work starts, but it still ran that work inline, so the whole draw-and-input loop sat still for however long `delete`'s own worktree walk and hooks took. Issue #342 is the rest.

## The seam

`App` holds `core: Core` by value, and `Core` owns a `JoinHandle` and a channel `Sender`, so exactly one owner may exist; a detached thread needs `Send + 'static` access, which rules out cloning `Core` itself. The per-row work `management::run_one_record` needs only five operations, none of which touch `Core`'s own mutable state (`action_running`, `action_control`, the clock thread): `worktree_admin_dir`, `linked_worktree_paths`, `ignored_directories_for_deletion` and `attempt_auto_update` each open the repo fresh from the path on every call, and `run_action_for_entity_blocking` needs only a clone of `Core`'s own `Arc<RwLock<Table>>`. `repon_core::ManagementHandle`, vended by `Core::management_handle`, is exactly those five methods behind a small `Send + Clone` struct wrapping that one `Arc` clone — the identical shape `Core::run_action`'s own fan-out thread already takes for its `Arc<AtomicBool>` and `Arc<RwLock<Table>>` clones, so the pattern is established rather than invented.

`before_sync` and `after_sync` are still resolved on the calling thread, fresh from `self.document` and `self.active_set.name`, into an owned `ActionSpec` before the thread starts: this keeps [0032](0032-hooks-around-a-built-in-fire-on-its-own-confirm-gate-never-its-completion.md)'s restriction intact exactly as it stood, since the hook still fires from the `y` that reached `run_management`, never from a Generation or a timer — only how the result is awaited moved, and that was already true of `run_action_for_entity_blocking`'s own synchronous shape before this change.

## Applying the report stays on the calling thread

`record_own_work`, `dismiss`, the Selection removal, `reload_config`, the cursor re-clamp and the summary Notice all touch `self.document`, `self.selection` and `self.cursor`, App-only state a background thread has no business reaching for. These now live in `App::apply_management_report`, called from `App::poll_management_run`, which drains a channel the background thread sends its finished `management::Report` on. Nothing but an explicit drain clears `App::management_run`, and nothing but `Message::Tick` calls `poll_management_run` in production, so the report is applied on the very next tick after the thread finishes rather than on some later keypress. `App::run_management`'s own two scan-marked regions, `management_run_start` and `management_report_apply`, hold the same two invariants [0032](0032-hooks-around-a-built-in-fire-on-its-own-confirm-gate-never-its-completion.md)'s tests already checked in one region before the split: the sync hooks fire only from inside the run, and a management write reaches the running app through `reload_config` alone, never through a second assignment of `self.document`.

## Refusing a second run

`App::management_running` mirrors `Core::action_running`'s own read exactly: `true` from the instant the confirm gate is accepted until the report is applied. The same bindings `action_running` already gates while a fan-out is live — `;`, `m`, `s`, `1` to `9`, `Ctrl+R` and `e` — are now gated on `App::any_run_outstanding`, the two conditions combined, so a fan-out and a management run can never both reach for `self.core` or `self.document` at once. `q` and `Ctrl+C` gain the identical confirm-first treatment quitting mid-fan-out already has, since a confirmed quit now abandons a background thread either way. Rejecting outright rather than queuing is the same choice `Core::run_action` already made for a second fan-out: a queue needs its own ordering and cancellation story nothing here asks for.

## Cancellation: between rows, never mid-row

This is the one question #342 left open rather than settled by precedent, and it needs its own answer rather than inheriting `Core::run_action`'s. That fan-out cancels an Action's steps directly, mid-flight, with SIGTERM then SIGKILL: a step is a child process, and killing one leaves a `Cancelled` receipt that is an honest description of what happened. A management operation's own row is not a child process. `delete`'s own row is a filesystem walk and two rounds of `fs::remove_dir_all`; interrupting it mid-call leaves a working tree in a state nothing describes and no later run can distinguish from a filesystem error, which is worse than finishing the row.

So `Action::Unwind`'s own `CancelManagementOnUnwind` level, tried at the same innermost priority as `CancelActionOnUnwind` (the two are mutually exclusive, since starting either is refused while the other is outstanding), raises a flag the background thread checks once, at the top of its loop, before starting the next row. A row already running always finishes; the flag only ever stops the *next* one from starting. The report sent back carries how many rows it actually reached, and `management::cancelled_summary` says so explicitly — "cancelled after 1/2" rather than a summary that silently undercounts what a full run would have shown — because a truncated run answering with the same words a complete one uses would read as success.

## Consequences

- `repon_core::ManagementHandle` is a new public type, documented in `GLOSSARY.md` alongside "Management operation": the read-only, path-driven reads a Core gives on the calling thread, plus `run_action_for_entity_blocking`, and none of a Core's other state.
- `App::run_management` no longer takes a `paint` closure. The confirm-gate-to-run handoff no longer needs a live `Tui` in hand at all: `handle_action_palette_key`, and the `handle_key_event_with_tui`/`handle_key_event` split that existed only to thread one through, collapse into a single `handle_key_event`, since nothing on that path holds a live `Tui` any more. The row Notice's own liveness now comes from the ordinary render loop reading `App::live_management_row_notice` every frame, not from an explicit repaint call between rows.
- `docs/spec/repo-management.md`'s "Once accepted" is rewritten to describe the background thread, the keys still gated and still live, and the between-rows cancellation grain; its "Writing config" section's "same frame the write completes" is now "the first tick after its background thread finishes", since a write genuinely no longer completes inside the keystroke's own frame.
- `docs/spec/keybindings.md`'s "Quitting, suspending, confirming" now names a management run alongside an Action fan-out everywhere it already named the latter alone.
- No change to what a management operation does, what it gates, or what it writes: `repo-management.md`'s receipts, refusals and confirm-gate wording otherwise stand, and the safety guards `remove_working_tree` and its callers already carry (the absolute-path and `.git` checks) are unmoved, since only which thread calls them changed.
