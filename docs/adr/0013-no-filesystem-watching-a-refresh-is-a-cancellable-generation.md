# No filesystem watching; a refresh is a cancellable generation

A real watcher was built and run rather than reasoned about: notify 8.2.0 with notify-debouncer-mini 0.7.0, recursive over both roots. It costs nothing to speak of. FSEvents delivers over a Mach port, so the file descriptor delta is zero regardless of tree size, resident memory rises by about 1.2 MB, arming takes 5ms, and three 180 second idle windows measured 0.00, 2.21 and 2.29 events per second, a trickle rather than a firehose. It was rejected anyway, for two reasons that are properties of this population rather than of notify. The values a cheap watch of `.git` can see, the branch and the two ahead/behind counts, cost 0.15 seconds to recompute for all 403 entities, so the watcher would buy a value that is already free. The value that would actually justify it, the typed status counts, needs the working tree watched, and the two roots hold 6,715,405 filesystem entries of which 78% are inside `node_modules`. Prior art agrees: lazygit contains no `fsnotify` anywhere in its source and polls instead, gitui reverted watching to an opt-in `--watcher` flag, tig polls `lstat` on named files inside the gitdir, and magit runs no timer-driven refresh at all. The one Rust tool found watching many repositories had to pass `NoCache` explicitly, because the convenience constructor's default file-id map allocated 1.87 GiB on this tree and had still not finished arming after 121 seconds.

What replaces the watcher is cheaper than the watcher: a sweep of `HEAD`, `index`, `packed-refs` and `refs/` across all 441 entities costs 1.79ms, and runs every 2 seconds, which is lazygit's own external-change-detection interval. Its blindness is stated rather than engineered around. It sees a commit, a checkout, a stage and a hard reset; it misses an unstaged edit, an untracked file, and a fetch, the last because `refs/remotes/origin/` gains an entry without moving the mtime of `refs/` itself.

A refresh is a generation, and an abandoned generation is cancelled rather than left to finish. lazygit and gitui both take the other option, letting the old refresh run to completion and dropping its write on arrival, and that is what this design expected to copy. Measured, letting it run costs 1.79 times the next generation's wall clock, because two generations contend for the same eighteen cores and the second pays for both. Setting gix's `should_interrupt` flag instead brings the next generation in at 1.04 times a cold run. The flag is checked per index entry, so a single Repo stops in 0.5 to 0.9ms, and a whole generation stops in about 250ms, nearly all of which is tasks that had not started yet still doing `gix::open` before reaching their first check. The difference from the prior art is scale: lazygit and gitui refresh one repository, Repon fans out over 403. Cancellation is cooperative, so late results still arrive and must still lose, which is why every result carries the generation that produced it and the comparison happens at the point of writing the cell rather than at the channel. That also makes supersession per entity rather than global, so a refresh scoped to the Selection cancels work only for the entities it covers and cannot strand the four hundred rows it never spoke for. Mechanics live in [the refresh spec](../spec/refresh.md).

The recorded cost model was wrong, mostly in the comfortable direction. The full probe of every entity is 4.4 seconds rather than 7.2, boundary-stop discovery is 19ms rather than 0.54 seconds, opening a Repo and reading its branch is 0.4ms rather than 10ms, and the status median is 11ms uncontended rather than 94ms. Two figures were wrong in ways that changed the design. Subsetting the expensive phase to the visible rows does not bound its latency: twenty rows took 1.145 seconds where ninety-four took 0.633, because one 40,000 file monorepo happened to sit in the first twenty. Visible-first is therefore an ordering and not a scope, and a refresh always covers every entity. And `.git` size does not predict probe cost, since `baseweb` carries 317 MB of `.git` and costs 47ms while `squad-metadata` carries 4 MB and costs 91ms, so the ordering is by position rather than by any cost heuristic, and the real predictor, working-tree file count, costs a full walk to learn. One further check settled a worry about the watcher that no longer matters but is worth recording: a gix status writes nothing at all, verified by a recursive snapshot of every file under `.git` taken before and after a full probe and found byte-identical, so Repon's own reads can never be mistaken for someone else's changes.

## Consequences

- Filesystem watching is closed rather than deferred, and the map's fog entry for it goes with it. A future reader will want to add notify, because the watcher measured cheap and the idle event rate is a trickle. It is cheap; what rules it out is the working-tree scope it needs and the freeness of what a cheaper watch would detect, and both of those are facts about this population.
- gix's per-repository thread limit is set to 1 and the fan-out is one rayon task per entity. Measured at 3.36 seconds wall and a 44.6ms median, against 4.50 seconds and 88.9ms with gix's own parallelism left on, because gix's status is internally parallel and a 403-way fan-out oversubscribes eighteen cores by an order of magnitude. This is not a config key: it is a measured property of two libraries rather than a taste, and exposing it would invite someone to make it worse. The measurement was made at design time and recorded here and in the specs it points at, but the setting itself did not reach `dirty_counts` until [#360](https://github.com/paulchiu/repon/issues/360): a claim asserted in three documents with nothing checking it is exactly how a decision and its implementation drift apart. What now holds them together is a source scan in `repon`'s test suite that reads `dirty_counts`'s marked region and fails if the `thread_limit` call is ever removed, so the divergence cannot reopen silently.
- The bullet above fixed gix's own thread limit but never varied the fan-out's other half, the pool width, which was simply whatever rayon's global pool defaults to (`std::thread::available_parallelism()`) and had never been measured at all: a setting nobody chose is not a decision, and [#361](https://github.com/paulchiu/repon/issues/361) exists because that gap is exactly how the thread-limit claim above went unimplemented for as long as it did. It built a reproducible harness, `tools/fanout-sweep` (its own workspace, outside `just ci`'s build and lint passes; `just sweep-fanout` and `just sweep-fanout-real` run it), timing one entity's full per-entity task warm from cache: branch, sync, default branch and base (all cheap on this corpus, since none of its repositories carry a remote or ever diverge from their own default branch, the same early-return path production's own `resolve_sync`, `default_branch::ChainFacts::resolve` and `base::probe` take for such a repository) followed by phase C's status walk, the dominant cost. The one phase not reproduced is worktree state: production itself only ever calls it for a `Kind::Worktree` entity, never a `Kind::Repo`, so a corpus of plain repositories exercises it in neither production nor this harness, and the real population's own linked worktrees still go untimed for that one phase. Swept pool width in {1, 2, 4, 8, 12, 18, 36} against gix's thread limit in {1, 2, 4, none}, three repeats per cell, on two synthetic corpora it generates from a seed (150 and 400 entities, shaped after refresh.md's own population: one or two outliers at 15,000-25,000 files, well under `vial-qmk`'s real 40,871, scaled down for corpus-build time and cross-checked separately by the single-repo `vial-qmk` measurement above; a heavy tail; a mass of small clean repos; a small dirty minority), then read-only against the owner's real `~/dev` plus `~/dev-misc` population as a check against the model, all on the same Apple M5 Max (18 cores) and rustc 1.95.0 this document's other 2026-08-30 measurement used, on 2026-09-03. The real-population figure itself moved under this fix: the walk's own boundary rule had checked only `dir.join(".git").is_dir()`, missing every linked worktree and submodule checkout, whose own `.git` is a file rather than a directory, the same rule `crates/repon-core/src/discovery.rs`'s `is_boundary` already uses (`dir.join(".git").exists()`); corrected to match, the same two roots resolve to 391 repository boundaries, not the 202 this document previously cited, and `just sweep-fanout-real`'s own example is fixed alongside it, since `~/dev,~/dev-misc` typed as one shell argument only tilde-expands the first root and the recipe silently ran on one root instead of two; it now takes each root as its own shell word. That real-population check reproduces discovery and phase C faithfully but not phases A and B, which it times on the no-remote early-return path for every entity while 342 of the 391 boundaries it finds do carry a remote, whose sync and default-branch phases production resolves with a live ahead/behind walk and a climb up the default-branch chain instead; the run prints that count itself rather than leaving it to be guessed. So the real population's absolute per-entity times are a lower bound rather than a stand-in for what a refresh of that machine costs, and what they support is the comparison across pool widths inside that corpus, where every cell pays the same omission. Nor is the population wholly organic: 37 of the 391 are a discovery-test fixture tree under `~/dev-misc` carrying one tracked file each, so they pad the entity count by about a tenth while contributing 37 of its 409,110 tracked files.

  Two things held, and a third turned out to be the more useful finding. Pool width is a broad plateau rather than a sharp optimum: at gix's thread limit pinned to 1 (the shipped setting), wall clock from 4 workers up through 36 stayed within a 6-12% band in every corpus tried (256-287ms on the 150-entity corpus; 660-703ms on the 400-entity corpus; 3.17-3.48s across the real population), where the 150-entity corpus alone had previously shown a noisy 34% band and no plateau at all. Gix's own thread limit is not, though, reconfirmed as worth pinning "at every scale tested" the way this document previously read: leaving it unbounded beats a pin of 1 outright at pool widths 1 and 2 in all three corpora, by 31-104% at width 1 (563.7ms against 431.6ms on the 150-entity corpus; 1.84s against 1.07s on the 400-entity corpus; 13.88s against 6.81s across the real population), because a width-1 pool leaves every other core for gix's own internal parallelism to spend, the same shape the single-repo `vial-qmk` isolation check above already showed. From width 4 up the ranking reverses on the real population, where pinning wins at every width by 4-18%, and is inside noise on the synthetic corpora, where the two stay within about 9% of each other and the sign flips from corpus to corpus.

  The third finding is about the numbers themselves, and it is why the figures above are quoted from one named run rather than averaged into a single authority. Re-run on the same machine, the same day, against the same code, the real population's width-1 pinned cell moved from 10.66s to 13.88s, the 150-entity plateau band moved from 17% to 12%, and the from-width-4 pin-versus-unbounded ranking flipped sign on both synthetic corpora. Three repeats per cell is not enough to separate cells that sit within roughly 10% of each other on a developer's live machine, and a page cache warmed by whatever else ran that hour moves the real corpus most of all. What survives re-running is the shape: the plateau from width 4 up, the pin being clearly wrong at widths 1 and 2, and width 18 being the best-behaved choice under contention. What does not survive is any ranking inside the plateau, so none of it should be hand-tuned on. Pinning to 1 remains the right default because it is at worst close to the best cell at the width the fan-out actually runs, and clearly right on the real population, not because it wins everywhere.

  The plateau is not flat once something else is sharing the cores, and this changes the picture in the pin's favour rather than against it. Recomposed on the 400-entity corpus with gix's thread limit fixed at 1, as shipped, and idle threads standing in for a concurrent fetch (4) or a full-width Action (18): the fastest cell in each regime was 564.7ms (idle, width 8), 681.7ms (moderate contention, width 36) and 808.3ms (heavy contention, width 36). A pool of 18, the physical core count and exactly what the global pool's own default already gives for free, stayed the closest of every width tried to whichever cell was fastest in its own regime, never worse than 5.8% off it (+5.8% idle, +1.9% moderate, +2.7% heavy); every other width lost by more in at least one regime, from +9.3% (width 36) up to +19.2% (width 4, the narrowest plausible hand-picked pool), because a narrow dedicated pool that looks competitive while idle is the one that falls furthest behind once a concurrent Action claims the rest of the machine. That ordering is the part to rely on: an earlier run of this same sweep put width 18 at +27.6% idle rather than +5.8% and named width 4 the idle winner, so the margins move with the machine's mood even though the ranking under contention does not. So the width stays what it already was, for a different reason than nobody having looked: a dedicated pool sized to a hand-picked constant was measured and rejected, since it would spend a second idle thread pool's worth of memory and startup cost to land nowhere this sweep found reliably better than free. `crates/repon-core/src/core.rs`'s `dispatch_probes` carries the same reasoning at its own dispatch site, and `probe_fan_out_still_uses_rayons_global_pool_rather_than_a_dedicated_one` in `repon`'s test suite is this decision's own source scan, the same shape as the thread-limit one above: a future dedicated pool is a real change to make on purpose, with a new sweep and an ADR update behind it, not one that lands silently.
- Unknown carries a reason. Timed out, no upstream and no default branch are all Unknown and all render `?` in the gutter; the detail pane says which. A sixth provenance state was rejected because it would cost a sixth glyph, a new disjointness obligation under [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md) and a reopened [0001](0001-per-cell-provenance.md), for a distinction that only matters once someone has looked at the row.
- The deadline belongs to the generation, not the cell. A rayon task cannot be pre-empted, so a per-cell deadline could only mark a cell while the work carried on underneath it, and a probe that is still running has not asked and got nothing back. A generation is cancelled at 30 seconds, comfortably clear of the measured 4.4, and every cell still Loading in it becomes Unknown at that moment.
- The spinner may appear in a cell as well as in the gutter, which amends [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md). While a row holds no values the spinner sits in the gutter, one moving character per row; once only some cells are outstanding it moves into those cells, because after the cheap phase lands in 0.4ms the branch is settled while the status is not. This is not the per-cell variant 0010 rejected, which put a glyph in every cell for every state.
- Six configuration keys fall out and belong to [Design the config schema](https://github.com/paulchiu/repon/issues/9): `refresh.poll_interval` (2s, 0 disables), `refresh.status_stale_after` (5m), `refresh.on_focus` (true), `fetch.enabled` (false), `fetch.interval` (5m) and `fetch.concurrency` (4). The fan-out shape is deliberately not among them.
- The periodic fetch must prune or Gone never appears at all, and 191 of the 203 Repos with remotes point at github.com, which documents a ceiling of roughly 15 read operations per second per repository and warns about automated read traffic, so its concurrency is bounded rather than fanned out.

## Amended by 0019

`Unknown`'s closed set of reasons shrinks from four to two. `NoUpstream` and `NoRemote` are removed, because a branch that tracks nothing renders `-` and a Repo with no remote renders `∅`, both values behind a blank gutter, and `base` is already Not applicable in the second case. Each was a settled fact wearing a missing one's mark, and the contradiction was live: the same fact rendered blank with `?` in [core-api.md](../spec/core-api.md) and as `-` on 16 Submodule rows in [discovery.md](../spec/discovery.md). `TimedOut` and `NoDefaultBranch` remain, and the set stays closed. Closed bounds how the set changes, not its size: a third reason, `SubmoduleUninitialized`, was added later for the uninitialised Submodule row, which [core-api.md](../spec/core-api.md) carries. See [0019](0019-a-detached-head-is-a-shape-of-head-not-a-worktree-state.md).
