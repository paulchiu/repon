# Repon releases what it enables and holds mouse capture off

Repon claims five pieces of terminal state on entry: raw mode, the alternate screen, bracketed paste, focus reporting and mouse capture. Four of those are enables, and each is released on every exit from the screen. The fifth is a disable, and it is never released. The contract is therefore **no residue**, that nothing Repon turned on is left on, and not "the terminal is left exactly as found", which is the sentence this decision retires. Both documents carried the retired sentence, not one: [config.md](../spec/config.md) said five pieces are restored under `## Launchers`, and [keybindings.md](../spec/keybindings.md#terminal-state) repeated the claim four lines below the row of its own table saying mouse capture is off. The conflict was noticed across the two documents and was already inside one of them.

The reason "as found" is the wrong promise is that mouse capture is not a durable terminal setting. A colour scheme, a font size or a scrollback limit persists across the programs that run in the terminal; DEC private modes 1000, 1002, 1003 and 1006 are set by a running program for its own lifetime and cleared by it on the way out. Nothing sets them on an idle shell and leaves them set. So a terminal found with capture on is, very nearly by definition, a terminal that something crashed or was killed out of, and the state that "as found" would have Repon preserve has no owner who chose it. The unconditional disable on entry repairs that terminal rather than damaging it. This is the argument that settles the ticket; the implementation difficulty below is a second reason, not the first one.

The two rejected behaviours fail against that. Never touching mouse capture satisfies "as found" trivially and means Repon runs with capture on in exactly the terminal described above, taking the terminal's own select-and-copy away from a screen that is mostly Repo paths and branch names people copy out of it, which is [0016](0016-one-binding-table-feeds-every-surface.md)'s stated reason for the setting; it was tried and reverted. Disabling on entry and enabling on restore satisfies the "independent enable/disable pairs" framing literally and turns capture *on* in the overwhelmingly common terminal that never had it, which is the worst of the three, because it is the only one that leaves residue.

Detection is not available, and the shape of its absence is worth recording, because a future reader will assume crossterm can be asked. It half can: `supports_keyboard_enhancement` in 0.29 writes `\x1B[?u\x1B[c`, a query followed by a primary device attributes sentinel, and waits on the reply with a 2000ms timeout, which is the whole pattern a DECRQM probe of mode 1000 would need. But it runs on `poll_internal` and `read_internal` behind private event filters with no public equivalent, so a mouse-mode probe means reading `/dev/tty` directly, racing the event thread that owns that stream, and paying crossterm's own 2000ms as the precedent worst case. The restore path is shared with quitting and with the panic hook, neither of which may block on a terminal that will never answer.

`XTSAVE` and `XTRESTORE`, `CSI ? 1000 s` and `CSI ? 1000 r`, were considered and rejected on the second paragraph rather than on cost. They are the mechanism the difficulty above would justify: no reply to read, so no timeout, no race and no crossterm API gap, and a terminal that does not implement them ignores both and lands on exactly the behaviour taken here, which is a safe degradation. They are rejected because faithfully restoring the previous value restores a state nobody chose, so the mechanism would work and the outcome would be wrong. The reopening condition is [0016](0016-one-binding-table-feeds-every-surface.md)'s own for the whole subject: someone wanting mouse support.

The rule moved documents because it was filed under the wrong owner. `Tui::exit` reaches `write_restore_sequence`, and `Tui::exit` is called by the Launcher handoff, by `Ctrl+Z`, by quitting and by the panic hook, so a rule written under `## Launchers` described one of four callers. [keybindings.md](../spec/keybindings.md#terminal-state)'s `## Terminal state` table already owns the five pieces and the reason for each setting, so it owns the asymmetry too, and it is the single source. [config.md](../spec/config.md#launchers) keeps the crossterm mechanics that are genuinely its own, that every piece is an independent pair with no automatic restoration and that ratatui's panic-hook example restores only two of them, and redirects for the contract rather than dropping a paragraph a reader will still go looking for. The redirect is itself asserted by a test, because a pointer nobody checks decays into a second copy, which is how the two documents came to disagree in the first place.

What keeps it true is a column rather than a comment. The table gains `released`, four times `yes` and once `no`, and the conformance test reads each piece's claim and release straight out of it: the `setting` column decides which of the enable/disable pair is written on entry, and the `released` column decides whether the other one appears on the way out or whether neither may. The previous test parsed a count out of prose and then hardcoded mouse capture as the exception in Rust, which meant the assertion, not the specification, was where the exception lived; a second asymmetry could be introduced in the code and argued for in prose without the test caring which document had blessed it. Now the spec names the exception set and the code cannot invent a member of it. A column is right here and a list was right in [0023](0023-an-unbuilt-binding-is-not-advertised-and-an-unavailable-one-answers-on-press.md) for the same reason in both cases: five rows in one table make a column that is read at a glance, and eleven exceptions scattered over six tables would have made six columns of "yes" concealing them.

Two boundaries follow. A child process is free to enable mouse capture for its own run, and lazygit does; Repon's requirement binds Repon, and re-entry disables unconditionally, so nothing the child leaves set can survive back into Repon's own screen. And [0016](0016-one-binding-table-feeds-every-surface.md) describes the behaviour as "not enabled at all", which reads as never touching it and is not what ships; it is corrected by amendment there rather than edited in place, so a reader arriving at the mouse question from the binding table gets the same answer as one arriving from the terminal-state table.
