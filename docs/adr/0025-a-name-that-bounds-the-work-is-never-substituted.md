# A name that bounds the work is never substituted

When the user supplies a name Repon cannot resolve, Repon either substitutes something else and warns, or refuses to start. Which grade applies depends on what the name decides. A name that decides how things *look* may fall back, because the substitution announces itself and costs nothing to undo. A name that **bounds the work**, what exists, what is discovered, what a gesture acts on, is never substituted: Repon exits non-zero before the terminal is claimed. An unresolvable `--set`, `REPON_SET`, `--config` or `REPON_CONFIG` takes the second grade; a `theme` that names nothing keeps the first.

A Set is the second kind by [config.md](../spec/config.md#sets)'s own definition: an entity excluded by a Set is never discovered and never probed, which is what separates it from a Filter, so it decides what exists rather than what is visible. Everything after it is scoped by it, including an Action fanning out across the Selection. The stake is measured rather than imagined, since `~/dev` holds 148 Repos and 161 Worktrees, so the gap between a named six-Repo Set and the implicit `all` is six rows against 309, and an Action touching six checkouts against one touching every checkout on the machine. This map's standing constraint is that anything automatic means the narrowest safe operation or none, and the rung the old behaviour fell through to, "the first declared Set", is not the narrowest. It is whichever Set happens to be first in the file. Arbitrariness is what disqualifies it: it is not a safe default but a coin toss wearing one's clothes.

[0001](0001-per-cell-provenance.md)'s founding rule decides the rest. An absent count must never render as a zero, because a zero is *plausible*, and plausibility is the whole defect. A Set name that resolves to nothing, rendered as a different Set, is that lie told about scope, and it is the least detectable instance of it in the program: by the design of record the active Set's name is on screen nowhere. [layout-and-provenance.md](../spec/layout-and-provenance.md)'s frame lists the table, the detail pane, the footer and the status row; [actions.md](../spec/actions.md)'s header priority is the entity count, run progress, the Filter's match count, the worktrees note and timing. [0014](0014-config-is-read-only-and-a-set-bounds-the-work.md) calls Sets the tab strip and no spec has yet built one, which is a separate question and separately ticketed as [#128](https://github.com/paulchiu/repon/issues/128).

The axis [config.md](../spec/config.md) already had could not decide this, which is why the ticket existed. "A flag is a thing typed moments ago and a file is a thing you have to go and fix" separates `--theme <missing>` from `theme = "missing"`, and it is right inside its class. It has no seat for `REPON_SET`, which is neither: a variable set in an rc file, or exported per-directory by direnv, was not typed moments ago and is not a file anyone is about to go and fix. Extending the axis by analogy would have put the environment on the lenient side, and that is backwards. A typo'd flag is at least suspected by the person who just typed it; a stale variable is suspected by nobody, and silently rescopes every launch until someone thinks to look. The blast-radius axis has a seat for all three and agrees with the older axis everywhere the older one reaches, so it replaces it as the general rule and keeps it as the tiebreak within the cosmetic class.

The reload precedent was cited for a case with none of its premises. `resolve_startup_set` followed `reload_active_set`'s graceful degrade, and `reload_config`'s own doc comment states why that grade is right there: the terminal is already claimed, so it is not the exit-before-the-terminal-is-claimed grade, and a session mid-work should not be torn down over a typo in a file it can go on using the previous, still-valid reading of. At startup no terminal is claimed, no session exists and there is no previous reading. Reload keeps its fallback and now keeps the reason rather than the analogy: the user is at the keyboard, is told in the status bar, and the alternative is destroying work in flight.

The config path splits on who named it rather than on whether a file is there. A missing file at the default path is not an error and must stay that way, since zero config is a supported way to run Repon, one implicit `all` rooted at the working directory, and nobody named that path. A path given to `--config` is a different act: it states an intent to run on a particular configuration, and if that file cannot be read, presenting the compiled-in defaults as though it had loaded misrepresents what Repon is running on. That is the same substitution one level further out, not the wrong Set but the wrong everything, including the Sets. `REPON_CONFIG` names a directory rather than a file, so the rule inside it is that the named thing must exist while what it contains may be absent: a `REPON_CONFIG` pointing at no directory is a typo and exits, and an existing directory holding no `config.toml` is zero config and runs, because the thing the user named was found and the state it is in is a legitimate one.

Exiting is not a trap, and the messages are what keep it from becoming one. Each names its own source, the flag or the variable and its value, because the user's next question after "that Set does not exist" is "then where is that name coming from". Each points at `repon sets`, which prints every Set's name, roots and match count, needs no terminal and is not scoped by the selection that just failed. `--set` beats `REPON_SET`, so an inherited variable is always one flag away from being overridden and can never leave Repon unlaunchable. And every one of these exits happens before the terminal is claimed, which [config.md](../spec/config.md#reading-and-failing) already makes load-bearing for exactly this reason: a message printed after the alternate screen is claimed goes nowhere anyone will read.

Two things follow for the implementation. `resolve_startup_set` stops being infallible and returns a failure the caller reports and exits on, which is the shape `document::load` and `keys::merge` already have for their own startup grades. And the four failure grades in [config.md](../spec/config.md#reading-and-failing) gain their fifth distinction inside the first row rather than a fifth row, since "missing file" was never one case: it is the default path, where absence is the normal state, and a named path, where absence is a typo.
