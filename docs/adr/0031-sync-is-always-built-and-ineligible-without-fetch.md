# `sync` is always built, and ineligible without `fetch`

The built-in `sync` action exists in every build of Repon. A `cargo install` with no `--features fetch` shows the same four entries in the Action palette a `--features fetch` install does, `ignore`, `unignore`, `delete` and `sync`; the difference is that `sync` refuses every row on the plain build, naming why, rather than being missing from the list.

The alternative was to gate the variant itself: compile `sync` into `Operation` only under `repon`'s own `fetch` feature, so a plain install never sees it at all. That mirrors how the mechanism it calls, `repon-core`'s `auto_update` module, is already gated, and it would have been the smaller diff. It is refused here for the same reason [0023](0023-an-unbuilt-binding-is-not-advertised-and-an-unavailable-one-answers-on-press.md) refuses an unbuilt keybinding for anything but a genuinely compile-time absence: a `[[action]]` name collision check, a help overlay, a spec table, and now a palette listing, all read `crate::management::OPERATIONS` as the one list of built-in names, and a name that comes and goes with a cargo feature makes every one of those four surfaces a claim that is only sometimes true. `Operation::eligibility` already matches exhaustively on `(Operation, Kind)`, which is the property this decision means to keep rather than work around: a `#[cfg(feature = "fetch")]` fourth variant would have needed a second, feature-gated `Operation` shape, or a `cfg`-only arm inside an otherwise unconditional match, either of which reopens exactly the "hand enumeration instead of an exhaustive match" defect the rest of this module was written to avoid.

0023 is about a keybinding, not a cargo feature, and the two are not identical: an unbuilt binding's chord is still reserved and still enforced by the load-time collision check whether or not the binding fires, where a variant excluded from the enum by `cfg` cannot be matched, named or reserved by anything, on that build, at all. So this is its own decision rather than an appeal to that one, and it reaches the opposite structural answer for a reason 0023 itself names: "a user who can see it and is told why it will not run learns more than a user who cannot see it at all." A plain-build user typing `s` in the ad hoc field, or reading `repon.log` after a keystroke that did nothing, is exactly who that sentence is about. `fetch.enabled = true` on a plain build already takes this shape, accepted and warned about rather than rejected at load ([config.md](../spec/config.md), `Warning::FetchEnabledButNotBuilt`); `sync` visible-and-refused is the same answer at the palette instead of the config file.

The refusal is a gate refusal, `Eligibility::Refused(Refusal::FetchNotBuilt)`, checked in `Operation::eligibility` ahead of every Kind: on a plain build every row refuses this way regardless of whether it is a Repo, a Worktree or a Submodule, because the fast-forward mechanism does not exist to call on a build like that, and no Kind changes that fact. Its message names the same install command `Warning::FetchEnabledButNotBuilt` already does, `cargo install --git https://github.com/paulchiu/repon --locked --features fetch repon`, read from [releasing.md](../spec/releasing.md) at test time in both places rather than typed twice: one way to say "your build cannot do this" was chosen once and reused, not reinvented for a second surface that says the identical thing.

A Worktree and a Submodule are refused on every build, `fetch` or not, for an unrelated reason each carries regardless of the feature: `repon-core`'s `repos_eligible_for_auto_update_attempt` acts on a Repo's own row only, a Worktree sharing that Repo's common dir is listed and never operated on the same way the periodic fetch's own common-dir filter already treats one, and a Submodule tracks a pinned commit rather than a branch, so there is nothing for a fast-forward to move. Both are named with a reason in the confirm gate rather than silently doing nothing, the same standing rule every other refusal in this module already keeps.

`repon_core::Core::attempt_auto_update` is the seam the feature boundary actually sits at, not `management::Operation`. It is a plain method on `Core`, present on every build, with two bodies behind `#[cfg(feature = "fetch")]`: one delegating to `auto_update::attempt`, the existing fast-forward with its own five eligibility rules, unchanged; the other an `unreachable!`, because `sync`'s own eligibility check above refuses every row before a run reaches it on a build without the feature. `AutoUpdateAttempt`, its return type, is plain data present on every build too, the same "bounding data always present, mechanism gated" split `FetchSpec` and `AutoUpdateSpec` already use. Nothing about the auto-update's own five rules, clean, behind, not ahead, tracking an upstream, is reimplemented for this: the built-in calls the existing function by hand, on demand, rather than only by the periodic fetch's timer.

## Consequences

- `crate::management::OPERATIONS` carries four entries unconditionally. `Operation::eligibility` matches exhaustively on `(Operation, Kind)`, and `sync`'s own build-time refusal is one guarded arm ahead of the per-Kind ones, not a second enum shape.
- `Core::attempt_auto_update` is the one production reader of `auto_update::Outcome` and `auto_update::Ineligible` outside that module's own tests. It reuses their five rules rather than reimplementing them, proven by `repon-core`'s own `attempt_auto_update` test module, which asserts the wrapper answers exactly what `auto_update::attempt` would for the same fixture, for every eligible and ineligible condition.
- The `FetchNotBuilt` refusal's message and `Warning::FetchEnabledButNotBuilt`'s are both read from [releasing.md](../spec/releasing.md)'s own install line at test time, so the two cannot drift into saying two different things about the same missing feature.
- A future built-in that needs the same treatment (compiled always, refused by feature rather than absent) reopens this ADR for its own reasoning rather than assuming the answer carries over silently; the two structural refusals here, the surfaces-must-agree argument and 0023's "seen and refused teaches more," are what would need to hold again.
