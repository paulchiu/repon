# The Filter language is total and three-valued

A Filter is a total, three-valued predicate. Total: every string a user can type is a valid Filter, so there is no parse failure, no error to report, and no fifth grade added to [0014](0014-config-is-read-only-and-a-set-bounds-the-work.md)'s four. Three-valued: a term is true, false or unprovable on a row, and an unsettled cell answers neither the term nor its negation, so [0001](0001-per-cell-provenance.md)'s rule that an absent value is never a zero reaches the query language instead of stopping at the renderer. Those two are the same instinct pointed at input and at data, and the vocabulary, the namespace, the refusals and the input line in [filter.md](../spec/filter.md) all fall out of them.

Totality is bought by making a colon the namespace. A term splits at its first `:`; if the text before it is a known key it is a keyed term, and otherwise the whole term is a substring match on the display name. So a bare word is **always** a name, in every position, forever, and the collision the ticket was opened on — a repository genuinely called `failed` against a reserved term `failed` — cannot occur and needs no escaping rule. The alternative, a bare reserved vocabulary, makes the reserved list a permanent tax: adding `dirty` as a term in a later version retroactively changes what a Filter someone already typed and stored means, which is a migration nobody would think to write. The same split makes every malformed input land somewhere legal. `kimd:repo` is a name search for that literal text, `is:banana` is a known key with an unrecognised value, `is:` is a known key with an empty value, and `:` is a name search; all four match nothing, none is an error, and the header's match count is the entire report. That is what makes a per-keystroke Filter viable at all, because a half-typed term is the normal state of the line rather than an exception to it.

Totality leaves one real gap, and the fix is one character. An unrecognised term and a genuine zero-match look identical in the list, and the match count cannot tell them apart, since both say zero. So the Filter line carries a fixed one-character advisory slot at its right end: `?` when any term is unrecognised, a space otherwise, with the offending term taking the `warn` role in place so the user can see which one. `?` is reused rather than spent: it means "Repon has no answer for this" in the gutter and "Repon has no meaning for this" in the Filter line, one level up on the same idea. A warning sign was measured and refused on [0020](0020-the-ascii-glyph-set-is-vetted-over-the-row-interior.md)'s own terms: `⚠` (U+26A0) is in 1 of the 5 macOS system monospace faces (Menlo has it; SF Mono, Monaco, Courier and PT Mono do not) against `?` in 5 of 5, and the width is worse than the coverage, since bare `⚠` measures one column while `⚠️` with U+FE0F measures two. Two spellings of one icon differing in width by an invisible codepoint is the class of defect that corrupts every column to its right, the emoji form renders only by falling back to a proportional colour face inside a monospace grid, and there is no ASCII counterpart for the `glyphs = "ascii"` set.

Three-valued matching is 0001 arriving where it was always headed. A term reads a cell, and a cell that has not settled has no value to read, so the term is unprovable rather than false; negation maps unprovable to unprovable, and only true matches. Without that rule, `-state:merged` would be plain set complement and would hand back three hundred rows Repon has not finished reading, indistinguishable from three hundred it read and confirmed — which is the absent count becoming a zero, one abstraction up. `NotApplicable` splits away from the other three and is decidable: it means the question does not apply to this row, which settles "is this Merged?" at no, where `Unknown` means the question applies and Repon does not know. So `-state:merged` includes every Repo row and excludes every row still loading. Two costs are accepted rather than hidden. A term and its negation do not partition the list, which will surprise someone exactly once. And at startup every cell is Loading, so a cell-based Filter matches nothing and fills in as probes land, while `name:`, `path:` and `kind:` work on the first frame; the rows a term cannot speak for stay reachable through `row:loading`, `row:unknown` and `row:failed`, which is why that key exists.

Deciding the vocabulary found the same defect twice, in two different words, and both fixes come from one rule: **when a word covers two things the model separates, each gets a key mirroring what is computed.** "Failed" was three producers wearing one glyph — a Failed probe cell, a failed derivation and a failed Action step all render `!` — while `n` and `N` navigate only the third, so the word already named two different sets in two settled specs. It becomes `row:` mirroring `RowSummary` exactly, so `row:failed` and "every row showing `!`" are one set by construction and cannot drift, and `action:` mirroring the receipt, so `action:failed` and the `n`/`N` walk select the identical rows. "Behind" was the same shape: [layout-and-provenance.md](../spec/layout-and-provenance.md) states that `sync` and `base` are different measurements that fail independently and coincide on one row, so `is:behind` had two referents; it becomes `sync:` with one value per rendered glyph and `base:` beside it, and divergence falls out for free as `sync:ahead sync:behind`. That the rule fired twice, on words chosen independently in two earlier specs, is the argument for the rule.

A Filter flattens: a matching row shows on its own and a non-matching parent is never dragged in as context. This preserves an identity the rest of the design already leans on, that the visible rows, the matching rows, the header's match count and the set `a` selects are all the same set. [0016](0016-one-binding-table-feeds-every-surface.md) refuses to let an Action act on visible rows precisely because clearing a Filter would silently widen its reach, and a context parent is a row `a` would sweep into an Action the user never matched. The cost is that the indent and the `└` marker vanish under a Filter and a filtered Worktree row does not say which Repo it belongs to, which is the cost [0019](0019-a-detached-head-is-a-shape-of-head-not-a-worktree-state.md) already accepts for a detached row's `branch` cell. Where a Filter hides a row that is already selected, the Selection is untouched and the confirm gate names the difference — `run "reinstall" on 12 repos? (3 not visible)` — on the pattern [0014](0014-config-is-read-only-and-a-set-bounds-the-work.md) set with `worktrees: 161 (preference off)`: a count that disagrees with the screen is named rather than hidden.

The refusals, each with the trigger that would reopen it. Fuzzy matching: refused because the list cannot reorder, so a fuzzy match can never show why a row matched, and because it makes a match count that [0018](0018-an-action-is-a-fanout-of-pty-backed-steps.md) puts on screen under a contract untrustworthy; reopen it if the list ever gains a ranked mode. Comparison operators such as `dirty:>5`: refused because the threshold question is answered by `is:dirty` plus the column already beside you, because `>` is a shell metacharacter that would make every `--filter` need quoting, and because `dirty:>` is a legal prefix meaning nothing mid-keystroke; `dirty:5` is not legal today, so they remain addable without changing any existing Filter's meaning. A boolean expression grammar with parentheses: refused as composition nobody asked for at the cost of a parser whose failure modes need a report designed for them. Quoting: refused because an unterminated quote is a parse failure and would undo totality, and the need is nearly absent — git's `check-ref-format` forbids a space in a ref name, and 0 of the 309 git entities under the design machine's `~/dev` have a space in theirs. Repeated keys that OR: refused because composition would then depend on whether two keys coincide, so `is:dirty is:ahead` would OR while `is:dirty kind:repo` ANDs, one keystroke apart with nothing on screen to say which you got; a comma inside one value does the job explicitly. `is:selected`: refused because it loops the Filter and the Selection through `a`, and "a Filter never mutates the Selection" is worth keeping obviously true. Live-data completion: refused for v1 because it needs a per-keystroke scan over a snapshot a refresh can replace underneath it, so the list would reorder for reasons unrelated to typing; it adds no syntax and stays a clean later addition. A `reason:` key matching rendered error text: refused because it would make the language depend on error wording, and because `ProbeError`'s variants are unspecified, so writing it would silently decide a type [0015](0015-the-core-owns-the-table.md) gives to the core API spec; `unknown:` exists instead, because `enum Unknown` is the one closed reason set in the design.

Four sentences elsewhere are corrected by this decision. [head.md](../spec/head.md) promises a `detached` Filter term, which is `head:detached`. [actions.md](../spec/actions.md) promises a `failed` Filter term, which is `action:failed` for the receipt and `row:failed` for the fold, two different sets. [refresh.md](../spec/refresh.md) lists Unknown's reasons as "timed out, no upstream, no default branch, no remote", but 0019 removed `NoUpstream` and `NoRemote` and the set is closed at two. [0016](0016-one-binding-table-feeds-every-surface.md)'s `Ctrl+J` and `Ctrl+K` are no longer "palettes only", since a completion list gives the Filter line a highlight for the first time; `Tab` accepts it and `Enter` always commits, never accepts, because a key whose effect depends on a widget the user is not looking at is a key whose effect they cannot predict. One open question is half discharged: [0010](0010-provenance-renders-as-a-row-gutter-and-blank-cells.md) and layout-and-provenance.md leave open whether a Vanished row wants a Filter of its own, and it does, as `presence:vanished`, because a Stale row is one Repon will refresh and a Vanished row is one it cannot; the gutter mark for such a row stays open and stays with that spec.

## Amended by #412

The `└` marker does not vanish under a Filter after all. A child row whose Repo did not survive the Filter now draws an orphan marker, `┆` under `full` and `:` under `ascii`, in the same column the connector would otherwise take, rather than leaving the column blank; the indent stays either way, so a filtered Worktree row is still marked as a child. The cost this ADR records narrows to what stands: a filtered Worktree row still does not say which Repo it belongs to, and the detail pane is still the only discriminator, but the marker column itself is never empty. See [#412](https://github.com/paulchiu/repon/issues/412).
