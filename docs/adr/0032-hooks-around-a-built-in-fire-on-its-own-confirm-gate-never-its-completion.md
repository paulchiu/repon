# Hooks around a built-in fire on its own confirm gate, never its completion

> **Retired.** This record is kept for its history. Its product intent now lives in
> [product.md](../product.md) and its implementation detail in
> [repo-management.md](../spec/repo-management.md) and [config.md](../spec/config.md). Nothing below is maintained.

`sync` gains two hooks, `before_sync` and `after_sync`, each naming one declared `[[action]]` in the identical `Option<String>` shape and fire-time resolution `on_refresh` already uses: the active Set's own value, then the top-level key of the same name, then no hook, re-resolved fresh rather than cached. [config.md](../spec/config.md)'s "Sets" and [repo-management.md](../spec/repo-management.md)'s "Hooks around sync" carry the field table and the behaviour; this decision is about the one thing copying that shape does not settle by itself, which trigger fires them.

[0029](0029-an-on-refresh-action-runs-on-the-refresh-key-alone.md) already decided this question once, for `on_refresh`, and restricted it to a keystroke the user aimed, never a timer and never a Generation starting. Its second reason is mechanical rather than a judgement call: an Action finishing already starts a fresh Generation, so a hook that itself fired on a Generation starting would retrigger on its own completion, forever, one child per Repo per cycle, with no debounce that makes the composition of those two settled rules safe. A built-in inherits that trap exactly as an Action does, because [refresh.md](../spec/refresh.md) fixes that a finished fetch starts a normal Generation the same way a finished Action does, and nothing about a built-in's own completion is structurally different: were `sync` finishing itself the signal a hook listened for, the identical loop would follow.

It does not follow that 0029's answer merely carries over unread, because a built-in's completion is not shaped like an Action's. `crates/repon/src/app.rs`'s own `run_management` says so directly: running a Management operation starts no Generation of its own. `record_own_work` writes each row's receipt straight onto the table, and the reload that follows re-reads config through the same path `Action::ReloadConfig` runs, re-applying `exclude` live where it changed; neither dispatches a fresh Generation, and no rebuilt `Core` restarts discovery unless the Set spec itself moved. So the premise the loop needs, "the built-in's own completion starts a Generation," is false for a Management operation the way it is true for an Action's fan-out finishing. A hook that fired on `sync`'s own completion would not be listening for a Generation at all; there is not one to listen for.

That does not make firing on completion the right answer anyway. `sync` is reached from exactly one place, `y` over the confirm gate `crates/repon/src/app.rs`'s `handle_action_palette_key` builds, the identical shape `on_refresh`'s own two call sites take on `r` and `R`: a keystroke the user aimed at running this built-in, once, right now. Firing the hooks from that same keystroke, rather than from whatever `sync` itself finishes doing, keeps [0002](0002-repon-owns-the-outer-loop-only.md)'s reconciliation intact for the identical reason it already holds for `on_refresh`: 0002 governs what Repon decides to do unbidden, never what the user just asked for, and "the user pressed `y`" is the asked-for half of that line regardless of whether the thing that runs next is called before, during or after the built-in's own act. There is also nothing else to listen for on the built-in side: `run_management` is one function call, not a state machine with a completion event of its own to publish, so "fire on completion" and "fire from the keystroke that reached this function" name the same moment for a built-in in a way they never did for an Action's asynchronous fan-out.

`before_sync` and `after_sync` still differ from `on_refresh` in one respect this ADR settles rather than inherits: `on_refresh` fires an Action and never waits for it, watched only through the receipts it leaves and the Warning a failed step earns. A sync hook cannot take that shape, because `sync`'s own outcome for a row depends on whether its `before_sync` passed: a failing pre-hook must stop the fast-forward from being attempted at all, which nothing running off the calling thread can answer before `run_management` has to report what happened. So a sync hook runs through `repon_core::Core::run_action_for_entity_blocking`, the identical executor, PTY and environment contract every Action step already gets, but on the calling thread, one row at a time, blocking `run_management` until that row's hook finishes rather than handing the run off the way `Core::run_action`'s fan-out does. This is still fired from the one keystroke that reached `run_management`, never from a Generation or a timer, so the restriction this ADR is about holds regardless: only how the result is awaited changed, not what triggers the awaiting.

`after_sync` never undoes a fast-forward that already happened. A post-hook failing is reported alongside the row's own `Synced` outcome, `SyncedAfterHookFailed`, carrying both facts rather than losing either: the branch moved, and the hook did not finish clean. There is no rollback to attempt: the fast-forward is a ref update and a tree-diff write, already durable by the time `after_sync` runs, and treating a hook's own failure as a reason to fabricate an undo would invent a mechanism `sync` itself does not have.

The environment contract stays at its declared eight `REPON_` variables. A hook script belongs to the Set that names it, in the same config file the person who wrote the hook also wrote `before_sync` or `after_sync` into, so which Set is active when it fires is already known statically to whoever configured it; a top-level hook shared across several Sets has the identical gap `on_refresh`'s own top-level fallback has always had, accepted rather than closed since [#215](https://github.com/paulchiu/repon/issues/215) shipped. Adding `REPON_SET` to answer it would also collide in name with an unrelated fact [config.md](../spec/config.md)'s "Sets" already fixes: `REPON_SET` is the environment variable a user sets to select the active Set at startup, an input Repon reads, not an output it produces for a child's own environment. Reusing that name for the opposite direction, something Repon sets for a process it spawns, would make the same four characters mean two different things depending on which side of the process boundary reads them. A differently-named output variable would dodge the collision but still answer a need the concrete case driving this issue does not have: `~/bin/mrx-sync-repo.sh`, hung off one Set's own `after_sync`, already knows which Set it belongs to by construction. `environment.rs:427-461`'s closed-set test is therefore unchanged, and this paragraph is the deliberate decision the issue asked for rather than an oversight: a future issue that finds a concrete top-level-hook case needing it can widen the contract then, on its own evidence.

## Consequences

- `before_sync` and `after_sync` are read fresh from `self.document` and `self.active_set.name` inside `run_management`, the exact function `on_refresh`'s own two call sites are the sibling of; a source scan holds the hook's own `Core::run_action_for_entity_blocking` calls to that one function, the same way `on_refresh_trigger`'s scan region holds `fire_on_refresh_hook` to `r` and `R`.
- `Core::run_action_for_entity_blocking` is a second, synchronous way to run an Action's steps against one Entity, beside `Core::run_action`'s asynchronous fan-out. It shares `run_action_for_entity`, the identical per-step execution, so a hook and a configured `[[action]]` can never diverge in what a step means; it touches none of `run_action`'s own state (`action_running`, `action_control`), because a hook is a distinct concern from the one fan-out the palette tracks, and calling it never contends with an in-flight Action, since the confirm gate that reaches `run_management` cannot even be opened while one is running.
- `management::Outcome` gains `BeforeSyncHookFailed` and `SyncedAfterHookFailed`, both exhaustively handled everywhere `Outcome` already is, `own_work`, `Report::summary` and the receipt-grade test included, rather than folded into the existing `Failed` or `Synced` arms: a hook failing is a fact worth its own name, not a shape that already existed.
- `sync`'s own confirm-gate handler now blocks on each row's hooks in turn rather than returning the instant the fast-forward attempt does. The cost is bounded by how long the hook script itself takes, the same honest cost 0029's own Consequences already accepted for `r` gaining a slow unattended Action: the user's own declaration, not second-guessed here either.
- The environment contract stays at eight `REPON_` variables; `environment.rs:427-461`'s test is unchanged, and the reasoning above is what a later issue would need to unseat to add a ninth.
- A future built-in wanting the same treatment reopens this ADR for its own reasoning, the same posture [0031](0031-sync-is-always-built-and-ineligible-without-fetch.md)'s own Consequences take: the keystroke-not-completion argument here is `sync`'s confirm gate having a single call site with nothing left running once it returns, which a built-in with an asynchronous shape of its own would need to re-derive rather than assume.
