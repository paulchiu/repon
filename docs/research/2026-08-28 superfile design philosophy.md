# superfile design philosophy

Research notes on [yorukot/superfile](https://github.com/yorukot/superfile) as **design inspiration only** for a new Rust/ratatui multi-repo git TUI. superfile is written in Go with [Bubble Tea](https://github.com/charmbracelet/bubbletea)/Lip Gloss; nothing here is a code source, only a source of visual and interaction ideas. Every claim below is cited to the exact page it came from. Sentences that are my own assessment rather than an observed fact are explicitly marked **Opinion:**.

Primary sources used: the [GitHub repo](https://github.com/yorukot/superfile) (README, LICENSE, source tree via the GitHub API), and the full documentation site at [superfile.dev](https://superfile.dev) (overview, getting‑started, configure, list, contribute, troubleshooting and changelog sections).

---

## What superfile is and what it optimises for

- superfile is a terminal file manager written in Go, built on the [Bubble Tea](https://github.com/charmbracelet/bubbletea) TUI framework, cross‑platform (Linux/macOS/Windows). Source: [superfile.dev/overview](https://superfile.dev/overview/).
- Its own GitHub repository description is simply **"Pretty fancy and modern terminal file manager"**, and its site meta‑description reads **"A fancy, modern terminal file manager. Complete your file operations with style."** Sources: [GitHub repo metadata](https://github.com/yorukot/superfile), [superfile.dev](https://superfile.dev/) (page `<meta>` tags).
- The docs state the founding motivation directly: *"Before creating superfile, I tried a lot of terminal file managers, but I was often disappointed by their UI design. So, I built superfile with a primary focus on delivering a refined, user-friendly interface."* Source: [superfile.dev/overview](https://superfile.dev/overview/).
- Crucially, the project is explicit about **what it is not optimising for**. Verbatim from the docs: *"superfile is sleek and visually appealing, making it a great choice for lightweight file or directory tasks. While it may not be as feature-packed as some other terminal file managers, it excels in usability and design. If you're looking for a full-featured file manager, I'd recommend tools like [Yazi](https://github.com/sxyazi/yazi) or others."* Source: [superfile.dev/overview](https://superfile.dev/overview/).
- **Opinion:** this is the single most importable idea from superfile; it picks a narrow lane (polish and clarity for everyday file operations) and consciously cedes the "does everything" lane to a competitor, rather than trying to out-feature it. A multi-repo git TUI has the same fork in the road (a lightweight, good-looking daily-driver vs. a Lazygit/Magit-style kitchen sink), and superfile's answer is a reasonable one to borrow.
- As of this research the repo has ~22.9k GitHub stars, MIT-licensed, with topics `bubbletea, cli, file-manager, terminal-app, tui`. Source: [GitHub repo metadata](https://github.com/yorukot/superfile).

## The visual language (panels, borders, rounded corners, sidebar, footer, file preview, spinner/progress, colour usage)

Observed directly from the README's demo screenshot (downloaded from [website/src/assets/demo.png](https://raw.githubusercontent.com/yorukot/superfile/main/website/src/assets/demo.png), linked from the [README](https://github.com/yorukot/superfile)) and cross-checked against the theme/config docs:

- **Everything lives in bordered boxes.** Every region (sidebar, each file panel, the code/file preview pane, the processes panel, the metadata panel, the clipboard panel) is drawn as its own rounded-corner box on a shared dark background, tiled edge-to-edge with no gaps. Source: demo screenshot; corner glyphs confirmed as `╭ ╮ ╰ ╯` in the shipped default theme's config. Source: [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/) (default `config.toml`).
- **Borders are literally just configurable characters**, not a "rounded corners" boolean. The default config sets `border_top`, `border_bottom`, `border_left`, `border_right` and all four corner and two "middle" (T-junction/divider) glyphs individually; the docs show a second, ready-made "heavy line" alternative (`━ ┃ ┏ ┓ ┗ ┛ ┣ ┫`), and note a single space character produces a borderless look. Source: [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/) ("Border style" section).
- **Focus is communicated purely by border colour**, not by weight, shadow, or a focus glyph. In the screenshot, the sidebar (currently focused) has a warm pink/red border while the three file panels around it have cool cyan/lavender borders. This maps exactly onto the theme file's `sidebar_border_active` (`#f38ba8`, pink) vs. `sidebar_border` / `file_panel_border` (`#6c7086`/`#1e1e2e`, muted grey) vs. `file_panel_border_active` (`#b4befe`, lavender) keys. Source: demo screenshot; theme keys from [superfile.dev/configure/custom-theme](https://superfile.dev/configure/custom-theme/) (default `catppuccin-mocha.toml`).
- **Panel titles are inline in the top border**, not a separate title bar row, e.g. a file panel's border literally spells out `📁 …ocuments/code/superfile` on its top edge, truncated with an ellipsis when the path is long, and the sidebar's top border reads `📁 Super File` in a two-colour blue→purple gradient. This gradient is a first-class theme key (`gradient_color`, currently limited to two colours). Source: demo screenshot; `gradient_color` key from [superfile.dev/configure/custom-theme](https://superfile.dev/configure/custom-theme/).
- **The bottom border doubles as a compact status line for that panel**, e.g. a file panel's bottom border shows `Browser` or `Select` (current mode) and a `5/25` cursor/total-item counter, right-aligned inside the border itself rather than in a separate footer row. This is togglable via `show_panel_footer_info`. Sources: demo screenshot; tutorial text *"Your current mode is displayed in the lower-right corner of the file panel (Select or Browser)"*, [superfile.dev/getting-started/tutorial](https://superfile.dev/getting-started/tutorial/); config key `show_panel_footer_info`, [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/).
- **Layout is a fixed grid, not floating windows**: a left sidebar column, a row of one-or-more file panels taking the remaining width (optionally an adjacent preview pane), and a bottom strip split into three boxes (Processes / Metadata / Clipboard). Source: demo screenshot; panel names confirmed in [superfile.dev/getting-started/tutorial](https://superfile.dev/getting-started/tutorial/) and again in the contribution guide's theme-screenshot checklist, [superfile.dev/contribute/how-to-contribute](https://superfile.dev/contribute/how-to-contribute/).
- **Search/filter is inline in the panel, not a separate bar.** The file panel's own top area shows a persistent `🔍 (/) Type something` prompt row. Source: demo screenshot.
- **Progress and status use icon + coloured bar + percentage, all inline in the Processes panel**: a clock glyph next to an in-flight copy at `18%` with a partially-filled gradient bar, and a green checkmark next to two completed operations at `100%` with a fully-filled bar. There is no separate spinner animation region, the icon itself is the state indicator (pending vs. done), and the bar's fill is the "spinner." Source: demo screenshot.
- **Colour usage is theme-driven and semantic**, not decorative: theme files define a `cursor` colour, plus named semantic colours `correct` (success/confirm, green in the default theme), `error` (red), `hint` (cyan), and `cancel` (used for destructive/cancel actions in modals). Source: [superfile.dev/configure/custom-theme](https://superfile.dev/configure/custom-theme/) ("Special" section of the default theme).
- **A dedicated Nerd Font icon set** is used throughout (folder icons, per-filetype icons, sidebar section icons, checkbox icons in selection mode), with an explicit opt-out (`nerdfont = false`) and troubleshooting guidance for users without a patched font. Sources: [superfile.dev/getting-started/installation](https://superfile.dev/getting-started/installation/) ("Before install", Nerd Font requirement callout), [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/) (`nerdfont`, `show_select_icons` keys), [superfile.dev/troubleshooting](https://superfile.dev/troubleshooting/).
- Inline image preview is supported via terminal graphics protocols (Kitty protocol on kitty/WezTerm/Ghostty) with a graceful fallback to ANSI colour-block rendering everywhere else, detected at runtime by probing the terminal with the `\x1b[16t` cell-size query rather than trusting `$TERM` alone. Source: [superfile.dev/getting-started/image-preview](https://superfile.dev/getting-started/image-preview/).

## Theming system (how themes are defined, what is themeable, how many ship, hot reload)

- Themes are individual **TOML files**, one file per theme, in a dedicated theme directory (`~/.config/superfile/theme` on Linux, equivalents on macOS/Windows), selected by name via a single `theme = "…"` key in the main config. Sources: [superfile.dev/configure/config-file-path](https://superfile.dev/configure/config-file-path/) ("Theme directory"), [superfile.dev/configure/custom-theme](https://superfile.dev/configure/custom-theme/).
- **20 themes ship by default** as of this research (0x96f, Ayu Dark, Blood, Catppuccin Frappé/Latte/Macchiato/Mocha, Dracula, Everforest Dark Medium/Hard, Gruvbox, Gruvbox Dark Hard, Hacks, Kaolin, Monokai, Nord, OneDark, Poimandres, Rosé Pine, Sugarplum, Tokyonight), each crediting a "ported by" contributor and an "original author" (mostly established editor/terminal colour schemes). Source: [superfile.dev/list/theme-list](https://superfile.dev/list/theme-list/). This is also confirmed directly in the source tree (`src/superfile_config/theme/*.toml`, 20 files), via the GitHub API.
- A theme file is organised into clear sections: **code syntax highlighting** (a [chroma](https://github.com/alecthomas/chroma/blob/master/styles) style name, reused for built-in code preview), **base colours** (full-screen fg/bg, the two-stop `gradient_color`, a `directory_icon_color` fallback), then **per-panel fg/bg/border/border-active** for the file panel, footer, sidebar (plus a `sidebar_divider` colour and `sidebar_item_selected_fg/bg`), **modals** (fg/bg/border-active, plus distinct `modal_cancel_fg/bg` and `modal_confirm_fg/bg`, i.e. cancel/confirm buttons are themed as if they were separate coloured chips), a **help menu** section (hotkey colour, title colour), and a **"special"** section for the semantic `cursor/correct/error/hint/cancel` colours. Source: [superfile.dev/configure/custom-theme](https://superfile.dev/configure/custom-theme/) (full default `catppuccin-mocha.toml` listing).
- Creating a theme is a copy-and-edit workflow: copy an existing theme's TOML into the theme directory under a new name, point `theme =` at it, and there is an explicit invitation to upstream it as a PR. Source: [superfile.dev/configure/custom-theme](https://superfile.dev/configure/custom-theme/); contribution requirements (screenshots of full view, sidebar-focused, process-panel-focused, help menu, new-file popup, image preview, and shell success/failure) are spelled out in [superfile.dev/contribute/how-to-contribute](https://superfile.dev/contribute/how-to-contribute/).
- **Hot reload:** no hot-reload of theme or config changes is documented anywhere in the docs I read. The plugin-enabling guide explicitly instructs *"Restart superfile - Changes require restarting the application"* after editing config, Source: [superfile.dev/configure/enable-plugin](https://superfile.dev/configure/enable-plugin/). **Opinion:** given config/theme loading is described only at startup (`LoadAllDefaultConfig()`, discussed below) and no changelog entry or doc mentions live-reloading, I treat "no hot reload" as the working assumption rather than a hard-confirmed negative; I did not find an explicit "themes require restart" sentence, only the plugin one.
- The changelog shows the theming system is actively curated over time: themes were added one at a time by different community contributors across releases (e.g. Everforest Dark Hard in v1.3.2, Gruvbox Dark Hard in v1.3.0, Monokai in v1.2.1, 0x96f in v1.3.2), and directory-icon colour became themeable only in v1.2.1. Source: [superfile.dev/changelog](https://superfile.dev/changelog/).
- Invalid themes are guarded against: a changelog fix explicitly reads *"Prevent crash due to invalid theme"* (v1.6.0). Source: [superfile.dev/changelog](https://superfile.dev/changelog/).

## Layout model (panel model, how many panels, how they resize, modal/prompt/overlay behaviour)

- The base layout is **five persistent panels**: sidebar, file panel(s), processes, metadata, clipboard, plus a command-execution bar that opens as an overlay rather than occupying permanent space. Source: [superfile.dev/getting-started/tutorial](https://superfile.dev/getting-started/tutorial/) ("Once superfile is running, it displays five panels: sidebar / file / processes / metadata / clipboard / command execution bar").
- **File panels are the one truly multi-instance, splittable region.** A user can open more file panels side-by-side (`n` = new panel, `N`/`split` = split the current panel at its own path), close one (`w`), and cycle focus between them (`tab`/`L` forward, `shift+left`/`H` back). The sidebar, preview, processes, metadata and clipboard panels are singletons. Source: [superfile.dev/getting-started/tutorial](https://superfile.dev/getting-started/tutorial/), hotkey names confirmed in [superfile.dev/list/hotkey-list](https://superfile.dev/list/hotkey-list/).
- **Toggling, not resizing by dragging, is the primary layout control.** Users show/hide the whole footer strip (`F`), show/hide the file preview pane (`f`), and the sidebar can be switched off entirely by setting its width config to `0`. There's no evidence of mouse-drag pane resizing in the docs, sizes are set via numeric config (`sidebar_width` 5–20, `file_preview_width` as a terminal-width divisor 2–10, `file_panel_name_percent` 25–100 for column allocation) or via terminal window resize, which the renderer recomputes against. Sources: [superfile.dev/list/hotkey-list](https://superfile.dev/list/hotkey-list/) (`toggle_footer`, `toggle_file_preview_panel`), [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/) (`sidebar_width`, `file_preview_width`, `file_panel_name_percent`).
- **Sidebar composition is itself configurable**, not just its width: `sidebar_sections = ["home", "pinned", "disks"]` controls which sections appear and in what order, and can omit sections entirely. Source: [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/) (`sidebar_sections`; added per changelog v1.6.0, [superfile.dev/changelog](https://superfile.dev/changelog/)).
- **Modals are centred overlays that dim nothing but visually sit above the still-visible grid.** A changelog entry frames this directly as a deliberate change: *"Update all modal, make other panel still show on background"* (v1.1.2). Source: [superfile.dev/changelog](https://superfile.dev/changelog/). Implementation-wise, a modal (e.g. the delete/quit confirmation "notify" model) renders as a fixed-size bordered box with title + body + an input-hint line (`Confirm`/`Cancel` or `Okay`), independent of the underlying panel grid, confirmed by reading the `notify` package's `Render()` method, source: [`src/internal/ui/notify/model.go`](https://github.com/yorukot/superfile/blob/main/src/internal/ui/notify/model.go).
- **The command/prompt bar is a separate overlay mode, not a panel**, with two distinct sub-modes: shell mode (`:`, runs any raw shell command in the current panel's directory, no stdout capture, just an exit code) and "SPF mode" (`>`, a small first-party command language: `split`, `open <PATH>`, `cd <PATH>`, with `${VAR}`, `$(cmd)` and `~` expansion). Source: [superfile.dev/getting-started/tutorial](https://superfile.dev/getting-started/tutorial/) ("SPF Prompt" section).
- Rendering internals reinforce the "layout is computed, not free-floating" model: a dedicated `rendering` package owns border configuration (title, footer info items, section dividers, per-corner glyphs) as pure data (`BorderConfig`) fed into a Lip Gloss-based renderer, and the project keeps whole PR series dedicated to "Dimension validations" / "layout validation and sidebar dimension fixes" / "Layout fixes with full end-to-end tests" (v1.5.0). Sources: [`src/internal/ui/rendering/border.go`](https://github.com/yorukot/superfile/blob/main/src/internal/ui/rendering/border.go); changelog v1.5.0 entries, [superfile.dev/changelog](https://superfile.dev/changelog/).

## Interaction model (modes, keybindings philosophy, vim-ness, discoverability, the help surface)

- There is an explicit **Browser mode vs. Selection mode** split per file panel (toggled with `v`), described in the docs as directly analogous to Vim's visual mode: *"If you are familiar with Vim, selection mode is similar to Vim's visual mode."* Bulk operations (copy/cut/delete) and shift-based range-select (`shift+up/down`, `J`/`K`) only work in Selection mode; the current mode is always visible in the panel's own bottom-right corner. Source: [superfile.dev/getting-started/tutorial](https://superfile.dev/getting-started/tutorial/) ("Selection mode").
- **The default keymap has a stated design rule**, quoted verbatim from the hotkeys doc: *"superfile default hotkeys design concept: All hotkeys that will change to files use ctrl+key (As long as you don't press ctrl your files will always be safe). Non-control file classes use the first letters of words as hotkeys."* Source: [superfile.dev/configure/custom-hotkeys](https://superfile.dev/configure/custom-hotkeys/). In practice: destructive/mutating actions are gated behind `Ctrl` (`ctrl+c/x/v/d/n/r/a/e/p`), while navigation and non-destructive toggles use bare mnemonic letters (`s` sidebar, `p` process bar, `m` metadata, `o` sort, `f` preview, `z` zoxide, `.` dotfiles).
- **superfile is explicitly *not* vim-first by default**, and says so with self-deprecating honesty: *"If you are a vim/nvim user please change your default hotkeys config to vim version!"* (README) and *"If you are a vim user, the default hotkeys may make you hate superfile."* (hotkeys doc). Sources: [README](https://github.com/yorukot/superfile) ("Hotkeys" section warning callout), [superfile.dev/configure/custom-hotkeys](https://superfile.dev/configure/custom-hotkeys/).
- Instead, vim-ness is offered as a **complete, maintained, swappable alternate keymap** (`vimHotkeys.toml`, credited to a named community maintainer in its header comment) rather than a partial vim-motion overlay, `hjkl`-ish navigation, `yxpd` for copy/cut/paste/delete, `-` for parent dir, etc., shipped as a second first-class file alongside the default. Source: [superfile.dev/configure/custom-hotkeys](https://superfile.dev/configure/custom-hotkeys/) (full `vimHotkeys.toml` listing).
- **Every action is a named symbolic key** (`confirm`, `list_down`, `toggle_file_preview_panel`, …) bound to an array of 1–2 physical keys in TOML, split into four scopes the docs label explicitly: *Global hotkeys*, *Typing hotkeys* (override everything, used while a text field is focused), and *Mode-Specific Hotkeys* (Normal-mode-only and Selection-mode-only actions that are allowed to collide with each other but not with globals). Source: [superfile.dev/configure/custom-hotkeys](https://superfile.dev/configure/custom-hotkeys/) (section headers and comments in the shipped `hotkeys.toml`).
- A small set of raw key combinations is reserved and explicitly disallowed from rebinding because they collide with terminal control codes (`Ctrl+M`≡Enter, `Ctrl+I`≡Tab, `Ctrl+?`/`Ctrl+[`≡Delete/Backspace). Source: [superfile.dev/configure/custom-hotkeys](https://superfile.dev/configure/custom-hotkeys/) (caution callout).
- **Discoverability has a dedicated, always-available surface**: pressing `?` opens a help menu listing hotkeys, and that help menu itself grew a search box (*"Add search functionality to help menu"*, v1.4.0). Sources: [superfile.dev/list/hotkey-list](https://superfile.dev/list/hotkey-list/) (`open_help_menu`), changelog v1.4.0, [superfile.dev/changelog](https://superfile.dev/changelog/).
- Additional discoverability details: the footer/border area itself surfaces state (current mode, cursor position, sort type) at all times rather than requiring the user to open a menu to know where they are, per the "visual language" section above; and there is a first-party fuzzy directory jumper (`z` opens a zoxide-backed modal with live search and arrow-key navigation, an explicit opt-in plugin) rather than requiring users to memorise paths. Source: [superfile.dev/list/plugin-list](https://superfile.dev/list/plugin-list/) (Zoxide plugin entry).
- **Opinion:** the two-keymap-files approach (default + vim, both fully specified, swapped by pointing at a different file) is a cleaner solution than the more common "vim mode: on/off toggle" pattern, because it keeps both keymaps simple, complete, and independently readable rather than layering conditionals into one file.

## Configuration philosophy (file format, location, defaults, what is configurable vs opinionated)

- **Format: TOML**, three separate files (`config.toml` (behaviour + style), `hotkeys.toml` (keybindings), and one theme `.toml` per theme) all human-editable text, opened directly with `$EDITOR`. Sources: [superfile.dev/configure/config-file-path](https://superfile.dev/configure/config-file-path/), [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/).
- **Location: OS-idiomatic config directories** (`~/.config/superfile` on Linux, `~/Library/Application Support/superfile` on macOS, `%LOCALAPPDATA%/superfile` on Windows) with a discoverable `spf pl` command that prints every resolved path (config/theme/data/log), and CLI flags (`-c/--config-file`, `--hotkey-file`) to override the config location entirely. Source: [superfile.dev/configure/config-file-path](https://superfile.dev/configure/config-file-path/).
- **Defaults are shipped inside the binary and materialised on first run**: default config/hotkeys/theme TOML files live in the source tree under `src/superfile_config/` and are embedded into the compiled binary with Go's `embed.FS`, then written out to the user's config directory the first time superfile runs. Source: [superfile.dev/contribute/implementation-info](https://superfile.dev/contribute/implementation-info/) ("How default configuration files are packaged with app"), confirmed by directory listing at [`src/superfile_config/`](https://github.com/yorukot/superfile/tree/main/src/superfile_config) (GitHub API tree).
- **The docs draw a hard line between three tiers**: `Setting` (behaviour: editor, default sort, auto-update, page-scroll size, etc.), `Style` (appearance: theme name, code previewer engine, nerd font toggle, transparency, preview width, border glyphs, sidebar width/sections), and `Plugins` (opt-in integrations: `metadata`, `enable_md5_checksum`, `zoxide_support`, plus a free-form `[open_with]` extension-to-command map that must sit at the very end of the TOML file because of how TOML tables close). Source: [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/) (page structure and full annotated default `config.toml`).
- **Almost nothing is hard-coded as "the app's opinion" once you're past install**, even superficial things like the exact `¦`-style corner characters, the percentage split between filename and metadata columns, whether file sizes are SI or IEC, and whether sort is case-sensitive are named config keys with documented defaults, not baked-in constants. Source: [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/) (full key list). **Opinion:** the project's actual opinion shows up not in what's configurable but in what ships as the *default*, Catppuccin Mocha theme, rounded borders, nerd-font icons on, ctrl-gated destructive actions, while nearly everything remains a one-line override away from that default.
- Missing/unknown config fields are handled gracefully rather than hard-failing: an `ignore_missing_fields` setting silences warnings for partially-migrated config files, useful across version upgrades where new keys are added. Source: [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/) (`ignore_missing_fields`); changelog shows this evolving (*"skip open_with from missing field validation"*, v1.5.0), [superfile.dev/changelog](https://superfile.dev/changelog/).
- Plugins follow a **dependency-then-flag** pattern: install an external CLI tool (`exiftool` for metadata, `zoxide` for jumping) yourself, then flip a boolean in config, superfile does not vendor or auto-install these dependencies. Source: [superfile.dev/configure/enable-plugin](https://superfile.dev/configure/enable-plugin/), [superfile.dev/list/plugin-list](https://superfile.dev/list/plugin-list/).

## Notable UX touches worth stealing

**Opinion / recommendation** (grounded in the facts above, cited inline):

- **Border-as-status-line.** Putting the panel title, path, mode, and cursor position *in the border itself* rather than a separate title/status bar means zero extra vertical real estate is spent on chrome, the whole box's edge is functional. Source of observation: demo screenshot + `show_panel_footer_info`/`sidebar_sections` config, [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/). Directly relevant to a repo-panel TUI: a repo panel's border could carry branch name, ahead/behind counts, and dirty-state glyph the same way.
- **Focus signalled by border colour alone, consistently, everywhere.** One `*_border_active` key per panel type, defined once in the theme, means a user never has to learn "how does *this* widget show focus" per-widget. Source: theme key inventory, [superfile.dev/configure/custom-theme](https://superfile.dev/configure/custom-theme/).
- **Two complete, swappable keymap files instead of a vim toggle**, discussed above, cleanly solves "vim users vs. everyone else" without a hybrid config. Source: [superfile.dev/configure/custom-hotkeys](https://superfile.dev/configure/custom-hotkeys/).
- **Ctrl-gates destruction, not confirmation dialogs alone**, as the *primary* layer of safety (per the stated hotkey design concept), with confirmation modals as a second layer for genuinely destructive ops (permanent delete, quit-with-unsaved-state). Source: [superfile.dev/configure/custom-hotkeys](https://superfile.dev/configure/custom-hotkeys/); modal confirm/cancel pattern, [`src/internal/ui/notify/model.go`](https://github.com/yorukot/superfile/blob/main/src/internal/ui/notify/model.go).
- **A tiny first-party command language (SPF mode) that's distinct from raw shell mode**, so "manipulate panels" (`split`, `open <path>`, `cd <path>`) is discoverable and scriptable without full shell risk, while raw shell is still one keystroke away for anything else. Source: [superfile.dev/getting-started/tutorial](https://superfile.dev/getting-started/tutorial/) ("SPF Prompt"). A multi-repo git TUI has an obvious analogue: a prompt mode for `open <repo>`, `filter <pattern>`, `fetch-all`, etc.
- **Theme contribution is treated as a first-class, checklist-gated design review**, not just "drop a TOML and merge", contributors must screenshot focused/unfocused borders, the help menu, a popup, and both success and failure states before a theme PR is accepted. Source: [superfile.dev/contribute/how-to-contribute](https://superfile.dev/contribute/how-to-contribute/) ("🎨 Adding a Theme" checklist). This is a process idea, not a UI idea, but it's directly reusable for any themeable TUI project.
- **Graceful capability fallback for terminal graphics** (probe with an escape sequence, prefer Kitty protocol, fall back to ANSI blocks, never hard-fail) is a good template for any terminal-capability-dependent feature (truecolor vs 256-colour, unicode box-drawing vs ASCII). Source: [superfile.dev/getting-started/image-preview](https://superfile.dev/getting-started/image-preview/).
- **Progress state as icon-identity, not animation-identity**: a static clock icon = pending/running, a static checkmark = done, with the *bar fill* carrying the sense of motion, cheap to render, unambiguous in a screenshot, and doesn't require an animation frame budget. Source: demo screenshot observation.

## What would NOT transfer to a git multi-repo TUI

**Opinion**, reasoned from the facts cited above:

- **The five-panel fixed grid (sidebar / panel(s) / preview / processes / metadata / clipboard) is shaped around filesystem browsing**, not around "a set of repositories, each with its own state machine." A git multi-repo tool's natural unit is a *repo* (with branch, ahead/behind, dirty/clean, last-fetch time), not a *directory listing row*, metadata and clipboard panels in particular (file size/MD5/EXIF-style metadata; cut/copy staging of files) have no direct analogue when the "items" are whole repositories rather than files. Source for the panel set: [superfile.dev/getting-started/tutorial](https://superfile.dev/getting-started/tutorial/), [superfile.dev/contribute/how-to-contribute](https://superfile.dev/contribute/how-to-contribute/).
- **Selection mode as Vim-visual-mode-for-bulk-file-ops** maps to "select multiple repos to fetch/pull in bulk," which is genuinely useful, but the *file-operation* verbs it's built around (copy/cut/paste/compress/extract/permanently-delete) don't translate; a repo-multi-select's verb set is entirely different (fetch, pull, stash, switch-branch, open-in-editor), so only the *interaction pattern* (shift+arrow range select, `A` select-all, mode indicator in the corner) transfers, not the verbs themselves. Source: [superfile.dev/getting-started/tutorial](https://superfile.dev/getting-started/tutorial/) ("Selection mode", "File operations").
- **The Ctrl-gates-destructive-actions rule was designed around irreversible filesystem mutation** (delete, overwrite) where "as long as you don't press ctrl your files are safe" is a meaningful guarantee. Git operations have a different risk shape (some are trivially reversible (checkout, stash) and some are genuinely destructive in a way `ctrl+` alone doesn't capture (force-push, hard reset, discarding uncommitted changes)) so the *rule itself* (single-modifier-class = safe) likely needs to be rethought per-command rather than reused wholesale. Source of the original rule: [superfile.dev/configure/custom-hotkeys](https://superfile.dev/configure/custom-hotkeys/).
- **Image/video/PDF inline preview and terminal-graphics-protocol detection** is file-manager-specific machinery with no equivalent need in a repo-status tool (at most you'd want a *diff* or *log* preview pane, which is a text-rendering problem, not an image-protocol problem). Source: [superfile.dev/getting-started/image-preview](https://superfile.dev/getting-started/image-preview/).
- **Metadata plugin (exiftool-backed) and MD5 checksum panel** are filesystem-object concerns (file bytes, EXIF, checksums) that have no meaningful equivalent for "a repository" as the unit of interest. Source: [superfile.dev/list/plugin-list](https://superfile.dev/list/plugin-list/).
- **Zoxide-style frecency jumping between directories** is a reasonable idea to borrow *conceptually* (jump between recently/frequently used repos by fuzzy name) but the actual zoxide integration is directory-path-specific and would need to be reimplemented against a repo list, not reused. Source: [superfile.dev/list/plugin-list](https://superfile.dev/list/plugin-list/).
- **`cd_on_quit`** (exiting the file manager changes your shell's cwd to wherever you last browsed) is meaningful because file managers are fundamentally about "where am I in the tree", the nearest analogue for a repo tool (exiting `cd`s you into the last-focused repo's directory) is plausible but much lower-value, since a git TUI's primary output is usually *state you read*, not *a location you navigate to*. Source: [superfile.dev/configure/superfile-config](https://superfile.dev/configure/superfile-config/) (`cd_on_quit`).
