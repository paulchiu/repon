# Rust TUI and git stack options

Research scope: a multi-repo git TUI built on ratatui. Primary sources only (docs.rs, crates' own repos/READMEs, ratatui.rs, gitoxide's repo/docs, git2-rs docs), each claim cited with exact URL and version. Compiled 2026-08-28.

## ratatui: version, rendering model, widgets, async/event-loop, backends

- **Current version: 0.30.2**, license **MIT**. Source: [crates.io/crates/ratatui](https://crates.io/api/v1/crates/ratatui) (API, checked 2026-08-28), `max_version: 0.30.2`, published 2026-06-19, `license: MIT`. Confirmed on [docs.rs/ratatui/latest/ratatui](https://docs.rs/ratatui/latest/ratatui/) and the [GitHub README](https://github.com/ratatui/ratatui) (MIT badge/LICENSE reference).
- **Rendering model**: immediate mode over a double-buffered cell grid. Per the [docs.rs crate docs](https://docs.rs/ratatui/latest/ratatui/), the app re-renders the full UI every frame via `terminal.draw(|frame| { ... })`; ratatui diffs the new buffer against the previous one and only writes the changed cells to the terminal (differential/partial redraw under the hood, immediate-mode API on top). The [GitHub quickstart](https://github.com/ratatui/ratatui) shows the canonical loop: call `terminal.draw(render)` with a closure that receives a `Frame`.
- **Widget set**: a `widgets` module (Block, List, Table, Paragraph, Gauge, Chart, Tabs, etc.) composed via the `Layout`/`Constraint` system for responsive terminal layouts. As of **0.30.0** the project moved to a Cargo workspace split (`ratatui-core`, `ratatui-widgets`, `ratatui-crossterm`, `ratatui-termion`, `ratatui-termwiz`); application authors depend on the umbrella `ratatui` crate, while widget-library authors are pointed at the lighter `ratatui-core` for API stability and fewer transitive deps. Source: [docs.rs/ratatui](https://docs.rs/ratatui/latest/ratatui/) crate-level docs.
- **Async/event-loop story**: ratatui itself has no async runtime dependency. Its own FAQ states plainly that ratatui "isn't inherently async" and that the only ratatui-adjacent piece worth making async is reading key events from stdin; rendering via `terminal.draw` is fast enough that async is not needed for that call. It lays out two patterns (a single-threaded sync loop (get key → update state → render) and a multi-threaded/tokio loop (separate event/main/render tasks)) and says to reach for async/tokio only when the rest of the app genuinely needs concurrent I/O. Source: [ratatui.rs/faq](https://ratatui.rs/faq/), "When should I use `tokio` and `async`/`await`?".
- The [Event Handling concept page](https://ratatui.rs/concepts/event-handling/) documents three patterns for wiring input instead: (1) centralized `event::read()` matching inline (simple, doesn't scale), (2) centralized polling + message/channel dispatch to sub-functions (works well multi-threaded), (3) distributed event loops where sub-modules take over the Terminal and their own loop. It does not itself prescribe tokio or threading mechanics, that's left to the app.
- **Backends**: ratatui supports **Crossterm** (default, cross-platform Windows/macOS/Linux), **Termion** (Unix-only), **Termwiz** (WezTerm's terminal lib), and **Termina**. The official [Backend Comparison page](https://ratatui.rs/concepts/backends/comparison/) gives a one-line TL;DR: **"Choose Crossterm for most tasks,"** noting it's the most widely used and easiest to learn due to popularity; Termwiz is called out as being for "WezTerm users only." The [Backends overview page](https://ratatui.rs/concepts/backends/) separately warns to avoid mixing incompatible major versions of the backend crate (ratatui 0.30.2 defaults to **crossterm 0.29**, with a documented migration path for apps still on 0.28).
- Backend crate versions/licenses (crates.io API, 2026-08-28): `crossterm` **0.29.0**, license MIT; `termion` **4.0.6**, license MIT; `termwiz` **0.23.3**, license MIT; `ratatui-termwiz` **0.1.2**, license MIT.

## State/architecture patterns the ratatui docs/templates recommend

- The [Application Patterns section](https://ratatui.rs/concepts/application-patterns/) documents three named patterns: **The Elm Architecture (TEA)**, **Component Architecture**, and **Flux Architecture**.
- **The Elm Architecture** ([ratatui.rs/concepts/application-patterns/the-elm-architecture](https://ratatui.rs/concepts/application-patterns/the-elm-architecture/)): classic Model/Update/View. `Model` holds all app state; an enum of `Message`s (e.g. `Increment`, `Quit`) represents things that can happen; `update(model, message) -> model` (optionally returning a follow-up message, enabling FSM-style cascades) is the single place state changes; `view(model) -> ratatui widgets` is documented as a pure function ("identical model states always produce identical outputs"), with the page acknowledging pragmatic exceptions (mutable refs for `StatefulWidget`, cursor placement for text inputs). The app loop is: read event → map to message → `update` → `view`/render.
- **Component Architecture** ([ratatui.rs/concepts/application-patterns/component-architecture](https://ratatui.rs/concepts/application-patterns/component-architecture/)): presented explicitly as the "object-oriented alternative to TEA." A `Component` trait exposes `init`, `handle_events`/`handle_key_events`/`handle_mouse_events`, `update`, and `render`; each component owns and co-locates its own state, event handling, and drawing rather than routing everything through one global update function. The page cites real projects using this shape (gobang, edma) and points at the official templates repo for a reference implementation.
- **Official templates**: [github.com/ratatui/templates](https://github.com/ratatui/templates) (MIT licensed), scaffolded via `cargo-generate`, offering: Hello World, Simple, Simple Async, Event Driven, Event Driven Async, and Component templates, all on ratatui + crossterm, with the async variants pulling in **tokio** and the Component template implementing the Component-trait/message-passing pattern described above. Note: the older, separately-named `ratatui-org/async-template` repo is archived/deprecated in favor of this templates repo (per [search results](https://github.com/ratatui/async-template) pointing to `ratatui/templates`).
- Net takeaway from ratatui's own docs: **no single mandated architecture**, TEA for a centralized, functional/FSM-friendly model; Component for larger apps that want self-contained, independently-testable UI pieces (this fits a multi-repo TUI well: one component per repo pane/tab).

## Git access: gitoxide (gix) vs git2 (libgit2 bindings) vs shelling out

| | **gix** (gitoxide) | **git2** (libgit2 bindings) | shelling out to `git` |
|---|---|---|---|
| Version (2026-08-28) | **0.87.1** | **0.21.0** | n/a (system binary) |
| License | MIT OR Apache-2.0 | MIT OR Apache-2.0 (binds **libgit2**, which is **GPL-2.0 with a linking exception**, not MIT/Apache, see licence section) | depends on invoking process only |
| API maturity | Mixed: workspace of ~many sub-crates, most in "Initial Development"/"Stabilization Candidate," only `gix-lock` and `gix-tempfile` marked "Production Grade" per the project's own stability tiers | Mature, stable, wraps the long-established libgit2 C API 1:1; 100% doc coverage on docs.rs | Fully mature (it's git itself), but you get text, not a typed API |
| Coverage: status/log/diff/branch/fetch | `Repository` exposes `index_worktree_status`/`tree_index_status`/`is_dirty`, `rev_walk`/`head_commit`/`commit_graph`, `diff_tree_to_tree`/`diff_resource_cache`, `branch_names`/`branch_remote_name`, `find_remote`/`remote_names` (all present but some (e.g. push, some worktree ops) sit behind feature flags and are newer/less battle-tested | `status_file`/`statuses`, `revwalk`, `diff_tree_to_tree`/`diff_tree_to_index`/`diff_tree_to_workdir`/`diff_index_to_workdir`/`diff_blobs`, `branch`/`branches`/`find_branch`, `find_remote`/`remotes` + `Remote::fetch`) comprehensive, 1:1 with libgit2's mature surface | Full coverage trivially (`git status --porcelain=v2`, `git log`, `git diff`, `git branch`, `git fetch`), at the cost of parsing porcelain/plumbing text output yourself and one process spawn per call |
| Performance | Project explicitly aims to "be the best performing implementation" and touts parallelism "from the get go." A cited discussion benchmark shows ~4x scaling in multithreaded commit traversal, and one comparison found gix confirming 8,477 commits in 28.3ms (≈299k commits/s) vs libgit2's 35.7ms (≈238k commits/s) on the same repo, but a separate real-world clone benchmark saw gix ~60x slower because it re-packs objects on clone in a way plain `git`/libgit2 doesn't. Net: fast on read-heavy graph/diff workloads, not uniformly faster on every operation. Source: [GitoxideLabs/gitoxide discussion #74](https://github.com/GitoxideLabs/gitoxide/discussions/74) | No first-party perf claims found in git2-rs docs; performance is essentially libgit2's, which is the long-standing C reference implementation used by GitHub Desktop, etc. | Highest fixed per-call overhead (process spawn + text parsing), but git's own internal algorithms are the reference point everyone else is measured against |
| Async-friendliness | Gitoxide's README lists **"use async IO everywhere" as an explicit non-goal**, stating git operations rely heavily on memory-mapped I/O and CPU-bound decompression that "doesn't lend itself well to async IO out of the box"; async is reserved for the transport/TCP layer behind a feature flag. Source: [github.com/GitoxideLabs/gitoxide README](https://github.com/GitoxideLabs/gitoxide), "Non-Goals" section | Not async; it's a synchronous FFI wrapper. git2-rs's own README describes it as "both threadsafe and memory safe", i.e., designed for use from worker threads, not `.await`. Source: [github.com/rust-lang/git2-rs](https://github.com/rust-lang/git2-rs) | Naturally async-friendly at the process level: `tokio::process::Command` gives you a non-blocking spawn/await even though the git binary itself is synchronous |
| What gitui chose, and why | **Uses both.** `asyncgit/Cargo.toml` depends on `git2 = "0.21"` (with https/ssh features) **and** `gix = "0.84.0"` simultaneously, plus `git2-hooks = "0.7"`, `rayon`, and `crossbeam-channel = "0.5"` for concurrency, notably **no tokio dependency at all**. Source: [raw Cargo.toml, extrawurst/gitui, asyncgit crate](https://raw.githubusercontent.com/extrawurst/gitui/master/asyncgit/Cargo.toml). gitui's top-level `Cargo.toml` likewise has no `git2`/`gix` direct dep (it's isolated in the `asyncgit` workspace member) and pulls `ratatui = "0.30"`, `crossterm = "0.29"`, `notify = "8"`, `notify-debouncer-mini = "0.7"`, `serde = "1.0"`, `ron = "0.12"` (no `toml`). License: **MIT**. Source: [raw Cargo.toml, extrawurst/gitui root](https://raw.githubusercontent.com/extrawurst/gitui/master/Cargo.toml) and [github.com/extrawurst/gitui README](https://github.com/extrawurst/gitui) (MIT badge). This is strong prior art: gitui runs git2 as its primary backend (mature, complete) off the UI thread via a thread pool + channels, while incrementally adopting gix for specific operations, with neither tied to tokio. |

**Cargo's own choice** is a relevant data point even though Cargo isn't a TUI: Cargo switched to using **gitoxide (`gix`)** by default for listing files in a git repository (PR [rust-lang/cargo#13696](https://github.com/rust-lang/cargo/pull/13696)), with an env-var opt-out (`__CARGO_GITOXIDE_DISABLE_LIST_FILES`), showing gix is considered production-viable for narrow, well-scoped operations even while the crate overall is still marked pre-1.0.

## Concurrency: N parallel repo scans without blocking the UI thread

- ratatui's own guidance (FAQ, above) is deliberately non-prescriptive: reach for tokio/async only if the surrounding app needs it; otherwise a plain OS-thread + channel design is fine and simpler. The **official templates** repo (MIT, [github.com/ratatui/templates](https://github.com/ratatui/templates)) offers both a plain **Simple**/**Event Driven** track and a **Simple Async**/**Event Driven Async**/**Component** track that pulls in **tokio**, so both idioms are "officially" supported starter points, not just community convention.
- Two concrete Rust-idiom choices for the "scan N repos in parallel" problem:
  - **tokio** (**1.53.1**, MIT, [docs.rs/tokio](https://docs.rs/tokio/latest/tokio/)): event-driven async runtime; natural fit if repo scans themselves are I/O-bound (network fetch) or you want structured cancellation/timeouts per repo.
  - **rayon** (**1.12.0**, MIT OR Apache-2.0, [docs.rs/rayon](https://docs.rs/rayon/latest/rayon/)) for CPU-bound parallel data processing (e.g. parallel diff/status computation across repos) combined with **crossbeam-channel** (**0.5.16**, MIT OR Apache-2.0, [docs.rs/crossbeam-channel](https://docs.rs/crossbeam-channel/latest/crossbeam_channel/)) to ship results back to the render loop without blocking it; this is exactly gitui's own choice (rayon + crossbeam-channel, no tokio, see table above).
  - **threadpool** (**1.8.1**, MIT/Apache-2.0, [docs.rs/threadpool](https://docs.rs/threadpool/latest/threadpool/)) is a simpler fixed-worker-pool alternative to rayon, but its last crates.io release was **2020-05-11** (over six years stale as of this research date) making it a maturity/maintenance risk relative to rayon or tokio for a new project.
- Recommendation shape given gix's explicit anti-async stance and git2's synchronous FFI nature: **neither gix nor git2 benefits from tokio directly**; the concurrency win comes from farming each repo scan out to a worker thread (rayon or a manual thread pool) and using a channel (`crossbeam-channel` or `std::sync::mpsc`) to post results back to the ratatui render loop, matching gitui's proven architecture rather than wrapping libgit2/gitoxide calls in `spawn_blocking`.

## Filesystem watching for repo change detection

- **notify**: current stable version **8.2.0** (a **9.0.0-rc.4** prerelease also exists on crates.io as of 2026-08-28), license **CC0-1.0** (public domain). Source: [crates.io API](https://crates.io/api/v1/crates/notify) and [docs.rs/notify](https://docs.rs/notify/latest/notify/).
  - Backends per platform: Linux/Android → inotify; macOS → FSEvents (default) or kqueue; Windows → `ReadDirectoryChangesW`; BSD/other Unix → kqueue variants; all platforms have a `PollWatcher` fallback for network filesystems and other cases inotify/FSEvents can't cover. Source: [github.com/notify-rs/notify README](https://github.com/notify-rs/notify).
  - Origin/adoption: "Inspired by Go's fsnotify and Node.js's Chokidar, born out of need for cargo watch," and listed as used by alacritty, deno, rust-analyzer, and zed, solid production pedigree for a Rust dev-tool watcher. Source: same README.
  - MSRV **1.88**, with a stated policy that MSRV may bump on minor releases if a dependency needs it, worth pinning in CI. Source: same README.
  - Events go through a channel-based `EventHandler` trait (works with `std::sync::mpsc`, `crossbeam-channel`, or `flume`); there's no native async/await surface, so integrate it the same way as the git backend (worker thread + channel into the render loop), not via `.await`.
- **Companion crates** for debouncing (raw notify events are chatty, e.g. a single `git commit` can fire many): `notify-debouncer-mini` (**0.7.0**, MIT OR Apache-2.0) and `notify-debouncer-full` (**0.7.0** stable / 0.8.0-rc.2 prerelease, MIT OR Apache-2.0). Source: [crates.io API](https://crates.io/api/v1/crates/notify-debouncer-mini). gitui itself depends on `notify = "8"` + `notify-debouncer-mini = "0.7"` for exactly this purpose (see Cargo.toml citation above), which is good prior art for a multi-repo watcher: one debounced watcher per repo (or one recursive watcher at a common root, filtered by repo) feeding the same result channel as the git scans.

## Config file options (toml/serde, figment, config-rs) and theming approaches

- **serde**: **1.0.229**, license MIT OR Apache-2.0. "A generic serialization/deserialization framework." Source: [docs.rs/serde](https://docs.rs/serde/latest/serde/) / [crates.io API](https://crates.io/api/v1/crates/serde).
- **toml**: **1.1.4+spec-1.1.0**, license MIT OR Apache-2.0, "a serde-compatible TOML-parsing library." Source: [docs.rs/toml](https://docs.rs/toml/latest/toml/) / crates.io API.
- **figment**: **0.10.19**, license MIT OR Apache-2.0. Layers multiple config sources (TOML/JSON/YAML/env/custom `Provider`s) into one typed struct via serde, with first-class **provenance tracking** so error messages point at exactly which source/file produced a bad value; built by Rocket's author and documented with guidance aimed at framework authors. Source: [docs.rs/figment](https://docs.rs/figment/latest/figment/). **Maturity flag**: crates.io API shows figment's newest published version dates to **2024-05-17**, over two years old as of this research date, i.e. currently dormant, not actively released.
- **config** (config-rs): **0.15.25**, license MIT OR Apache-2.0. Layered config ("set defaults, then merge in overrides from files/env/programmatic sources") supporting TOML, YAML (via yaml-rust2), JSON/JSON5, INI (via rust-ini), RON, and custom formats via a `Format` trait; also supports live file watching and dotted-path deep access. Source: [docs.rs/config](https://docs.rs/config/latest/config/). This is the more actively released of the two layered-config crates as of 2026-08-28.
- **Theming approach used by an existing Rust git TUI**: gitui depends on `ron = "0.12"` (Rusty Object Notation) and **not** `toml` in its root `Cargo.toml` (see citation above); it defines its themes/keybindings as RON files rather than TOML, and its README documents per-user customizable color themes with automatic light/dark terminal detection, plus vim-style keybinding alternatives, both configured via user config files. Source: [github.com/extrawurst/gitui README](https://github.com/extrawurst/gitui) and [raw Cargo.toml](https://raw.githubusercontent.com/extrawurst/gitui/master/Cargo.toml).
- For a new project: `serde` + `toml` is the minimal, most conventional Rust config stack (what most CLI/TUI tools reach for first); `figment` or `config` are worth it only once you need layering (defaults → file → env → CLI flag), of the two, `config` looks better-maintained right now given figment's multi-year-stale release history.

## Recommended default stack, with the single biggest risk

**Recommended stack:**
- UI: **ratatui 0.30.2** (MIT) with the **crossterm 0.29** backend (ratatui's own "choose Crossterm for most tasks" default), [ratatui.rs backend comparison](https://ratatui.rs/concepts/backends/comparison/).
- Architecture: **Component Architecture** (per-repo-pane components implementing ratatui's documented `Component` trait shape), scaffolded from the official `ratatui/templates` **Component** template, a natural fit for "multi-repo," since each repo/tab is one component owning its own state, event handling, and render.
- Git backend: **git2 (0.21.0)** as the primary/only backend to start (mature, complete coverage of status/log/diff/branch/fetch, and it's the backend gitui leans on as primary today. Keep `gix` in view for a specific narrow win later (e.g. fast parallel status/log scanning across many repos) exactly as gitui itself does) both dependencies side by side, not an either/or.
- Concurrency: **no tokio.** One worker thread (or a small `rayon` pool) per repo scan, reporting back over `crossbeam-channel` (0.5.16) into the main ratatui render loop, mirrors gitui's proven, tokio-free architecture and matches gitoxide's own stated preference to keep git operations off an async runtime.
- Filesystem watching: **notify 8.2.0** + **notify-debouncer-mini 0.7.0**, one recursive watcher (or one per repo root) feeding the same result channel as the git scans.
- Config: **serde 1.0 + toml 1.1** for the common case; reach for **config-rs 0.15** only if true multi-source layering (file → env → CLI) is a real requirement, skip figment given its multi-year-stale release history.
- Theming: a user-editable theme file (RON, following gitui's precedent, or TOML for consistency with the rest of config) mapped onto `ratatui::style::Color`/`Style` at load time, with light/dark auto-detection as a stretch goal.

**Single biggest risk**: **`git2`'s statically-vendored `libgit2` is the one dependency in the entire stack whose license text is not MIT/Apache** (GPL-2.0 with a linking exception, see licence table above). It's legally safe to link and ship, but it's the item most likely to trip an automated "all deps must be Apache/MIT" license-scanner or a legal review that doesn't know to look for the linking-exception carve-out, and it's the one place a policy exception or scanner allow-list entry will need to be documented up front rather than discovered late. (If that risk is unacceptable, the fallback is dropping to `gix`-only for the git backend, pure Rust, MIT OR Apache-2.0 throughout, at the cost of relying more heavily on sub-crates the project's own stability tiers still mark as pre-"Production Grade.")
