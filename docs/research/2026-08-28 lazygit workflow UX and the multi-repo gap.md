# lazygit workflow UX and the multi-repo gap

Research notes for Repon (see `CONTEXT.md`): lazygit owns the *inner loop* (work inside one repo); Repon owns the *outer loop* (seeing and acting across many repos). This document studies lazygit's workflow UX as the model to imitate for the outer loop, and documents exactly where lazygit's own multi-repo support stops.

Primary sources: the [lazygit README](https://github.com/jesseduffield/lazygit/blob/master/README.md), [`docs/Config.md`](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md), [`docs/Custom_Command_Keybindings.md`](https://github.com/jesseduffield/lazygit/blob/master/docs/Custom_Command_Keybindings.md), [`docs/Custom_DiffRenderers.md`](https://github.com/jesseduffield/lazygit/blob/master/docs/Custom_DiffRenderers.md), the generated [English keybindings cheatsheet](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md), and the project's issue tracker. Facts are cited inline; anything that is my own reading or recommendation is explicitly marked **Opinion**.

## The panel model and how focus moves

lazygit's screen is a fixed grid of list panels down the left with one shared main panel on the right. The default panel order and grouping is literally spelled out in the config schema:

> "The side panels, in the order they appear from top to bottom. Each entry is a list of one or more names that share a single panel as tabs (cycle through them with the next-tab/previous-tab keys)... Valid names are: 'status', 'files', 'worktrees', 'submodules', 'branches', 'remotes', 'tags', 'commits', 'reflog', 'stash'. 'files', 'branches', and 'commits' must always be included; they can't be hidden."
>, [`docs/Config.md`, `gui.sidePanels`](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md#L118-L131)

The shipped default groups them as `[status]`, `[files, worktrees, submodules]`, `[branches, remotes, tags]`, `[commits, reflog]`, `[stash]`, five stacked boxes, several of which are themselves tab-groups you cycle with `[`/`]` ([Config.md](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md#L126-L131), confirmed against the `[`/`]` "Previous/Next tab" bindings in the ["List panel navigation"](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#list-panel-navigation) section of the cheatsheet).

Selecting an item in a side panel drives what the shared main panel shows (select a file and the main panel shows its diff, select a commit and it shows that commit's diff. An outside reviewer of the UX describes this as the core discipline of the whole interface: "you always have a focus on one box" and "when you interact with boxes on the left, the right box changes" ([bwplotka.dev, "The (lazy) Git UI You Didn't Know You Need"](https://www.bwplotka.dev/2025/lazygit/)). **Opinion**: this single-focus, live-preview-on-selection model is the part most worth carrying into a multi-repo tool) select a repo in the list, its status/diff/branch fills the detail pane, with no modal jump.

Two further navigation mechanics matter:

- **Screen modes**: `+` and `_` cycle the focused panel through normal/half/full screen "so that you can see more of the main section" ([README, Commit graph](https://github.com/jesseduffield/lazygit/blob/master/README.md#commit-graph); flag documented as `-sm/--screen-mode` with values `normal|half|full`, per the [Debian manpage](https://manpages.debian.org/trixie/lazygit/lazygit.1)). `gui.expandFocusedSidePanel` similarly lets the focused side panel grow "accordion" style ([Config.md](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md#L104-L111)).
- **`0` always focuses the main panel** from any list panel, a single consistent escape hatch to "go look at the detail" that appears in nearly every panel's row in the cheatsheet (e.g. [Files](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#files), [Commits](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#commits), [Local branches](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#local-branches)).

## Context-sensitive keybindings (the core DX idea) and how the cheatsheet/help surfaces them

The defining DX idea is that the same keys mean different, panel-appropriate things, and the tool actively teaches you this rather than hiding it. Concretely:

- `d` is "Discard" in Files, "Drop" in Commits, "Delete" in Local branches, "Delete" (remote branch) in Remote branches, "Remove" in Remotes/Submodules/Worktrees/Stash, and "Delete" (tag) in Tags, one physical key, panel-specific verb, always the "destructive/remove" action for that panel (cross-referenced across the [Files](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#files), [Commits](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#commits), [Local branches](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#local-branches), [Worktrees](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#worktrees) and [Tags](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#tags) tables in the cheatsheet).
- `w` is "New worktree" in Local branches, Commits, Remote branches, Reflog, Sub-commits, Stash and Tags, the same mnemonic works from anywhere you can point at a ref (same cheatsheet, cross-panel search for `New worktree`).
- `<space>` is "Stage" in Files, "Checkout" in Commits/Reflog/Sub-commits/Remote branches/Tags, "Pick hunk" in the merge-conflict main panel, and "Apply" in Stash, always "the primary, low-friction action on the selected item," but that primary action is panel-defined ([Files](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#files), [Commits](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#commits), [Main panel (merging)](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#main-panel-merging), [Stash](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#stash)).

This is a designed, first-class concept, not an incidental side effect of many keymaps. The custom-commands system exposes "context" as a literal config field with an enumerated, closed set of values (`status`, `files`, `worktrees`, `submodules`, `localBranches`, `remotes`, `remoteBranches`, `tags`, `commits`, `reflogCommits`, `subCommits`, `commitFiles`, `stash`, `global`), and documents that "global" is the one context that "will take affect everywhere" ([Custom_Command_Keybindings.md § Contexts](https://github.com/jesseduffield/lazygit/blob/master/docs/Custom_Command_Keybindings.md#contexts)). A context can also be a comma-separated list, e.g. `context: 'commits, subCommits'`, to bind one command to more than one panel at once (same doc, "Bonus" note).

The cheatsheet itself is generated, not hand-maintained: the top of the English file reads "This file is auto-generated. To update, make the changes in the pkg/i18n directory and then run `go generate ./...` from the project root" ([Keybindings_en.md, line 1](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md)), and it exists in at least nine languages ([`docs/keybindings/` directory listing](https://github.com/jesseduffield/lazygit/tree/master/docs/keybindings)). In-app, the same information surfaces live: pressing `?` opens a "keybindings menu" ([Global keybindings row](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#global-keybindings)), and the docs state that "Custom command keybindings will appear alongside inbuilt keybindings when you view the keybindings menu by pressing '?'" ([Custom_Command_Keybindings.md](https://github.com/jesseduffield/lazygit/blob/master/docs/Custom_Command_Keybindings.md#L46)) (so the help surface is always a live, context-filtered reflection of what the current panel can actually do, user customizations included. **Opinion**: this is the single most transferable idea for a multi-repo tool) a small, closed set of panel "contexts" (e.g. repo-list, per-repo detail, branch-across-repos) each with their own dense keymap, plus one context-aware `?`/help overlay that is generated from the same binding table the app runs on, not hand-written prose that drifts.

## Staging, committing, branching, rebasing: the interaction flows worth carrying over

These are lazygit's headline features, each demonstrated with a demo GIF in the README and each collapsing what is normally a multi-command, editor-round-trip git workflow into a few keystrokes inside one screen:

- **Line-level staging**: "Press space on the selected line to stage it, or press `v` to start selecting a range of lines. You can also press `a` to select the entirety of the current hunk." ([README § Stage individual lines](https://github.com/jesseduffield/lazygit/blob/master/README.md#stage-individual-lines))
- **Interactive rebase, done incrementally or all at once**: "Press `i` to start an interactive rebase. Then squash (`s`), fixup (`f`), drop (`d`), edit (`e`), move up (`ctrl+k`) or move down (`ctrl+j`) any of the TODO commits, before continuing the rebase by bringing up the rebase options menu with `m`... You can also perform any of these actions as a once-off (e.g. pressing `s` on a commit to squash it) without explicitly starting a rebase." ([README § Interactive Rebase](https://github.com/jesseduffield/lazygit/blob/master/README.md#interactive-rebase)), no TODO file ever opens in an editor unless you explicitly ask for one.
- **Cherry-pick**: "Press `shift+c` on a commit to copy it and press `shift+v` to paste (cherry-pick) it." ([README § Cherry-pick](https://github.com/jesseduffield/lazygit/blob/master/README.md#cherry-pick))
- **Amend any commit, not just HEAD**: "Pressing `shift+a` on any commit will amend that commit with the currently staged changes (running an interactive rebase in the background)." ([README § Amend an old commit](https://github.com/jesseduffield/lazygit/blob/master/README.md#amend-an-old-commit))
- **Rebase from a marked base commit**: mark a commit as the rebase base with `shift+b`, then press `r` on the target branch to rebase "only bringing across the commits from our feature branch" ([README § Rebase from marked base commit](https://github.com/jesseduffield/lazygit/blob/master/README.md#rebase-from-marked-base-commit)).
- **Undo/redo via reflog**: "You can undo the last action by pressing `z` and redo with `shift+z`... Undo uses the reflog which is specific to commits and branches so we can't undo changes to the working tree or stash." ([README § Undo](https://github.com/jesseduffield/lazygit/blob/master/README.md#undo))
- **Rebase magic / custom patches**: build a patch from an old commit's diff at the line level, then remove/move/reverse-apply it, all inside the TUI ([README § Rebase magic](https://github.com/jesseduffield/lazygit/blob/master/README.md#rebase-magic-custom-patches)).

A second-source review of the same flows independently confirms how few keystrokes real sequences take in practice ("amending and force-pushing becomes '2 space A P enter'" and interactive rebase with reordering is roughly "3 r i \<arrange\> m c") and states plainly that "short key bindings are game changers in general" ([bwplotka.dev](https://www.bwplotka.dev/2025/lazygit/)).

**Opinion**: none of these specific git flows need to be reproduced by a multi-repo tool (that's exactly the inner-loop work Repon hands back to lazygit per `CONTEXT.md`). What's worth carrying over is the *shape* of the interaction: a single keystroke does the obvious primary action on the selected item, a capital/shift variant does the more consequential sibling action (stage vs. amend, copy vs. paste, checkout vs. force-checkout), and multi-step git sequences (rebase, cherry-pick) become a mark-then-act two-step instead of a multi-flag command line.

## Speed and responsiveness expectations users have of it

lazygit is a compiled Go binary using the [gocui](https://github.com/jesseduffield/gocui) terminal-UI library, which the project maintains itself, a technical choice that keeps the tool a single dependency-free executable. Responsiveness is treated as a first-class, configurable concern, not an afterthought:

- Background polling intervals are explicit config, defaulting to a 10s file/submodule refresh, 60s fetch, and 2s external-change-detection poll, each individually toggleable via `git.autoRefresh` / `git.autoFetch` / `git.autoDetectExternalChanges` ([Config.md § refresher](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md#L553-L566)).
- The user-visible bar for "acceptable" is near-instant even on large repos. In [issue #2875, "Very slow on large repositories"](https://github.com/jesseduffield/lazygit/issues/2875) (opened against the Linux kernel checkout), a maintainer's own baseline was offered as the comparison point: "Wow, that's bad. For me, it takes 12s to load without the config, and basically instantaneous with the config", where "the config" was a one-line `git.log.order: default` tweak plus (crucially) running `git gc`, after which the reporter confirmed "the repo opens up in seconds only." The issue was closed as resolved by that combination of a config change and repo hygiene, not a lazygit-side fix ([issue #2875 thread](https://github.com/jesseduffield/lazygit/issues/2875)).
- Lag that does turn out to be lazygit's own fault gets treated as a bug worth batching git invocations to fix: a 2026 write-up describes a case where "lazygit was making **one Git command per file**" when discarding many files at once, causing a UI freeze on 100+ file selections, fixed by a PR that "Collects files into batches" and issues one `git reset`/`git checkout` per batch instead ([Abanoub Hanna, "Fixing UI Lag"](https://abanoubhanna.com/posts/lazygit-ui-lag/)). **Opinion**: this is a fact about lazygit's own engineering, but it's also the general lesson, N git subprocesses for N items in a list is the default failure mode any repo-list tool will hit first, and it gets worse, not better, when N is "repos" instead of "files."

**Opinion**: for a multi-repo tool this bar is stricter, not looser, than lazygit's own, a repo list is a fan-out over N git processes (status, ahead/behind, branch) where lazygit only ever pays that cost once. Getting a screenful of repos to feel "basically instantaneous" (the phrase the maintainer himself uses as the standard, above) means the same discipline lazygit applies internally: async/background fetches, debounced polling, and batched/parallel git invocations rather than N sequential ones, from the first version.

## What lazygit already does for multiple repos (recent repos, repo switching, worktrees, submodules) and exactly where it stops

lazygit's own multi-repo surface is real but narrow, every mechanism below operates on **one repo at a time**, with switching between repos as a modal, one-at-a-time action:

- **Recent-repos switcher**: `<ctrl+r>` globally, or `<enter>` on the Status panel, opens a list of "recently open repositories" you can jump into ([Global keybindings, `openRecentRepos`](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#global-keybindings); [Status panel, `recentRepos`](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#status); config keys documented at [Config.md, `keybinding.universal.openRecentRepos`](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md#L725) and [`keybinding.status.recentRepos`](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md#L737)). This switches the whole app's context to a different repo; it is not a simultaneous multi-repo view.
- **Launch flags for picking a repo**: `-p`/`--path` opens a specific repo directly, alongside `-w`/`--work-tree` and `-g`/`--git-dir` for the bare-repo/dotfiles pattern, and `-f`/`--filter` to scope the log to a path ([Debian manpage](https://manpages.debian.org/trixie/lazygit/lazygit.1)), one repo per invocation.
- **Startup-outside-a-repo behavior** is itself configurable (`notARepository: prompt|create|skip|quit`, default `prompt`, which "ask[s] whether to initialize a new repo or open in the most recent repo") ([Config.md](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md#L630-L636)), confirming there is no "browse all repos under a folder" startup mode; the fallback is always either init-here or jump-to-one-recent-repo.
- **cd-on-exit shell integration**: the README ships a `lg()` shell function using `LAZYGIT_NEW_DIR_FILE` so that "when you call `lg` and exit you'll switch directories to whatever you were in inside lazygit" ([README § Changing Directory On Exit](https://github.com/jesseduffield/lazygit/blob/master/README.md#changing-directory-on-exit)), an explicit acknowledgment that "which repo/directory am I even in now" is a real cross-repo navigation problem, solved here only for the shell prompt, one repo at a time.
- **Repo-specific config layering**: a `.git/lazygit.yml` inside a repo overrides the global config, and "files called `.lazygit.yml` in any of the parent directories of a repo will also be loaded; this can be useful if you have settings that you want to apply to a group of repositories" ([Config.md](https://github.com/jesseduffield/lazygit/blob/master/docs/Config.md#L19)). This is config inheritance for a *group* of repos, not a live multi-repo view or bulk action; it changes what one repo's lazygit instance does, not what you see across repos at once.
- **Worktrees panel**: create/switch/remove worktrees for the current repo, and jump into worktree-creation from Branches/Commits/Tags/Stash/Reflog/Sub-commits with `w` ([Worktrees cheatsheet section](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#worktrees); README demo at [README § Worktrees](https://github.com/jesseduffield/lazygit/blob/master/README.md#worktrees)). Worktrees are multiple working copies of the *same* repository/object-store, not independent repos; this is the closest thing lazygit has to "more than one checkout at once," and it stops at the repo boundary.
- **Submodules panel**: "Enter submodule. After entering the submodule, you can press `<esc>` to escape back to the parent repo" ([Submodules cheatsheet section](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#submodules)). This lets you descend into a nested repo one level at a time, but it's a stack-based drill-down (one repo's UI replaced by another's, `esc` to pop back), not a combined view of the parent and its submodules together.

**Where it stops, precisely**: there is no panel that lists arbitrary, unrelated repos (only *recently opened* ones, or ones reachable via submodule/worktree relationships to the current repo); no directory-scan/auto-discovery of `.git` folders; no simultaneous status view across repos; and no bulk action (pull, fetch, branch, commit) that fans out to more than one repo at a time. Every mechanism above still funnels down to "lazygit is currently pointed at exactly one repo."

## Documented user demand for multi-repo (link real issues/discussions)

This gap is not speculative; it is a recurring, multi-year request thread on the tracker, and the maintainer has stated a design position on it:

- [**Issue #3072, "Add tabs - Manage multiple repositories at the same time"**](https://github.com/jesseduffield/lazygit/issues/3072) (opened 2023-10-14, closed 2024-01-28 as "completed"). The original request: "Add tabs. In each one have a different repository. Show in each tab if there are changes to push or pull." Maintainer [jesseduffield](https://github.com/jesseduffield) replied directly with a design position: "I'd love to have the recent repos menu become a fully-fledged view that lets you e.g. concurrently do a `git pull` on each repo. But having tabs would be going too far," then closed the issue "in favour of [#3278]" (both quotes from the [issue #3072 comment thread](https://github.com/jesseduffield/lazygit/issues/3072)).
- [**Issue #3278, "Dedicated repos view"**](https://github.com/jesseduffield/lazygit/issues/3278) (opened 2024-01-28 by jesseduffield himself, **still open**). This is the maintainer's own framing of what a "no-tabs" multi-repo surface would need: a dedicated view replacing the recent-repos popup, supporting range-select and bulk actions ("switch to repo," "pull/push/fetch," "run a custom command," "run a pre-configured custom command"), explicitly noting "All of these actions (except switching) can support range select, allowing users to easily perform bulk actions (e.g. pull several branches at once)." The open design question in the issue itself is *where the view lives* (popup vs. promoting Status into a real repo-list panel) (it remains unresolved. Commenters piled on with wants that go well beyond the original scope: one linked [**gita**](https://github.com/nosarthur/gita) directly as prior art ("it has a nice way of handling multiple repositories, group them, etc."); another asked for folder-based auto-discovery ("run Lazygit on my `~/git` folder" and see a table of every repo/branch/ahead-behind status at once, with number keys to jump to a repo); a third asked for genuinely cross-repo operations) "create branches across repos, checkout branches across repos... stage all the changes and create 1 commit that gets replicated across two repos," citing IntelliJ IDEA's multi-repo project support as the model ([issue #3278 comment thread](https://github.com/jesseduffield/lazygit/issues/3278)).
- [**Issue #1071, "Work with multiple repositories without the need to leave lazygit and cd to each"**](https://github.com/jesseduffield/lazygit/issues/1071) (2020-11-06, closed as "completed"). The reporter's actual workflow: "I have multiple repositories, each repository represents a microservice," wanting to `cd ~/Dev` and work with all of them from lazygit, citing VS Code's multi-root workspaces as the reference UX. jesseduffield's resolution was to point at the *existing* recent-repos popup ("if you press 'enter' on the status panel you'll get a list of recent repos... Does that satisfy your requirement?"), the reporter accepted it, but a later commenter on the same thread pointed out its real limit: deep/nested repos aren't scanned, unlike VS Code's configurable max-scan-depth ([issue #1071 comment thread](https://github.com/jesseduffield/lazygit/issues/1071)).
- [**Issue #4170, "Is There any way to browser multiple repositories in lazyGit?"**](https://github.com/jesseduffield/lazygit/issues/4170) (2025-01-14, **still open**, no response). Verbatim: "Like vscode, which can scan and list every .git folder under root with open every git repo. Is Lazygit has this feature?"
- [**Issue #3947, "switch to a new repo"**](https://github.com/jesseduffield/lazygit/issues/3947) (2024-09-28, **still open**, labeled *enhancement*). Verbatim: "Currently I can press Ctrl+R to switch into one of recently open repositories, but I cannot switch into any new repository, unfortunately. Even if I would do lazygit manually in another tab inside of that repo, it still does not appear in the list of 'Recent repositories'", a direct statement of the recent-repos mechanism's ceiling.
- Adjacent, narrower asks in the same vein: [**issue #1425**](https://github.com/jesseduffield/lazygit/issues/1425) ("How to support multiple remote repos at the same time?", 2021, closed) is about multiple git *remotes* on one repo rather than multiple repos, but reflects the same underlying friction; [**issue #3293**](https://github.com/jesseduffield/lazygit/issues/3293) ("Support per-repo config files") is the design discussion that produced the `.git/lazygit.yml`/`.lazygit.yml` layering described above, config-per-repo, not a multi-repo *view*.
- Beyond the tracker: a third-party author describes building a separate small TUI, *git-scope*, specifically because "the problem isn't how to manage Git (it was where the changes were" across many repos, framing lazygit as excellent for the single-repo case but silent on the cross-repo overview ([Medium, "Why LazyGit Wasn't Enough for My Multi-Repo Workflow"](https://medium.com/@kumarbharath63/why-lazygit-wasnt-enough-for-my-multi-repo-workflow-ee8c4deca839)) summarized via search result rather than a direct fetch of the full article, so treat the exact wording as approximate). A live Hacker News thread, ["Ask HN: What's your workflow for handling many Git repos locally?"](https://news.ycombinator.com/item?id=46256018), shows the same question being asked independently of lazygit's own tracker.

**Opinion**: the throughline across every one of these threads is the same three asks, repeated by different people over five years: (1) see status/ahead-behind for many repos at a glance, (2) discover repos by scanning a folder tree rather than only remembering "recently opened" ones, (3) bulk-act (mainly pull/fetch, sometimes push) across a selection of them. Nobody in these threads is asking lazygit to edit files or resolve conflicts across repos, the demand is squarely for the "outer loop" `CONTEXT.md` already scopes Repon to, which is a good sign the scoping is right, not that the problem is easy: #3278's own open question (does this live as a popup or a first-class panel?) is exactly the panel-model question this document's first section covers, applied to a list of repos instead of a list of files.

## Adjacent prior art in the multi-repo space

| Tool | What it is | Verdict |
|---|---|---|
| [**gita**](https://github.com/nosarthur/gita) | Python CLI that shows a compact, color-coded status line per repo (ahead/behind/dirty/staged/stashed) and runs a git or shell command across a set of repos, with repos organizable into named groups ("when the project contains several independent but related repos, we can define a group and execute `gita` command on this group," [README](https://github.com/nosarthur/gita)). | Closest existing spirit to what #3278's commenters asked for, and cited by them directly, but it's a batch CLI with a status table, not an interactive TUI with a panel model or context-sensitive keybindings. |
| [**mani**](https://github.com/alajmo/mani) | Go CLI, YAML-config-driven (`mani.yaml`), auto-discovers repos under a directory, runs arbitrary tasks/commands across a filtered set of projects in parallel with tabular output (`mani exec --all git status`), and can `mani sync` to clone a team's whole repo set from the config ([README](https://github.com/alajmo/mani)). | Strong on discovery, config-as-code, and parallel bulk execution; still fundamentally a scripted batch-runner you invoke per-command, not a persistent interactive TUI you sit inside. |
| [**meta**](https://github.com/mateodelnorte/meta) | Node-based "meta repo" pattern: a `.meta` file lists child repos, `meta git clone`/`meta git update` fan a git operation out across all of them, and all behavior beyond that is contributed by npm-style `meta-*` plugins ([README](https://github.com/mateodelnorte/meta)). | Solves reproducible team-wide checkout composition well; it's a command-fan-out and plugin framework, with no visual/TUI layer at all. |
| [**myrepos (mr)**](https://myrepos.branchable.com/) | Perl tool that registers repos (any of git/bzr/hg/darcs/svn/etc.) in `~/.mrconfig`, then runs a uniform verb (`mr update`, `mr status`, `mr commit`) recursively over every registered repo under the current directory, with parallel jobs (`-j5`) and per-repo command overrides. | The most venerable and VCS-agnostic of the batch tools (predates git's dominance); pure CLI, no live status view and no TUI; you get output, not a dashboard. |
| [**git-repo**](https://gerrit.googlesource.com/git-repo/) | Google's manifest-driven tool for Android-scale multi-repo trees: a manifest XML declares dozens/hundreds of repos, `repo sync` fans out clone/fetch across all of them, `repo forall` runs a command in each. Explicitly stated purpose: "Repo is not meant to replace Git, only to make it easier to work with Git" ([gerrit.googlesource.com/git-repo](https://gerrit.googlesource.com/git-repo/)). | Built for a very different scale (hundreds of vendor-partitioned repos forming one product) and for CI/build reproducibility more than day-to-day interactive dev; no TUI, and the manifest model is heavier machinery than most teams' repo sets need. |
| [**gitui**](https://github.com/extrawurst/gitui) | Rust TUI, explicitly positioned as a fast single-repo git client: "GitUI provides you with the comfort of a git GUI but right in your terminal while being portable, fast, free and opensource" ([README](https://github.com/extrawurst/gitui)); its own benchmarks emphasize parsing the Linux kernel's 900k+ commit history in ~24s at low memory. lazygit's own README lists it as an "Alternative" ([README § Alternatives](https://github.com/jesseduffield/lazygit/blob/master/README.md#alternatives)). | Same category and same single-repo scope as lazygit itself, no multi-repo story, but its speed-and-memory obsession is a useful bar for what "fast TUI" means in this genre. |
| [**ghq**](https://github.com/x-motemen/ghq) | Go CLI that organizes *clones* on disk in a `go get`-style hierarchy (`~/ghq/github.com/user/repo`) and offers `ghq get/list/root/rm` to fetch and enumerate them ([README](https://github.com/x-motemen/ghq)). | Solves "where do my clones live and how do I find one by name" cleanly, and is a natural repo-*discovery* source to sit underneath a multi-repo TUI, but it has no status view, no bulk actions, and no interactivity beyond listing paths. |
| [**Jujutsu (jj)**](https://jj-vcs.github.io/jj/latest/) | A from-scratch VCS with a Git-compatible backend, positioned as a Git alternative/complement rather than a wrapper around it (its docs devote whole sections to "Git comparison" and "Git compatibility" ([jj-vcs.dev docs](http://docs.jj-vcs.dev/latest/)). | Operates one repository at a time like git/lazygit/gitui; it changes *how* you version-control a single repo, not how you see or act across many) orthogonal to the multi-repo problem, not a competitor for it. |

## What a complementary multi-repo TUI must do that lazygit does not

Grounded in the gap documented above (lazygit's own explicit stopping points, plus the specific asks from #3278, #1071, #4170, and #3947), a multi-repo companion needs, at minimum:

1. **Discovery by scanning, not just memory.** lazygit only ever offers *recently opened* repos ([issue #3947](https://github.com/jesseduffield/lazygit/issues/3947)) with no folder-tree scan ([issue #4170](https://github.com/jesseduffield/lazygit/issues/4170), [issue #1071](https://github.com/jesseduffield/lazygit/issues/1071)). A companion tool's baseline job is to find every `.git` under a root (with a configurable depth, echoing the VS Code comparison raised twice in these threads), something `ghq`'s clone hierarchy gives for free if adopted as the discovery source, but which a generic tool must do by walking arbitrary directories too.
2. **A simultaneous, glanceable status view across the whole set**, not a one-repo-at-a-time popup, the exact thing jesseduffield rejected doing inside lazygit as "tabs," instead scoping it to "the recent repos menu become a fully-fledged view" in [#3278](https://github.com/jesseduffield/lazygit/issues/3278). The commenter mockup in that issue (repo × branch × ahead/behind × remote, in one table, jump by number) is close to a spec.
3. **Range-select and bulk actions** across repos, pull/fetch at minimum, per [#3072](https://github.com/jesseduffield/lazygit/issues/3072) and [#3278](https://github.com/jesseduffield/lazygit/issues/3278), applying lazygit's own range-select interaction (`v`, `<shift+up/down>`, documented in [List panel navigation](https://github.com/jesseduffield/lazygit/blob/master/docs/keybindings/Keybindings_en.md#list-panel-navigation)) to a list of *repos* instead of a list of files/commits. **Opinion**: this is the single feature most requested and least present anywhere in the prior-art table above, gita and mani get closest, but as scripted batch runners rather than an interactive select-then-act TUI.
4. **The same context-sensitive keybinding + generated-cheatsheet discipline**, applied to repo-list contexts instead of file/commit/branch contexts, reuse the *idea* documented above (small set of named contexts, `?` opens a live, filtered binding menu), not lazygit's specific bindings, since the objects being acted on (repos) are different from lazygit's (files, hunks, commits).
5. **Speed treated as a hard constraint from day one, not a later optimization**, because a repo list is structurally an N-way fan-out of exactly the git subprocess calls lazygit only ever pays once per invocation (see Speed section above; also the batching fix in [Abanoub Hanna's write-up](https://abanoubhanna.com/posts/lazygit-ui-lag/) as a cautionary example of what happens when a tool issues one subprocess per list item).
6. **A clean handoff into lazygit for the inner loop**, not a reimplementation of it, per `CONTEXT.md`'s own scoping, the multi-repo tool's job ends at "here's the repo, here's its state," at which point the natural action is to shell out to (or launch) lazygit already pointed at that repo (`lazygit -p <path>`, per the [manpage](https://manpages.debian.org/trixie/lazygit/lazygit.1)) rather than growing its own staging/rebase UI. Nothing in the issue threads above asks lazygit-the-tool to gain cross-repo *editing*; every request is about visibility and bulk read/sync actions, which is the right scope boundary to keep.
